For a Skin's author

A Skin runs on the tablet and knows only Decaid’s API, so it can show nothing the server holds. The plugin serves it (ADR-0030): a Skin calls an HTTP endpoint of the plugin’s on the tablet, the plugin asks the server over its own connection, and the answer comes back in the same call. So far a Skin reads the status, the Shots at its Machine’s Location, any one of them whole and a Recipe’s Reference Shot, chooses a Recipe’s Reference Shot, and edits the rating and note of any Shot at the Location. It may report its page and be asked to reload. It may also edit a Recipe by writing its DYE2 record itself (Writing DYE2’s recipes).

Calling the plugin

Section titled “Calling the plugin”

Decaid serves a plugin’s endpoints beside its own API, each by its name alone:

Address
HTTP http://<tablet>:8080/api/v1/plugins/decent-sync.reaplugin/<endpoint>
WebSocket ws://<tablet>:8080/ws/v1/plugins/decent-sync.reaplugin/<endpoint>
  • Every answer is JSON. A served request answers 200. A refusal answers another status, with a code and a message (see Refusals). The one exception is page, which answers 204 with nothing in it.
  • Answers come quickly or not at all. Decaid gives a plugin 30 seconds to answer. The plugin gives the server 10: a request still unanswered then is refused as unreachable. While the plugin isn’t connected it refuses at once, without asking. Before it asks the server the plugin may ask Decaid first: for DYE2’s recipes, to read which Recipe reference names, and to write an edit of a Shot. Decaid’s own API answers in milliseconds. Were it to take most of the 30 seconds, the call could run past them, and Decaid then answers it itself, with an error and no code. Treat that as unreachable: a choice or an edit may still have been made.
  • Nothing is queued. A request refused as unreachable was not kept, and is not sent later. Ask again. That holds for a choice and for an edit of another tablet’s Shot too: one refused while the plugin isn’t connected changes nothing, then or later.
  • Decaid answers some requests itself. It answers 404 while the plugin isn’t loaded, and for an endpoint the installed plugin doesn’t have, such as status on the 1.9.0 plugin or an earlier one.
  • The status is asked at once. It doesn’t wait for what the tablet has still to send the server, so it answers while a tablet catches up after an outage.
  • Shots are asked once the tablet has caught up. A request to shots, shot or reference, a choice included, goes to the server behind what the tablet had still to send as the Skin asked, so a Shot pulled a moment ago on this tablet is in the answer, and can be chosen. While a tablet catches up after an outage that can take longer than the 10 seconds, and the request is refused as unreachable, whatever else would have refused it. For a moment after the plugin loads, while it reads back what it kept for the server, they are refused as unreachable at once. Ask the status, which doesn’t wait, to learn whether the Machine is served. A reference refused so is answered from the tablet’s copy where it has one.
  • An edit of a Shot is asked at once. It waits for nothing the tablet has still to send, as it is of a Shot another tablet holds, so a Shot can be rated while a tablet catches up.

Anything on the tablet’s network can call these endpoints, as it can Decaid’s own API but for managing plugins and Skins where Decaid asks a token for it (A token for managing plugins): Decaid checks no caller of them. That network can already change the Workflow and delete Shots through Decaid. The server holds each tablet to its own Machine’s Location, whatever a caller asks for.

Status

Section titled “Status”

GET /api/v1/plugins/decent-sync.reaplugin/status says whether the plugin is connected to the server, whether its Machine is served, and which Machine and Location it is. Call it to decide which screens to show.

A Machine is served while it takes part in the Library: at a Location, with its sharing on, connected as itself. Served, it answers 200:

Otherwise it answers the refusal every other endpoint would give at that moment: that HTTP status, with the same fields and the refusal’s code and message. So served alone decides, whatever the status:

Field What it is
connected Whether the plugin holds a connection the server has welcomed.
served Whether the other endpoints answer for this Machine now.
machine The Machine’s id and name on the server. Null while the server wasn’t asked or didn’t answer, and for hardwareMismatch.
location The Location the Machine is at, by id and name, whether or not it shares there. Null where it is at none, and wherever machine is null.
code, message Why it isn’t served. Absent while it is.

Each call asks the server afresh. Nothing is remembered from the last answer.

The Location’s Shots

Section titled “The Location’s Shots”

GET /api/v1/plugins/decent-sync.reaplugin/shots lists the Shots at the Machine’s Location, whichever Machine pulled them: the Shots the management interface’s Shots list lists for that Location. Newest first by when they were pulled, a page at a time, with no filters.

Query What it is
limit How many Shots the page may hold, from 1 to 50. 50 without it.
cursor The nextCursor of the page before. Leave it out for the first page.
Field What it is
id The Shot’s id, which is Decaid’s. Read it whole with shot.
pulledAt When it was pulled, in UTC.
machine The Machine that pulled it, by its id and name on the server. Compare its id with the status’s to tell this Machine’s Shots from the others’.
onThisTablet Whether this tablet is the one that last reported the Shot, so Decaid’s own API has it unless it was deleted there since.
recipe The Recipe it was pulled with, or null: its id and name on the server, and recordId, the id of this tablet’s DYE2 record of it, which the Workflow names in context.extras.dye.recipeId. recordId is null where this tablet holds no record of the Recipe, as for another Location’s Recipe, which a Shot names once its Machine’s Location History is corrected.
bean The coffee’s roaster and name, as the Shot recorded them.
dose, targetDose The dose weighed and the dose aimed for, in grams.
yield, targetYield The yield weighed and the yield aimed for, in grams.
duration How long it ran, in seconds, without its Preheat.
rating Its rating on Decaid’s scale of 0 to 10, where 0 is unrated.
barista The Barista’s name, as the tablet recorded it.
hasNote Whether it has a note.
unfinished Whether it is an Unfinished Shot, in which nothing poured: the Machine never reported pouring and the scale never showed 1 g in the cup, past a cup weighed before the Shot’s tare. A cleaning or calibration Shot is never one.
referenceOf The Recipes of this Location it is the Reference Shot of, each named as recipe is, by name. Empty for most Shots. An Archived Recipe is left out, and so is another Location’s.

A value the Shot didn’t record is null. nextCursor is null on the last page; otherwise send it back as cursor for the next. A cursor is the server’s to read: treat it as opaque. It stays good while Shots are pulled or leave the list, so a Shot pulled since the first page isn’t in a later one. Read the first page again to see it.

A Shot leaves the list when an Admin corrects its Machine’s Location History so that it was pulled at another Location, and joins that Location’s.

A Shot whole

Section titled “A Shot whole”

GET /api/v1/plugins/decent-sync.reaplugin/shot?id=<Shot's id> gives one of those Shots with its measurements:

Field What it is
shot The Shot’s record with its measurements, as the server stores them, which is as Decaid sent them: what Decaid’s GET /api/v1/shots/<id> gives on the tablet that holds it. Draw it with the code that draws the tablet’s own Shots.
recipe The Recipe it was pulled with, as a row names it, or null.
referenceOf The Recipes it is the Reference Shot of, as a row names them.

A tablet reads whole only a Shot its list would list. Any other is refused as noSuchShot, whether or not the server holds it: another Location’s, a Shot that left the list, and an id that names nothing are answered alike.

A long Shot’s record passes 1 MiB. It is read whole all the same, and takes longer to arrive. Answers reach the tablet in turn, so ask for a few Shots at a time: one still waiting behind the others after 10 seconds is refused as unreachable, and the server leaves requests unanswered while a tablet is far behind on what it asked for. An answer longer than about 16.7 million characters is never sent, so a Shot or a page that long is refused as unreachable each time: no Shot Decaid records comes near it.

A Recipe’s Reference Shot

Section titled “A Recipe’s Reference Shot”

GET /api/v1/plugins/decent-sync.reaplugin/reference?recipe=<record id> gives a Recipe’s Reference Shot: the one Shot chosen to show how the Recipe’s Shots should go. Every tablet at a Location is given the same one, whichever Machine or Location pulled it.

Name the Recipe by the id of its DYE2 record on this tablet: the id the Workflow names in context.extras.dye.recipeId, which each of the tablet’s Shots records, and the recordId the other endpoints give. The plugin turns it into the Recipe’s own id, which the record carries.

Field What it is
recipe The Recipe asked about, named as a row’s recipe is.
reference Its Reference Shot, or null where it has none.
reference.shot, .recipe, .referenceOf The Shot whole, as shot gives one: its record with its measurements, the Recipe it was pulled with, and the Recipes of this Location it is the Reference Shot of.
reference.rating Its rating on Decaid’s scale of 0 to 10, where 0 is unrated. Null where it recorded none.
reference.note Its note, or null.
reference.profileDiffers Whether it was pulled on another Profile than the Recipe’s: the Recipe names a Profile, and the Shot’s is another, or none in the Library. Its curves then describe another program. False for a Recipe that names no Profile.
source "server" where the server answered just now. "tablet" where it couldn’t be asked and this is the tablet’s copy, which may be older.
  • The server is asked first. While it answers, the answer is the server’s, for a Recipe in a slot or in none.
  • The tablet’s copy stands in while the server can’t be asked. The plugin keeps a copy for each Recipe in a Recipe Slot at its Location (Reference Shot copies). Where the request would be refused as unreachable, it answers 200 from that copy instead, with source "tablet". That includes a copy saying the Recipe has none.
  • No copy, no answer. A Recipe in no slot has no copy, and neither has one whose Reference Shot is too large to keep (1 MiB). Those are refused as unreachable while the server can’t be asked.
  • A Reference Shot may be another Location’s. A tablet reads it whole through this endpoint all the same. Through shot that Shot is still refused as noSuchShot.
  • A hidden Shot reads as none. A Reference Shot whose Pending Machine was dismissed is null until that hardware is given a machine entry.
  • A record must be a Recipe of the Library’s. A recipe no record on the tablet has, or whose record carries no Recipe’s id, as one a barista saved moments ago, is refused as noSuchRecipe. So is a Recipe of another Location.

Listen on changes for the push that says a Recipe’s Reference Shot changed, and read it again then.

Choosing a Recipe’s Reference Shot

Section titled “Choosing a Recipe’s Reference Shot”

PUT /api/v1/plugins/decent-sync.reaplugin/reference?recipe=<record id> makes a Shot the Recipe’s Reference Shot, from the tablet where it was judged. Name the Recipe as a read does, by the id of its DYE2 record on this tablet, and the Shot in a JSON body:

It answers 200 with the Recipe’s Reference Shot as it now is: what reading it gives, whole, with source "server". The server makes the choice as it makes one in the management interface, and it reaches every tablet at the Location and the management interface at once.

  • Any Shot the tablet can open. A Shot in the Location’s list, whichever Machine pulled it, or the Reference Shot of one of the Location’s Recipes, which may be another Location’s. Any other Shot is refused as noSuchShot.
  • Only the Location’s Recipes. A Recipe of another Location, which a tablet may still hold a record of for a moment after its Machine moves, is refused as notAtThisLocation. A record that carries no Recipe’s id, or a Recipe the server no longer has, is refused as noSuchRecipe.
  • Not an Archived Recipe. It is refused as archived, as in the management interface, until the Recipe is restored.
  • A tablet can’t clear one. A request names a Shot. One without a shotId is refused as invalidRequest. Clearing a Reference Shot is done in the management interface or by an assistant.
  • A Shot pulled a moment ago can be chosen. The request follows what the tablet has still to send, so the server has the Shot by the time it is asked.
  • It is made now or not at all. While the plugin isn’t connected the request is refused as unreachable at once, without being sent, and nothing is kept to send later. The tablet’s copy is no answer to a choice.
  • A choice the plugin sent may have been made, whatever it answers. The plugin also answers unreachable when it sent the request and has no answer: its connection closed first, or 10 seconds passed. The server may have made that choice already, or make it within the next minute if it was still waiting its turn. The answer doesn’t say which unreachable it is. So after one, read the reference again once the plugin is connected, or wait for the push, before showing the choice as failed.
  • No person is named. The Recipe’s history in the management interface names the Machine the Reference Shot was chosen on, and no account. Anyone at the tablet may choose.
  • The same Shot again changes nothing. It answers 200 as the first time did, and adds nothing to the Recipe’s history.

The tablet’s own copy is replaced a moment after the answer, for a Recipe in a slot, and a push follows it, on this tablet and on the others at the Location.

Editing a Shot’s rating and note

Section titled “Editing a Shot’s rating and note”

PUT /api/v1/plugins/decent-sync.reaplugin/shot?id=<Shot's id> sets a Shot’s rating, its note or both (ADR-0031). It is one call for any Shot in the Location’s list, whichever tablet holds it: a Skin needn’t know where a Shot is held. Send what to set in a JSON body, and leave out what to leave alone:

Field What it is
rating A number from 0 to 10, whole or not, on Decaid’s scale, where 0 is unrated.
note Text of at most 40,000 characters, where empty is none.

It answers 200 with the Shot’s rating and note as they now are:

rating is null where the Shot has none, and note where it has none or only blanks, as a Reference Shot’s are.

  • The tablet’s own Shot works without the server. The plugin sends the edit to Decaid’s own Shot update (PUT /api/v1/shots/{id}) first, with only the fields given. Where Decaid holds the Shot it is written at once, whether or not the plugin is connected, and whether or not the Machine is served: a Capture-only Machine’s Skin rates its own Shots this way too. The edit reaches the server as any edit made on the tablet does, when the plugin is next connected, with no person and nothing added to the Shot’s list of edits.
  • Any other Shot goes through the server. Where Decaid answers that the tablet doesn’t hold the Shot, the plugin asks the server. The server applies the edit at once, so the management interface, the Location’s list and a Shot Summary show it, and writes it into the Shot on the tablet that holds it, now if that tablet is connected and otherwise when it next connects (A Shot’s rating and note).
  • Only the Shots in the Location’s list. Any other is refused as noSuchShot: another Location’s, an id that names nothing, and the Reference Shot of one of the Location’s Recipes that was pulled elsewhere, though the tablet can read that one.
  • Another tablet’s Shot is edited now or not at all. While the plugin isn’t connected the request is refused as unreachable at once, without being sent, and nothing is kept to send later.
  • An edit the plugin sent may have been made, whatever it answers. As for a choice, the plugin also answers unreachable when it sent the request and has no answer. After one, read the Shot again once the plugin is connected before showing the edit as failed.
  • The later edit of a field wins. Where the rating or the note was changed on the tablet that holds the Shot later than this edit, without seeing it, that tablet’s stands, and the Shot’s page in the management interface lists the other as dropped. An edit of the rating never undoes a note, or the reverse.
  • The Machine is named, and no person. The Shot’s page in the management interface lists an edit made through the server with the Machine it was made on, and no account. Anyone at the tablet may edit.
  • Only the rating and the note. Any other field in the body, a null, a rating outside 0 to 10, a note that is too long or holds a NUL or half of a surrogate pair, and a body with neither is refused as invalidRequest, whichever tablet holds the Shot, before Decaid or the server is asked. To clear a rating send 0, and to clear a note send empty text.
  • If Decaid refuses its own Shot’s edit, or doesn’t answer, the request is refused as shotUnwritten, and the server is not asked.
  • Nothing is pushed when a Shot is edited, but for a Recipe’s Reference Shot, whose copy on each tablet follows the edit. Read the list again to show an edit made elsewhere.

Refusals

Section titled “Refusals”

Every refusal is an HTTP status with a code to act on and a message to show. A Skin refused as unreachable, captureOnly or hardwareMismatch shows its tablet’s own Shots.

Code Status When
unreachable 503 The plugin isn’t connected to the server, its connection closed before the answer came, or the server didn’t answer within 10 seconds.
serverTooOld 503 Answered only by the plugins of 1.10.0 to 1.11.1, while connected to a 1.9.0 server during an upgrade; later plugins never answer it, as every server they work with has these endpoints. Treat it as unreachable.
captureOnly 409 The Machine is a Capture-only Machine: at no Location, or with its sharing off.
hardwareMismatch 409 The machine connected to the tablet is not the one the tablet’s token was issued for. Its records wait as a Pending Machine’s, or go to the Machine that hardware belongs to, until an Admin settles it on the Machines page.
noSuchShot 404 No Shot at the Machine’s Location has the id asked for, or to be edited. For a choice: the Shot is none this tablet can open.
noSuchRecipe 404 No DYE2 recipe on the tablet has the record id asked for, or the one that has it is no Recipe of the Machine’s Location. For a choice: its record carries no Recipe’s id, or the server has no such Recipe.
notAtThisLocation 403 A choice only: the Recipe belongs to another Location than the Machine’s.
archived 409 A choice only: the Recipe is Archived.
recipesUnread 500 Decaid didn’t give the plugin DYE2’s recipes, or gave them in a shape it doesn’t recognise, so it couldn’t tell which Recipe was asked about. Ask again.
shotUnwritten 500 An edit of the tablet’s own Shot only: Decaid refused the update, or didn’t answer it. The message gives Decaid’s status. Ask again.
invalidRequest 400 The request is not one the endpoint can read: a limit that is no whole number from 1 to 50, a cursor no page gave, or no id, recipe or, for a choice, shotId, or one longer than 2,048 characters, or, for an edit, a body that sets neither a rating nor a note, or sets one to a value it can’t take, or sets anything else. The message says which.

The plugin answers some of these itself, at once, without asking the server: unreachable while it isn’t connected, recipesUnread, shotUnwritten, noSuchRecipe for a record that carries no Recipe’s id, and invalidRequest for a limit, a missing id, recipe or shotId, an id, recipe, shotId or cursor too long to be one, or an edit’s body. The server answers the rest, and tells a Machine that isn’t served so whatever it asked for, but for an edit of the tablet’s own Shot, which the server is never asked.

A request with a method an endpoint doesn’t take answers 405, with an error in place of a code. status, shots, shot and reference take GET, shot and reference take PUT too, and page takes PUT alone.

Changes

Section titled “Changes”

A Skin listens on the WebSocket endpoint changes rather than polling. Each push is a JSON object whose what names what changed. So far there are three: the two here, and reload, under Reporting the page, and reloading.

It is sent when the server welcomes the plugin’s connection, and when that connection is lost. Read the status again after it: the Machine may have moved, or its sharing changed, while the plugin was away.

It is sent when the tablet’s copy of a Recipe’s Reference Shot changes: another Shot was chosen, on a tablet or anywhere else, or it was cleared, the Shot’s rating or note changed, or the Recipe entered a slot. It names the Recipe as an answer does, recordId being the id of this tablet’s DYE2 record of it. Read reference again for that Recipe if it is the one on screen.

  • Only Recipes in a slot are pushed. A Recipe in no slot has no copy, so nothing is pushed when its Reference Shot changes. Read it again when the Skin shows it.

  • A tablet that was off is pushed what changed when it reconnects, once the server has sent the copies it missed.

  • A push may repeat. One is also sent when the Recipe is renamed, so compare what reference gives with what is drawn.

  • Decaid sends a push only to the sockets open at that moment, and keeps none for a socket opened later. Read the status once the socket opens.

  • A Skin can send nothing on this socket.

  • Ignore a what you don’t know. Later releases add more.

Reporting the page, and reloading

Section titled “Reporting the page, and reloading”

A Skin that reports its page lets an Admin, or Staff at its Location, reload it from anywhere, and the Machine’s Software tab show which build it is showing. A Skin that does neither is unaffected: it is never pushed the reload, and is reloaded only by restarting the Skin view.

Each time the page loads, and each time its socket on changes opens, PUT its Skin id, its version and when the page loaded to the HTTP endpoint page:

  • skinId is the Skin’s id as Decaid’s Skin list names it: the id in its skin-manifest.json. version is optional. loadedAt is an ISO 8601 time, the same for every report of one page load, and later for each new load: performance.timeOrigin gives both. It may be at most a minute ahead of the tablet’s clock.
  • It answers 204, whether or not the plugin is connected to the server. A body it can’t read answers 400 with invalidRequest and a message; any method but PUT answers 405.
  • Only a report from the tablet’s own Skin view counts: one whose Host is localhost, 127.0.0.1 or [::1], as Decaid’s Skin view loads the Skin from http://localhost:<port>/. Address Decaid as your page’s own location.hostname does there. A report from another device, as a browser on the cafe’s network, answers 204 and is not kept, so it never sets what the tablet shows or confirms a reload.
  • Report again each time your socket on changes opens. Decaid keeps it open while it loads the plugin again, as after a settings change or an update; the plugin then holds no page, and still asks your page to reload when asked to, counting the first report of your Skin after its push.

To be reloaded, listen on changes for:

and load the page again (location.reload()). The reload is done once your fresh page reports a later loadedAt than the page before (or, where the plugin holds none, reports at all) within 15 seconds; a page that reports nothing in that time, or a page of another Skin, leaves it not confirmed.

Streamline’s endpoints

Section titled “Streamline’s endpoints”

The plugin’s skin endpoint and its changed WebSocket are the ones Streamline reads, and are unchanged. changed pushes only {"what":"workflow"}, which Streamline reads as a change to the Workflow or DYE2’s recipes. Nothing above is pushed there.

Writing DYE2’s recipes

Section titled “Writing DYE2’s recipes”

A Skin may edit a Recipe by writing its record in DYE2’s list of recipes, recipes under dye2.reaplugin in Decaid’s store, as DYE2’s editor does. The Streamline Cafe Skin does so to change a Loaded Recipe’s Profile or Bean, renaming one still under the name DYE2 generated for it (ADR-0022). The server takes the record’s change as the Machine’s edit of the Recipe and writes it to every tablet at the Location.

  • What the server reads. profileId, beanId with beanBatchId, name, and the dial and settings in dashboardVariables that DYE2’s editor saves. Beside a profileId it reads no profileTitle or profileSnapshot, and beside a beanId no beanName or beanRoaster. It rewrites title, subtitle, the names DYE2 copies and the embedded workflow from the Recipe, so a Skin writes those for DYE2 alone.
  • Write beanId and beanBatchId together. beanId wins: a beanBatchId changed under the Bean the record names already is taken where the batch is of that Bean, and otherwise changes nothing. A beanId with no batch of its own gives the Recipe its batch of that Bean, or else that Bean’s batch most recently added at the Location, or none. A beanId this tablet holds no record of is none, and clears the Recipe’s Bean on every Machine.
  • Write the record before the Workflow. Write the record, then the Workflow: its profile, or its beanBatchId with coffeeName and coffeeRoaster. With a new profile, write the record’s brew temperature (dashboardVariables.brewC) too, and put the Workflow’s profile at it: the other Machines are written the new profile at the Recipe’s brew temperature, as DYE2 applies one. The plugin reads DYE2’s recipes as a Workflow change moves the bean or the profile under a Loaded Recipe, and holds that change back until it has, so the server takes the record’s edit first, and the other Machines have it within seconds. A profile changed in the Workflow alone unloads the Recipe, as DYE2 clears it, unless the record holds that profile already: DYE2 compares the Workflow’s profile with the record’s embedded workflow.profile, or else its profileSnapshot, so write the new profile there too, whole. The server takes the rest of a Workflow change that moves the profile, such as a batch picked with it, only where the record it has been reported holds the new profile already, as DYE2 clears the recipe a moment after any other.
  • What is not taken. An Archived Bean, or a batch held with its Bean that is Archived, of an Archived Bean or not at the Recipe’s Location (never added there, or finished there), changes neither the Recipe’s Bean nor its batch. A profileId that is none of the Library’s Profiles changes none. Where a recipe names a profile the plugin has not read among the tablet’s, it reads and sends the tablet’s profiles before the recipes, so a profile saved on this tablet before the record that names it is the Library’s by then. The Recipe’s own is written back over the record, and nothing is offered or added at the Location. The Workflow keeps what was picked: such a batch stays that Machine’s own, with the Recipe loaded.
  • The server renames nothing. A Recipe’s name changes only as a record or an edit sets it, so a rule renaming one under a generated name is the Skin’s, written in the same record. On a Skin with no such rule, as Streamline, a Recipe keeps its generated name as its Bean changes.
  • Gaps.
    • DYE2, the plugin and a Skin each rewrite DYE2’s whole list, and Decaid’s store takes no conditional write, so a write lost to another made at the same moment is never heard of. Read the list just before writing it, and change only your record.
    • A record written with no Workflow change, as a name edited on its own, reaches the server at the plugin’s next poll, 30 s by default.
    • With a Recipe loaded, any bean batch picked that the Recipe’s Location offers becomes the Recipe’s, so a one-off Shot of another coffee can no longer be pulled under it without changing it.
