# AI Repo Map

## Start here

The repository holds the milestone 1 workspace, scaffolded by [ticket #2](https://github.com/loganfuller/decent-sync/issues/2), with accounts, Locations, Machine identity, and Shot and Steam Record capture.

Target requirements come from `GLOSSARY.md`, accepted `docs/adr/` decisions and [milestone 1](https://github.com/loganfuller/decent-sync/issues/1), then the assigned ticket. ADR-0010 is superseded by ADR-0012, ADR-0015 extends ADR-0004, and ADR-0017 sets the supported Decaid and plugin versions.

Root `package.json` scripts are the commands; the README's Development section lists them. One protocol change updates the plugin, server and shared package together here; the old plugin repo is archived.

`protocol/` exports its TypeScript source under the `@decent-sync/source` condition, which esbuild, TypeScript and Vitest use, so they need no protocol build. Node at runtime uses `protocol/dist`, so the server needs `npm run build -w protocol` first (the root `build`, `start` and `dev:server` scripts do this). The Prisma client is generated into `server/src/generated/` (git-ignored) by the server's `build` and `typecheck` scripts. Tables and columns are snake_case (`@@map`, `@map`) while models keep Prisma's casing.

Every REST route requires a signed-in account unless marked `@Public()` (`server/src/accounts/guards.ts`); only health, first-run setup, sign-in, and invite and password reset links are public. A route that requires an account requires an Admin unless marked `@AllowStaff()`, so a new route stays Admin-only until Staff are meant to use it. `server/test/access.test.ts` names every route marked either way, and fails until a new one is named. Staff read everything an Admin reads (Locations, Machines, Pending Machines, Shots, Steam Records and the rest) except other accounts' personal information; restricting reads further is for a later version. What their Locations limit is what they change. A Staff route that changes something takes the account's `Scope` (`@CurrentScope()`, `server/src/accounts/scope.ts`): the Locations a Staff member works at (`staff_locations`, also in the account's `locations`), read with the session on every request and never kept, so a change applies to the next request on any instance. Staff may move a Machine from now from one of those Locations to another, judged under its row lock; every other change is Admin-only. Invites (`server/src/accounts/invites.service.ts`) and password reset links (`password_resets`, `server/src/accounts/password-resets.service.ts`, at most one per account, replaced when another is issued) hold a random secret stored only as its hash; expiry is set and judged by PostgreSQL's clock, and acceptance, redemption and revoking an invite each claim it with a conditional update, so of concurrent ones on any instances only the first succeeds. An Admin's change to an account (its role and Locations, deactivating or reactivating it, issuing a password reset link) runs under one advisory lock (`ACCOUNTS_LOCK`, `administer` in `accounts.service.ts`), which decides that the last active Admin stays an active Admin and that the Admin making the change still is one. Deactivating an account (`deactivated_at`) locks its row, then deletes its sessions and withdraws its password reset link; redeeming a link locks the account's row first too, so the two run one at a time. A session starts under the account's row lock (`FOR SHARE`, `SessionsService.start`), refused if the password checked has since changed or the account was deactivated, so a sign-in racing a reset or a deactivation either is ended by it or is refused; a session is also refused on every request while its account is deactivated. Expired sessions are deleted in a statement of their own that skips locked rows, never inside a transaction holding other locks. Times that decide these links are read with `clock_timestamp()` (`databaseNow` in `accounts.service.ts`), and acceptance and redemption lock the link's row before reading it, so a link that expires while they wait for a concurrent change that then rolls back is refused. State-changing requests are refused as cross-site unless their `Origin` is `PUBLIC_URL`, or the requested host when that host is an IP address or `localhost` (not another domain name, which would admit DNS rebinding).

The plugin's WebSocket at `/sync` is outside the REST guards: it authenticates by the Machine token in `hello`. Tokens and session cookies are random secrets stored only as SHA-256 hashes (`server/src/secrets.ts`); a token is returned once, when it is issued (creating a machine entry, from a Pending Machine or not, or reissuing it, which revokes the old one). Do not assume one server instance: deployments run one for now, but the server must stay correct with several on one database. The connection that holds a Machine is stored on its row (`connected_session_id`, written when a hello is accepted, released when that connection closes or its instance shuts down, which first waits for hellos still being accepted); a Machine is online while that is set and it was heard from within three heartbeat intervals, so a crashed instance's Machines go offline by themselves. Last-seen times and session expiry are written and judged by PostgreSQL's `now()`, never an instance's clock; `server/test/session-expiry.test.ts` runs sessions on instances whose clocks are days off. A migration sets `idle_in_transaction_session_timeout` on the database (`server/prisma/migrations/20261006020933_idle_in_transaction_timeout`), so a transaction abandoned by a vanished host releases its row locks within 30 s; the server's connections send no settings at startup, which a pooler may refuse. Only the database's owner or a superuser may set it, so the server checks it on a new connection after migrating and warns while it is off (`checkIdleInTransactionTimeout` in `server/src/migrations.ts`). Each instance keeps only its own connections (`LiveConnections`). Accepting a hello, reissuing a token and dismissing hardware send a PostgreSQL `NOTIFY` (`AccessChanges`, ADR-0016) inside their transaction, delivered on commit; every instance then checks its connections to that Machine against the database (`MachinesService.standings`, read for all of them together: token still current, mismatched hardware not dismissed, still the connection holding the Machine) and closes those that fail. A new connection checks itself once registered, so a change committed while its hello was accepted is caught either there or by the notification; heartbeats check too, in the same query that records them (`MachinesService.heard`), and every connection is checked once the listener reconnects, covering notifications missed meanwhile. The server answers each heartbeat as it arrives, ahead of the database work queued for its connection, and the plugin drops a connection it has heard nothing on for three intervals (`MISSED_HEARTBEATS` in `protocol/`). A stalled database therefore closes no connection: until it recovers, the connection's heartbeat checks wait, and its Machine shows offline because its last-seen time cannot be written. A refused hello never writes `connected_session_id`, so it never replaces a connection. Whatever gives hardware to a Machine, holds it as a Pending Machine or dismisses it takes an advisory lock on that model and serial (`lockHardware`) before any Machine's row, so those run one at a time. `server/test/server-instances.test.ts` runs several instances on one database. Sign-in attempts are counted in `sign_in_windows` (`server/src/accounts/sign-in-limiter.ts`), one upsert per attempt with windows judged by PostgreSQL's `now()`, so every instance enforces one limit; `server/test/sign-in-limits.test.ts` runs it on two instances. Two limits are each instance's own, kept in its memory, because they protect only its CPU, memory and worker pool and decide nothing shared. Password checks with no session (sign-in, first-run setup, accepting an invite, using a password reset link) run at most 2 at once with 16 waiting, in turn; beyond that they are refused with 429 before any hash or sign-in limiter work (`PasswordChecks` in `server/src/accounts/password-checks.ts`, tested in `server/test/password-check-limits.test.ts`). A sign-in waits its turn before its attempt counts. Every `TooManyRequests` refusal carries its `Retry-After` (`RetryAfterFilter`). The sync gateway holds at most 64 connections whose hello has not been accepted and refuses upgrades beyond them with 503, logging that at most once a minute; connections that hold a Machine are not counted (`MAX_AWAITING_HELLO`, tested in `server/test/sync-connection-limits.test.ts`). A refused upgrade's socket (503, or 404 off `/sync`) is destroyed once its answer is sent, and its errors are handled: the HTTP server stops handling an upgraded socket's errors, so a client resetting it would otherwise crash the process.

Identity is decided once per connection at `hello` (`resolveIdentity` in `server/src/sync/identity.ts`) and stored on the Machine as its identification: identified, hardware not reported, unidentified or mismatch. Every `hello` also names its tablet (ticket #79), which the same transaction records against whoever the connection resolved to: the token's Machine, or for a mismatch the reported hardware's Machine or Pending Machine (`tablets.ts`, handed over by `transferPendingRecords`), numbered last under an advisory lock every hello takes and holds until it commits, so a Machine's latest connection's tablet is its highest-numbered; `AI_PROTOCOL_NOTES.md` has the contract. Beyond the spec's wording: a bound Machine reporting serial `"0"` is identified only from a known alias (so one identified by hand stays identified), an unbound Machine's `hello` without hardware is hardware not reported whatever its connection id, and a token reporting hardware another Machine has is a mismatch whose hardware belongs to that Machine, with no Pending Machine. Aliases are remembered only when a connection shows they are the Machine's (its own real hardware, or serial `"0"` on an unbound Machine) or when an Admin enters an Unidentified Machine's hardware. Dismissing a Pending Machine refuses its hardware for each Machine reporting that mismatch at dismissal (`DismissedHardware`). The refusal survives token rotation for those Machines; a later report using another Machine's token follows normal identity resolution.

Anything that decides a Machine's identity or tokens (`acceptHello`, token reissue, entering hardware by hand) runs in a transaction holding the Machine's row lock (`lockMachine` in `machines.service.ts`), so they are decided one at a time. Machine rows are locked `FOR NO KEY UPDATE`, which excludes other such locks but not the foreign-key checks of rows referencing the Machine: a Shot edit that writes its row twice checks that key again, and with `FOR UPDATE` it would deadlock with a Location History change waiting for that Shot. Take Machine rows before a Pending Machine's, as a hello does: dismissing locks the mismatched Machines (in id order) before it writes the Pending Machine, since the reverse order deadlocks with a reconnecting tablet. Any new way of revoking access must notify the same way, inside its transaction.

A Machine's Location History is a list of entries (`location_assignments`), each naming a Location and the time the Machine arrived there; an entry lasts until the next one, and before the first the Machine's Location is unknown. A machine entry created with a Location starts its history then, by PostgreSQL's clock, so a tablet's backfilled history keeps an unknown Location until an Admin moves that first entry earlier. A move must come after the latest entry, and neither a move nor a corrected time may be in the future. A correction may change an entry's Location, its time or both: its time stays between the entries before and after it, and its Location differs from theirs. Removing an entry recorded by mistake leaves the Machine where the entry before it says; when the entry after it names that same Location, the Machine never left, so that entry is removed too. Each Shot's and Steam Record's Location is stored (`location_id`) and derived from its Machine's history at its pulled-at or steamed-at time (`creditLocations`, `creditShotLocation` and `creditSteamRecordLocation` in `location-history.ts`); a Pending Machine's records have none until a Machine takes them over. Storing a record's credit and changing a Machine's history both hold the Machine's row lock (`lockMachine`); a Shot's pulled-at time is set once, by the first full record, which also credits it, and only adoption changes that credit afterwards, under the hardware's and the Machine's locks. A change credits again only the Machine's records recorded in the span it affects (`creditLocations` takes that span): from a move's time on; for a corrected time, from the earlier of the old and new times to the later, or to the next entry when the Location changes too; for a corrected Location, from the entry to the next one; for a removal, from the removed entry to the next one that remains. Outside its span, the history names the same Location for every time as before. A record stored during a change, on any instance, is credited by the changed history because both hold the row lock: it is stored either before the change, which then credits it again if it is in its span, or after it. Adoption credits only the records it hands over (`handOverRecords`), as the Machine's own history has not changed. Changing a history and adopting hardware, including in a binding hello, run with `CREDITING_TRANSACTION`'s limits (60 s rather than Prisma's default 5 s): on 250,000 Shots and 250,000 Steam Records for one Machine, a change crediting them all took up to 15 s on the development database, and a hello handing as many over 13 s, while that Machine's deliveries waited and may have failed and been resent. A binding hello may outlast the plugin's 15 s wait for `welcome`; it still commits, and the plugin's next hello finds the hardware bound. A Location credited through an inferred Machine is reported as inferred (`locationInferred`); it is not stored. Steam Records are stored once and credited once, when first stored, so only history changes and adoption change their Location; they carry no inferred marker (ADR-0015).

A tablet's library, settings and paired devices are collections (`reported_collections`), the latest value of each per Machine, credited, handed over and handled once by delivery id as Workflow events are; an unavailable report (no machine or scale connected, a DYE2 key never written, a failed read) keeps the value known. `docs/COLLECTIONS.md` has the contract.

A delivery of a Shot, Shot edit, Steam Record, Workflow, machine state or collection whose storage fails in a way that would repeat (PostgreSQL's class 22, 23514 or 54000, such as a NUL in a string) is set aside in `set_aside_deliveries` for its token's Machine, its message kept as received, once per delivery id by an insert that skips a conflict, and acknowledged as stored, so it cannot hold up the tablet's outbox; any other failure still closes the connection with 1011. Indexes from that Machine leave out a Shot or Steam Record set aside. `docs/AI_PROTOCOL_NOTES.md` (Deliveries set aside) has the contract, and `server/test/set-aside-deliveries.test.ts` covers it through Seam 1.

Workflow changes and machine state transitions (`workflow_events`, `machine_state_events`) are credited as inferred Shots are, to the token's Machine or for a mismatch to its reported hardware's Machine or Pending Machine (`creditReporter` in `credit.ts`, as Steam Records are), and every way a Machine takes over hardware hands them over with its Shots and Steam Records (`transferPendingRecords`). Each delivery is handled once: its id is recorded for its token's Machine (`machine_event_deliveries`) whether or not it changes anything, and a delivery already recorded changes nothing. Otherwise the event is inserted only if it differs from the latest event stored for whoever it belongs to, in one statement while that Machine's row lock or the hardware's lock is held, so the decision never depends on what an instance remembers. Ids are kept for 90 days by PostgreSQL's clock: every instance deletes older ones as it starts and hourly (`DeliveryIdCleanup` in `src/machines/delivery-id-cleanup.ts`), in bounded batches that skip locked rows, as expired sessions are deleted. The latest stored (highest `id`) is the current Workflow or machine state; `observed_at` is the tablet's clock and `received_at` PostgreSQL's. `docs/WORKFLOW-AND-STATE.md` has the contract.

A Location's time zone is an IANA name spelled as PostgreSQL's `pg_timezone_names` lists it, so date filters can use it in `AT TIME ZONE`: Shot and Steam Record date filters compare each record's time on its own Location's clock, or UTC without one (`server/src/record-filters.ts`, `docs/SHOTS.md`). PostgreSQL built without tzdata's backward links lacks aliases such as `US/Eastern` and the older CLDR names browsers report (such as `Asia/Calcutta`); `server/src/locations/time-zones.ts` resolves those through `Intl` to a zone PostgreSQL knows.

## Data

Shot storage and reconciliation are described in `docs/SHOTS.md`, and Steam
Records in `docs/STEAM_RECORDS.md`. The built plugin keeps one in-memory
`Outbox` beside `SyncConnection`: `ShotCapture` captures shot events and scans
bounded summary pages once per load, `SteamCapture` polls Steam Record ids and
indexes them on every welcome, `MachineEvents` sends Workflow changes and
machine state transitions, `CollectionCapture` polls the library, settings and
paired devices and sends each whole on every welcome, and the outbox replays
what is unacknowledged on reconnect. `ShotsService` stores early edits durably, compares versions under
a PostgreSQL advisory lock, and separates metadata from compressed curves;
`SteamRecordsService` stores each Steam Record once, the same way separated.
All hardware adoption paths transfer Pending Shot, Steam Record, event and
collection credit before deleting the Pending Machine (`transferPendingRecords`), and credit
those records' Locations by the adopting Machine's Location History.
`server/test/shots.test.ts` and `server/test/steam-records.test.ts` cover this
through Seam 1 and two instances on one database, and
`server/test/location-history.test.ts` covers Locations the same way.
