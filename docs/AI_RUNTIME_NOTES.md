# AI Runtime Notes

Read before implementing the plugin or its simulated host. This note keeps the host constraints needed by milestone 1 in this repo; the archived plugin is prior art, not a required documentation dependency.

References use the checkout convention in `AGENTS.md`. Audited against local Decaid commit `a45961b3` on 2026-10-03; the `fetch` discrepancy and the record shapes below were also checked at v0.8.6 and v0.8.7 (no changes under `lib/src/plugins` or `lib/src/models/data` between them). Check the oldest supported release and the version under investigation before relying on additional host behavior.

## Loading and settings

The plugin supports the Decaid versions ADR-0017 names (before v1, v0.8.7 or newer) and declares `log`, `api`, `events.machine`, `events.shots`, `events.workflow` and `network.websocket`, as specified in issue #1, and `pluginStorage`, for the tablet's id (ticket #79). Unknown permissions can prevent loading; check `decaid:lib/src/plugins/plugin_manifest.dart` before adding one. Decaid installs a plugin update by itself only when the update adds no permission: one that does waits as the source's `pendingUpdate` until someone approves it on that tablet, in Settings, Plugins (**Review**, then **Approve and update**) or with `POST /api/v1/plugins/{id}/update/approve` (`decaid:lib/src/plugins/plugin_source_service.dart`, `_updatePlugin` and `approvePendingUpdate`). Say so in `UPGRADING.md` for any release that adds one.

## Plugin storage

With `pluginStorage`, `host.storage(command)` sends a `{ type: "read", key }` or `{ type: "write", key, data }` command to Decaid and returns nothing. Decaid answers a read with a `storageRead` event of `{ key, value }`, `value` null for a key never written, and a write with a `storageWrite` event whose payload is only the data written, not its key (`_handlePluginStorage` in `decaid:lib/src/plugins/plugin_manager.dart`, unchanged in v0.8.8). A command that fails is logged by Decaid and never answered, so a plugin waits for each with a timeout. Commands travel as JSON, values are kept in a Hive box named after the plugin's id, and a write the plugin sends while it unloads still lands: Decaid finishes a retiring generation's writes before the next generation loads. Without the permission, `host.storage` throws a `PluginPermissionError`. The same Hive box is what `GET /api/v1/store/{plugin id}/{key}` reads.

Decaid's backup (`GET /api/v1/data/export`, and the app's own backup) holds a plugin's storage only once the store API has opened it since Decaid started: `KvStoreExportSection` lists the `namespaces` of the store behind `KvStoreHandler`, which knows only the boxes it has opened itself, and `host.storage` opens them through the plugin loader's own store (`decaid:lib/src/services/storage/hive_store_service.dart`, the same in v0.8.7, v0.8.8 and `main` on 2026-10-07). On Decaid v0.8.7's Linux release, a backup left out `decent-sync.reaplugin` until `GET /api/v1/store/decent-sync.reaplugin/tabletId` had been answered, and left it out again after Decaid restarted. So the plugin reads its storage through the store API once it knows the tablet's id (`keepStorageInBackups` in `plugin/src/decaid.ts`), asking again every 30 s until it is answered; a backup taken after that holds the id. Restoring a backup (`POST /api/v1/data/import`) keeps a key the tablet already has unless asked to overwrite: Decaid's onboarding restores with `onConflict=skip`, before any plugin is installed, and Settings, Data Management asks whether to skip or overwrite existing data. Backups do not hold installed plugins.

Decaid calls the global `createPlugin(host)` entry point and calls `plugin.onLoad(settings)` synchronously without awaiting a returned promise (`decaid:lib/src/plugins/plugin_manager.dart`). Keep `onLoad` short and schedule connection work through a timer. The loader has a load watchdog; inspect `decaid:lib/src/plugins/plugin_loader_service.dart` when changing startup behavior.

The target build is one ES2020 `plugin.js` with no module syntax. Decaid pastes it into a function body and then checks `typeof createPlugin`, so `createPlugin` must be declared at the top level of the script: `plugin/build.mjs` bundles an esbuild IIFE and assigns `var createPlugin` after it. The plugin's `id` must equal the manifest's. Use the host APIs and timer callbacks; do not assume a browser or Node environment. Run the built file in the simulated host, not just the TypeScript source.

The manifest (v0.8.7, `PluginManifest.fromJson`) has no field for a minimum Decaid version, and unknown keys are ignored. The server enforces the minimum instead: the plugin sends Decaid's `fullVersion` from `GET /info` (the tag it was built from plus a build number, from `flutter_with_commit.sh`) in every `hello`, and does not connect until it can read it. The server refuses an older or unreadable version with `decaid_too_old` (ADR-0017).

Secure settings are supplied to the loaded plugin, while the settings REST response reports whether they are set rather than exposing their values (`PluginLoaderService.pluginSettings`). The token must be declared secure. Settings changes can reload the plugin, so startup and unload must tolerate a new runtime generation.

## CPU time

Plugin JavaScript runs on Decaid's main isolate: `PluginLoaderService` is created in `decaid:lib/main.dart`, nothing in `lib/src/plugins` starts another isolate, and on Android flutter_js runs QuickJS synchronously. A long stretch of plugin work therefore holds up Decaid itself, its interface included. QuickJS interprets JavaScript and regular expressions, so costs differ from Node's. On 5 MiB of a Shot's JSON, on an Apple M5 with QuickJS 2025-04-26 (2026-10-05), `JSON.parse` and `JSON.stringify` of the Shot took 40 to 60 ms each, a `charCodeAt` loop over it about 140 ms, and a sticky regular expression matching its runs of ASCII about 15 ms. Each match costs as much as dozens of steps of a loop, though, so matching run by run is slow where runs are short: counting the UTF-8 bytes of 5 MiB of text alternating between ASCII and Japanese that way took 2.7 s. `utf8Length()` (`protocol/src/chunking.ts`) therefore matches only long runs of ASCII and steps through the rest. Chunking (`frames()`) took 35 ms for a 5 MiB Shot, 40 ms for one with 2 MB of Japanese notes, about 230 ms for 5 MiB of accented prose, and about 280 ms at worst, for text whose runs of ASCII are each exactly `ASCII_STEPS` (32) characters long. A tablet's CPU is several times slower. To measure, bundle the code with esbuild as an ES2020 IIFE and run it with `qjs` from Alpine's `quickjs` package in Docker.

## Server transport

Inspect `decaid:lib/src/plugins/plugin_transport_service.dart`, especially `_openWebSocket`, `send` and `_reserveOutbound`:

- `host.transport` opens `ws://` or `wss://` connections with `network.websocket`. The WebSocket open options support URL and subprotocols, not custom headers. Authenticate in the protocol handshake.
- `send` acceptance is not a server acknowledgment. Keep delivery state until the server acknowledges the stored logical message.
- A plugin generation may hold 8 transports, counting opens still in progress. `open()` has no timeout and cannot be cancelled: an upgrade the server never answers holds its slot until TCP gives up, possibly never. The plugin abandons an attempt after its connect deadline and counts its own transports so it never asks for a ninth (`plugin/src/connection.ts`); eight hung opens stop it reconnecting until it is reloaded.
- Default pending outbound and queued inbound limits are each 1 MiB per transport. The outbound check covers both a single payload and the sum already pending; sends exceeding it fail with `transport_resource_limit`.
- `send` resolving says only that the frame was queued, and nothing tells the plugin when it has been written, so frames just below 1 MiB would not do: several pending at once still pass the limit. The plugin sends frames of at most 256 KiB, measured in UTF-8 with their envelope and escaping, and counts what it has sent until the server confirms it, keeping at most 512 KiB unconfirmed (`plugin/src/sender.ts`; see `AI_PROTOCOL_NOTES.md`). The simulated host enforces the pending-byte limit, writes frames in order and can slow the writing, so tests exercise this.
- Unloading retires the plugin's transports. Milestone 1's in-memory outbox cannot preserve every transient event across an unload; record history is recovered by backfill. A durable outbox belongs to milestone 2.

## Local API and events

Use plugin-scoped `fetch` for Decaid's local API. `PluginManager._performFetch` has response-size (`maxFetchResponseBytes`, 10 MiB by default) and timeout (30 s) constraints; it does not provide a streaming response to JavaScript. Never rely on fetching an unbounded list in one response.

ADR-0009's original rationale and the original Further Notes in issue #1 stated that private-IP fetch is blocked; both have been clarified. **Source discrepancy:** `_performFetch` at v0.8.6, v0.8.7 and `a45961b3` passes the URL to `HttpClient.openUrl` without a private-address check. Treat documented restrictions as host policy, not proof of enforcement. The agreed architecture still uses WebSocket for all server traffic.

Steam Records have no `updatedAt`, nothing in Decaid, Streamline or DYE2 edits them, and `GET /steams` returns every record (each with its full Workflow and profile) in one unpaginated response that outgrows the fetch limit at cafe volume. Milestone 1 therefore captures new Steam Records and backfill only, not edits. A Steam Record's `timestamp` is the tablet's local time without an offset, and nothing on it is in UTC, so the plugin places it in the runtime's local time zone (`STEAM_RECORDS.md`). QuickJS on Linux follows the process's `TZ` (checked in Decaid v0.8.7's Linux release); whether QuickJS on Android reads local time in the tablet's zone is unverified. Each Steam Record after the first in a run of Decaid starts with the previous record's last milk temperature, replayed by `BengleMilkProbe` (`decaid:lib/src/models/device/impl/bengle/bengle_milk_probe.dart`) to the subscription `SteamSequencer` opens for each record. Every supported Decaid serves Shots with `updatedAt`, in UTC, which changes only when their content does; order Shot versions by `updatedAt` alone, and ignore a Shot without it (ADR-0017). Check optional fields in real records from supported versions; absence of an endpoint means unavailable data, not an empty collection.

## Identity and attribution

`preferredMachineId` is a connection identifier, not the hardware identity. Inspect `decaid:lib/src/services/webserver/settings_handler.dart` and the relevant machine implementation for Bluetooth/USB behavior. Use model and serial per ADR-0004 and ADR-0015; serial `"0"` is not a real identity. `GET /machine/info` fails while no machine is connected, so the plugin may have to send `hello` without hardware and send a new one once the machine reports it. Decaid sends `stateUpdate` only while a machine is attached (`PluginManager._replaceSnapshotSubscription`), which the plugin takes as its cue to read `/machine/info` again.

Shots and Steam Records include a Workflow; inspect `decaid:lib/src/models/data/shot_record.dart`, `steam_record.dart` and `workflow.dart` for capture-time identity. Only Shots carry it: `de1_state_manager` stamps `workflow.machine` (with `provenanceStatus` `captured` or `unavailable`) when a shot starts, and only since v0.7.6. Older Shots lack it; Decaid's imports from the legacy Tcl app (`de1app-*`) are not captured at all. Steam Records never carry it, because the steam sequencer stores the current Workflow. Apply ADR-0015's crediting rules instead of attributing every record to whichever tablet sent it.
