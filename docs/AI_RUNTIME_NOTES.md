## Loading and settings

The plugin supports the Decaid versions ADR-0017 names (v0.9.3 or newer) and declares `log`, `api`, `events.machine`, `events.shots`, `events.workflow` and `network.websocket`, as specified in issue #1, `pluginStorage`, for the tablet's id (ticket #79), `emit`, to tell skins it changed DYE2's recipes (ticket #168, Skins below), `manage.extensions`, for Software Actions (ticket #660, ADR-0034), and `notifications`, for its one notice on the tablet saying why it stopped syncing (ticket #540, `plugin/src/tablet-notice.ts`), added in the same release so that each tablet approves one update for both. Unknown permissions can prevent loading; check `decaid:lib/src/plugins/plugin_manifest.dart` before adding one. Decaid installs a plugin update by itself only when the update adds no permission: one that does waits as the source's `pendingUpdate` until someone approves it on that tablet, in Settings, Plugins (**Review**, then **Approve and update**) or with `POST /api/v1/plugins/{id}/update/approve`, which needs a token while "Require authorization for extension management" is on (always on v0.9.2; Local API and events, below; `decaid:lib/src/plugins/plugin_source_service.dart`, `_updatePlugin` and `approvePendingUpdate`), or through a Software Action approving the plugin's own update, which only a plugin that already takes Software Actions carries out, so the release that added `manage.extensions` could not be approved that way. Say so in `UPGRADING.md` for any release that adds one.

Decaid shows no warning on the tablet for a plugin installed through its API, `host.localApi` included, even one asking for `manage.extensions` (read in v0.9.3's source for #657). Holding that permission, the plugin can install any plugin and approve any update's permissions, its own included, so an Admin's account, or the server, can put code on every connected tablet (ADR-0034).

## Plugin storage

With `pluginStorage`, `host.storage(command)` sends a `{ type: "read", key }` or `{ type: "write", key, data }` command to Decaid and returns nothing. Decaid answers a read with a `storageRead` event of `{ key, value }`, `value` null for a key never written, and a write with a `storageWrite` event whose payload is only the data written, not its key (`_handlePluginStorage` in `decaid:lib/src/plugins/plugin_manager.dart`, unchanged in v0.8.8 and v0.9.0). A command that fails is logged by Decaid and never answered, so a plugin waits for each with a timeout. Commands travel as JSON, values are kept in a Hive box named after the plugin's id, and a write the plugin sends while it unloads still lands: Decaid finishes a retiring generation's writes before the next generation loads. Decaid's `HiveStoreService.set` takes no null, so a write of null fails and `host.storage` can delete no key (Decaid's store API can, with `DELETE /api/v1/store/{plugin id}/{key}`, which the plugin does not use), and Hive opens a box whole into memory (`decaid:lib/src/services/storage/hive_store_service.dart`, the same in v0.8.7, v0.8.8 and v0.9.0): what the plugin keeps there must be bounded, as the outbox's kept deliveries are, in a fixed ring of keys, and its Reference Shot copies, in a key for each of the nine Recipe Slots (`plugin/src/reference-copies.ts`, ticket #510). `_handlePluginStorage` puts no limit on a value's size (read at v0.9.1 and v0.9.2, 2026-11-14); the largest value Decaid's store takes through its own API is 1 MiB, the body `POST /api/v1/store/{namespace}/{key}` reads (`largeRequestBodyBytes` in `decaid:lib/src/services/webserver/bounded_request_body.dart`, read through `readBoundedRequestBodyString` in `kv_store_handler.dart`, which answers 413 past it), so no copy larger than that is kept (`MAX_REFERENCE_COPY_BYTES` in `protocol/`). The plugin sends its commands one at a time (`plugin/src/storage.ts`), matching a read's answer by its key and a write's by the string written, since its answer carries no key; once Decaid leaves a write unanswered, it sends writes without waiting until Decaid answers anything again, and as it unloads it sends the writes still queued, the one awaiting an answer again first. Without the permission, `host.storage` throws a `PluginPermissionError`. The same Hive box is what `GET /api/v1/store/{plugin id}/{key}` reads.

Decaid's backup (`GET /api/v1/data/export`, and the app's own backup) holds a plugin's storage only once the store API has opened it since Decaid started: `KvStoreExportSection` lists the `namespaces` of the store behind `KvStoreHandler`, which knows only the boxes it has opened itself, and `host.storage` opens them through the plugin loader's own store (`decaid:lib/src/services/storage/hive_store_service.dart`, the same in v0.8.7, v0.8.8, `main` on 2026-10-07 and v0.9.0). On Decaid v0.8.7's Linux release, a backup left out `decent-sync.reaplugin` until `GET /api/v1/store/decent-sync.reaplugin/tabletId` had been answered, and left it out again after Decaid restarted. So the plugin reads its storage through the store API once it knows the tablet's id (`keepStorageInBackups` in `plugin/src/decaid.ts`), asking again every 30 s until it is answered; a backup taken after that holds the id. Restoring a backup (`POST /api/v1/data/import`) keeps a key the tablet already has unless asked to overwrite: Decaid's onboarding restores with `onConflict=skip`, before any plugin is installed, and Settings, Data Management asks whether to skip or overwrite existing data. Backups do not hold installed plugins.

Decaid calls the global `createPlugin(host)` entry point and calls `plugin.onLoad(settings)` synchronously without awaiting a returned promise (`decaid:lib/src/plugins/plugin_manager.dart`). Keep `onLoad` short and schedule connection work through a timer. The loader has a load watchdog; inspect `decaid:lib/src/plugins/plugin_loader_service.dart` when changing startup behavior.

The target build is one ES2020 `plugin.js` with no module syntax. Decaid pastes it into a function body and then checks `typeof createPlugin`, so `createPlugin` must be declared at the top level of the script: `plugin/build.mjs` bundles an esbuild IIFE and assigns `var createPlugin` after it. The plugin's `id` must equal the manifest's. Use the host APIs and timer callbacks; do not assume a browser or Node environment. Run the built file in the simulated host, not just the TypeScript source.

The manifest (v0.8.7 to v0.9.2, `PluginManifest.fromJson`) has no field for a minimum Decaid version, and unknown keys are ignored. The server enforces the minimum instead: the plugin sends Decaid's `fullVersion` from `GET /info` (the tag it was built from plus a build number, from `flutter_with_commit.sh`) in every `hello`, and does not connect until it can read it. The server refuses an older or unreadable version with `decaid_too_old` (ADR-0017).

Secure settings are supplied to the loaded plugin, while the settings REST response reports whether they are set rather than exposing their values (`PluginLoaderService.pluginSettings`). The token must be declared secure. Settings changes can reload the plugin, so startup and unload must tolerate a new runtime generation.

## CPU time

Plugin JavaScript runs on Decaid's main isolate: `PluginLoaderService` is created in `decaid:lib/main.dart`, nothing in `lib/src/plugins` starts another isolate, and on Android flutter_js runs QuickJS synchronously. A long stretch of plugin work therefore holds up Decaid itself, its interface included. QuickJS interprets JavaScript and regular expressions, so costs differ from Node's. On 5 MiB of a Shot's JSON, on an Apple M5 with QuickJS 2025-04-26 (2026-10-05), `JSON.parse` and `JSON.stringify` of the Shot took 40 to 60 ms each, a `charCodeAt` loop over it about 140 ms, and a sticky regular expression matching its runs of ASCII about 15 ms. Each match costs as much as dozens of steps of a loop, though, so matching run by run is slow where runs are short: counting the UTF-8 bytes of 5 MiB of text alternating between ASCII and Japanese that way took 2.7 s. `utf8Length()` (`protocol/src/chunking.ts`) therefore matches only long runs of ASCII and steps through the rest. Chunking (`frames()`) took 35 ms for a 5 MiB Shot, 40 ms for one with 2 MB of Japanese notes, about 230 ms for 5 MiB of accented prose, and about 280 ms at worst, for text whose runs of ASCII are each exactly `ASCII_STEPS` (32) characters long. A tablet's CPU is several times slower. To measure, bundle the code with esbuild as an ES2020 IIFE and run it with `qjs` from Alpine's `quickjs` package in Docker.

## Server transport

Inspect `decaid:lib/src/plugins/plugin_transport_service.dart`, especially `_openWebSocket`, `send` and `_reserveOutbound`:

- `host.transport` opens `ws://` or `wss://` connections with `network.websocket`. The WebSocket open options support URL and subprotocols, not custom headers. Authenticate in the protocol handshake.
- `send` acceptance is not a server acknowledgment. Keep delivery state until the server acknowledges the stored logical message.
- A plugin generation may hold 8 transports, counting opens still in progress. `open()` has no timeout and cannot be cancelled: an upgrade the server never answers holds its slot until TCP gives up, possibly never. The plugin abandons an attempt after its connect deadline and counts its own transports so it never asks for a ninth (`plugin/src/connection.ts`); eight hung opens stop it reconnecting until it is reloaded.
- Sockets on Decaid itself count against the same 8: DYE2's `changed` socket and the Live View's (Local API and events, below). The plugin opens one only while that leaves a transport free for a connection to the server, counting the slots earlier connection attempts still hold, so they never stop it reconnecting (`Transports` in `plugin/src/host.ts`). A Live View socket that can't open for want of a slot, or that closes, is tried again 5 s later while streaming, and so is the search for a milk probe that finds none. They share the slots with DYE2's: while earlier attempts hold slots, the Live View's may take the one DYE2's socket would open again into, after DYE2 reloads, until a viewer leaves or the attempts end; the plugin's poll of DYE2's lists makes up for the pushes missed. A steady connection holds at most seven: its connection to the server, DYE2's socket and five of the Live View's, the fifth a Bengle's milk probe's while one is attached (ADR-0024).
- Default pending outbound and queued inbound limits are each 1 MiB per transport. The outbound check covers both a single payload and the sum already pending; sends exceeding it fail with `transport_resource_limit`.
- `send` resolving says only that the frame was queued, and nothing tells the plugin when it has been written, so frames just below 1 MiB would not do: several pending at once still pass the limit. The plugin sends frames of at most 256 KiB, measured in UTF-8 with their envelope and escaping, and counts what it has sent until the server confirms it, keeping at most 512 KiB unconfirmed (`plugin/src/sender.ts`; see `AI_PROTOCOL_NOTES.md`). The Live View's frames, outside that count, have 64 KiB of their own (`AI_PROTOCOL_NOTES.md`, Live frames). The simulated host enforces the pending-byte limit, writes frames in order and can slow the writing, so tests exercise this.
- The inbound limit counts the frames Decaid holds for the plugin: `_enqueue` closes the transport, with `transport_resource_limit`, on a frame that would take them past 1 MiB, and so on any one frame larger than that. Read at v0.9.1 and v0.9.2 (2026-11-14, ticket #508): once the plugin has registered its listener (`onEventRegistered`), which it does before its `hello`, `_drain` hands each frame to the plugin's JavaScript as it arrives, in the same call (`_dispatchTransportEvent` in `decaid:lib/src/plugins/plugin_manager.dart`), so Decaid holds a frame only before that; while the plugin's JavaScript runs, on Decaid's main isolate (CPU time, above), later frames stay unread in the socket, which the limit doesn't count. The server keeps to the limit as Decaid declares it, not to that: it sends frames of at most 256 KiB, and counts its writes and answers until the plugin confirms them, keeping at most 768 KiB unconfirmed, 512 KiB of chunks and 256 KiB of small messages sent whole (`server/src/sync/sender.ts`; `AI_PROTOCOL_NOTES.md`, Chunked messages). The simulated host gives the plugin one frame in each later turn of its event loop, so frames that arrive together count against its limit, and a write sent all at once past 1 MiB closes its transport.
- Unloading retires the plugin's transports. The outbox keeps its Workflow and machine state deliveries in plugin storage until acknowledged, and sends them first after a reload (ticket #93, `WORKFLOW-AND-STATE.md`, Kept across unloads); everything else it holds is in memory, and the record history it held is recovered by backfill.

## Local API and events

Use plugin-scoped `fetch` for Decaid's local API. It sends a request's method, headers and body as given (`init.method`, `init.headers`, and `init.body`, a string sent as its UTF-8), so the plugin writes through it too. `PluginManager._performFetch` has response-size (`maxFetchResponseBytes`, 10 MiB by default) and timeout (30 s) constraints; it does not provide a streaming response to JavaScript. Never rely on fetching an unbounded list in one response.

ADR-0009's original rationale and the original Further Notes in issue #1 stated that private-IP fetch is blocked; both have been clarified. **Source discrepancy:** `_performFetch` at v0.8.6, v0.8.7, v0.9.0 and `a45961b3` passes the URL to `HttpClient.openUrl` without a private-address check. Treat documented restrictions as host policy, not proof of enforcement. The agreed architecture still uses WebSocket for all server traffic.

On v0.9.2 the routes that manage plugins and Skins take a request only with a bearer token scoped `extensions:manage`, answering 401 to one with no token or one Decaid does not know, and 403 to a token it knows that lacks the scope (`extensionManagementRoutes` in `decaid:lib/src/services/webserver/extension_management_auth.dart`): those that install, update, enable, disable or remove one, approve a plugin's update, save a plugin's settings, choose the default Skin, or start and stop the Skin server. `POST /api/v1/settings` refuses the same way, applying no key, a body that turns `automaticUpdateCheck` on while it is off, changes `defaultSkinId` or holds `webUiPath` (`SettingsHandler`). The plugin's `fetch` carries no token, so it makes none of these through `fetch`: it manages plugins, and writes the automatic update checks, through `host.localApi` (below), which needs none. What the plugin reads is untouched, `GET /plugins`, `/webui/skins`, `/webui/skins/default` and `/webui/server/status`, and so are plugins' own endpoints, DYE2's `record` among them, and Decaid's own update check and Plugins screen. Decaid takes a token it knows off a request before a plugin's endpoint sees it. `server/test/fixtures/decaid/simulated-devices-v0.9.2/` holds its answers.

v0.9.3 asks the same token, on the same routes and the same `POST /api/v1/settings` bodies, only while Settings → Security → "Require authorization for extension management" is on (`decaid:lib/src/services/webserver/extension_management_auth.dart`, `decaid:lib/src/settings/security_page.dart`; `decaid:doc/Api.md`, Extension management authorization). It is off on a new install and after an update from v0.9.2, whatever tokens the Tablet holds; off, those routes take any request that reaches the Tablet, as before v0.9.2, and ignore an `Authorization` header. `host.localApi` with `manage.extensions` works either way.

v0.9.3's switch is changed only in Decaid on the Tablet: `GET /api/v1/settings` does not report it, and `POST /api/v1/settings`, a backup import and a sync neither set nor carry it. So nothing the plugin reads reports which way a Tablet is set, and it can be turned on at any time: a guarded route answering 401 would show it on only at that moment.

In both modes v0.9.3 refuses with 403 a browser page managing plugins and Skins whose `Origin` is not the Tablet's own numeric address or `localhost` (`decaid:doc/Api.md`, Browser origins). A request with no `Origin`, as the plugin's `fetch` and `curl` send, is not checked.

What v0.9.3 does, run on its Linux release headless on 2026-11-23 for ticket #660 (`server/test/fixtures/decaid/tablet-software-v0.9.3/`, recorded by its `record.mjs` with a probe plugin; `server/test/support/decaid-plugins.ts` simulates it from them):

- `host.localApi(path, { method, body, contentType })` takes the whole path from `/api/v1/`, and resolves `{ status, headers, body }`, the body as text, for any HTTP status (`PluginLocalApiBridge` in `decaid:lib/src/plugins/plugin_local_api_bridge.dart`).
- It rejects, with `Invalid argument(s): ...`, a path not under `/api/v1/`, a method other than GET, POST, PUT or DELETE, a route off its allowlist ("localApi reaches only the plugin and skin management routes, not GET /api/v1/settings"), and a settings body with any key but `defaultSkinId` and `automaticUpdateCheck` ("localApi changes only these settings: defaultSkinId, automaticUpdateCheck"); and with `PluginPermissionError` for a plugin without `manage.extensions`.
- Out of its reach are `GET /api/v1/update`, the reads of `/api/v1/settings` and the machine routes: the plugin reads them with `fetch`, and reaches Decaid's update socket through `host.transport`.
- With "Require authorization for extension management" on, a plain request, the plugin's `fetch` or another app's, to a plugin route that manages answers 401 `{"error":"Missing or malformed bearer token"}`, and so does a `POST /settings` turning `automaticUpdateCheck` on while it is off; the reads, `GET /plugins`, `GET /plugins/{id}/settings` and `GET /update`, need none; `host.localApi` is taken either way (`protected.json`).
- A `host.localApi` call under way as Decaid unloads the plugin, to save its own settings or disable it, is never answered to the plugin: Decaid answered the probe plugin's own HTTP caller 500 `{"error":"plugin unloaded"}`, and saved the settings all the same (`ownSettingsSaved`).
- `GET /plugins/{id}/settings` answers the settings that were set, without defaults, a `secure` one only as `{ "isSet": bool }`, and `{}` for a plugin it does not know.
- `POST /plugins/{id}/settings` merges, `null` clearing a setting; an undeclared name refuses the whole body with 400 (`Setting "x" not defined in plugin manifest`); a number sent as text is put back to its default, with 200; and a plugin it does not know answers shelf's plain 500, `Internal Server Error`.
- `POST /plugins/update` answers 200 with `results`, one for each plugin it updates, those with a `github_release` or `github_branch` source: `updated`, `alreadyCurrent`, `pendingApproval` or `failed`. A plugin Decaid bundles is listed with `source: null` until its first update check, which records its repository as a `github_release` source.
- An update that adds a permission waits: `pendingApproval`, and the list entry's `pendingUpdate`, `{ version, releaseTag, addedPermissions, detectedAt }`, answered so again at each check. `POST /plugins/{id}/update/approve` installs it, answering 200 `{ message, id, version, loaded }`, and answers 409 where none waits.
- `POST /plugins/install/github-release {repo}` and `install/github-branch {repo, branch}` answer 200 `{ message, id, version, loaded }`, a new plugin `loaded: false`. A branch install of a commit records it as both `branch` and `commit`. Errors are 400 (`repo is required (owner/repo)`, `Plugin package has no manifest.json`) or 500 with Decaid's sentence, for no such repository, release or branch. There is no install by release tag (decentespresso/decaid#1030).
- `DELETE /plugins/{id}` removes a plugin with its settings; one Decaid bundles is back after Decaid restarts, as dcamp was.
- `GET /update` answers `{ phase, currentVersion, latestVersion, releaseNotes, releaseUrl, installable, progress, error }`. `/ws/v1/update` sends that state as it opens and on each change, takes `{"command":"check"}` (phase `checking`, then the result), and answers a command it can't carry out with `{ error, url }`, as `install` on Linux: "In-app install is not supported on this platform".
- Decaid follows a change of `automaticUpdateCheck` made over its API only when it next starts (read in its source for #657).

What v0.9.3 does with a plugin's notices, run on its Linux release headless on 2026-11-23 for ticket #540 (`server/test/fixtures/decaid/notices-v0.9.3/`, recorded by its `record.mjs` with a probe plugin; `server/test/support/decaid-notices.ts` follows it):

- `host.notify({ id, message })` returns a request id (`notice_1`, ...) at once; a `notificationResult` event follows to that load only, `{ requestId, id, status: "accepted" }` or `{ requestId, id?, status: "rejected", reason }`, `id` left out where it was not valid.
- An id or message that is not a string, is blank, is longer than 128 or 600 UTF-16 code units, or holds a control character other than tab and line feed is rejected as `validation`. A plugin's sixth notice, of a new id, is rejected as `capacity`; replacing one of its five is not.
- A notice with the id of one the plugin holds replaces it in place: the same message keeps its revision and read state, another is a new revision, unread. `host.dismissNotification(id)` withdraws one, and with no id every notice of the plugin; an id it does not hold changes nothing and saves nothing. Neither answers, so a withdrawal whose save fails leaves the notice up without a word (from `removeSource` in notification_center.dart, not recorded); the plugin asks again at each heartbeat.
- Saving a plugin's settings, which reloads it, and restarting Decaid keep its notices; disabling it removes them. No REST route lists notices: the center is saved in `shared_preferences.json` as `flutter.private.notificationCenter.v1`.

Its `dye.applyRecipe` and `dye.applyFavourite` writers own `context.extras.feedRate` from then, so a recipe holding a feed rate applies, where v0.2.24 threw before its PUT (`assertDeclaredFields`). A skin built for a Decent Sync deployment needs no clearing of its own: the plugin's load write clears what the recipe names none of (ADR-0022).
- **It offers a reload once a newer build is on the tablet** (v0.2.26, `3922003`). `checkSkinUpdate` in `src/modules/app.js` compares the build Decaid holds with the one loaded, 30 s after it starts and every 12 h, and shows a notice to tap. Nothing of Decent Sync's takes part.
- **It follows Decaid's theme** (v0.2.27, `73539b1`). `followDecaidTheme` in `src/modules/ui.js` takes Decaid's `themeMode` wherever a barista never used Streamline's own toggle, so the Theme Tablet Setting (ADR-0023) changes Streamline's look, as it next loads.
- **A recipe's apply writes every steam, hot water and flush setting it holds** (v0.2.29, decentespresso/streamline-js#154). `mergeRecipeLiveSettings` in `src/modules/dyeStrip.js` writes each the record holds, whatever its modes, the steam temperature, flush temperature and flush flow among them, which up to v0.2.28 it left to the plugin's load write; a steam time or flow above 0 in the unit the recipe's steam mode is not using is written too (`recipeSteamPatch` in `src/modules/steam-mode.js`). So the plugin's load write finds them held after it (ADR-0022, Loading).
- **That apply switches steam** (v0.2.29, `recipeSteamPatch`). With the heater off, a record holding a steam time or temperature turns steam on (`steamOnPatch`), at the record's values and at the one Streamline remembers (`last-steam-temp`, `last-steam-duration`) for the one it holds none of, else 150 °C and 30 s. A record holding a steam time under 1 s, or a steam temperature below 135 °C, turns steam off whole (`steamOffPatch`), as DYE2's dashboard does (ADR-0022, Steam on and off).
- **It keeps what steam comes back to** (v0.2.29). Before the apply's write it keeps the steam temperature and time to come back to, the Workflow's where the apply turns steam off, and the flow.
- **Not during Auto Steam** (v0.2.29). While an Auto Steam session is active the apply writes no steam time, flow or temperature (`isAutoSteamActive` in `src/modules/api.js`), which `server/test/support/simulated-streamline.ts` models from `autoSteam()` until `leaveAutoSteam()`.
- **A failed apply is undone on the strip** (v0.2.29). Its highlight goes back where it was, with a "Could not apply recipe" notice.
- **A hold on Sleep closes Decaid** (v0.2.29, decentespresso/streamline-js#194, `c5091e5`). `sleepExitEnabled`, on until turned off, is kept in Decaid's store by `src/modules/settingsSync.js`; opening Decaid again wakes the Machine. Nothing of Decent Sync's reads it.
- **Its settings page renamed four settings** (v0.2.29, `99f57ad`, `6b0602d`). "Weight Flow Multiplier" is "Weight Look-ahead", the volume and hot water ones "Volume Look-ahead" and "Hot Water Look-ahead", on a page named "Shot control" (was "Flow Multiplier Settings"), and the flow calibration's label is "Flow calibration". Decent Sync's labels follow in sentence case (`protocol/src/settings-fields.ts`, `COLLECTIONS.md`); Decaid's field names (`weightFlowMultiplier` and so on) are unchanged.
- **It switches Skins through Decaid's host hook** where there is one (v0.2.29, `d84b8f5`; `window.decentApp.switchSkin`, `switchSkinNatively` in `src/modules/skin-version.js`), and its Skin cards show the versions Decaid has installed rather than GitHub's (`d0668b1`). Nothing of Decent Sync's reads either.
- **The LED colour sequence is gone** (v0.2.29, `ab09327`), with its `streamline.ledSequences` setting; static colours stay.
- **It logs each Workflow write** (v0.2.24, `823641e`). `putWorkflow` in `src/modules/api.js` logs `[AUDIT] workflow PUT by <writer>: <field paths>` for every `PUT /workflow` Streamline sends, always on (`logger.audit`), naming the writer `updateWorkflow` was given and the paths of the patch, never their values. It reaches the tablet's webview log, so a lost edit can be traced to the order of Streamline's writes; the plugin's writes and DYE2's are not in it.
- **Its steam counter counts delivery** (v0.2.24, `18b2c91`, `db5068b`; `src/modules/steam-timer.js`). The status line counts only machine state `steam` with substate `pouring`, holds through `pausedSteam`, and drops the count once delivery ends. Decaid reports the pause after a stop on time, or after Two Tap Stop's first tap, still as `pouring`, at a target flow of 0, which a Steam Record's duration leaves out (`STEAM_RECORDS.md`, decentespresso/decaid#1047): so Streamline's count can read 2 to 4 s longer than the Steam Record's duration.
- **Up to v0.2.13**, `resyncIfDrifted` pushed the kept value back whenever the Workflow held another. Seen on the test tablet (Decaid 0.8.8+2900, [#130](https://github.com/loganfuller/decent-sync/issues/130)): a hot water volume written as 120 was back at Streamline's 100 0.27 s after Decaid applied it, and a steam flow of 2.0 went back to Streamline's 2.5 when the DE1 reconnected.
- **It refreshes when a plugin pushes a change** (decentespresso/streamline-js#120 and #127, `streamline-js:docs/plugin-surfaces.md`, checked on `main` at `07be2b3`, which v0.2.14 (`3a4bd23`) includes). On load, every minute and on focus or visibility, `skinPlugins` in `src/modules/plugin-surfaces.js` picks the plugins `GET /api/v1/plugins` lists as loaded with an `http` endpoint `skin`, and `GET /api/v1/plugins/{id}/skin` is read (`parseSkinAnswer`, which takes `{"version":1,"surfaces":[],"live":{"endpoint":"changed"}}` with no surfaces). `liveEndpoint` takes `live.endpoint` only if the plugin's manifest declares it as a `websocket` endpoint, and while the page is visible Streamline keeps one reconnecting socket per plugin open to `/ws/v1/plugins/{id}/{endpoint}`, closing it while the page is hidden. A push of `{"what":"skin"}` re-reads only `skin` (`pushWants`); any other dispatches `streamline:workflow-refresh`, on which Streamline re-reads the Workflow and the DYE strip DYE2's favourites and recipes, at least 2 s apart (`src/modules/dyeStrip.js`). Nothing is written to the machine. In Decaid, already at v0.8.7, an `api` entry is read by `ApiEndpoint.fromJson` (`decaid:lib/src/plugins/plugin_manifest.dart`), which needs its `id`, a `type` of `http` or `websocket`, and a `data` object, or the manifest is invalid; `_handlePluginApiEndpoint` (`decaid:lib/src/services/webserver/plugins_handler.dart`) dispatches a request to a declared `http` endpoint to the plugin's `__httpRequestHandler`, with `api`, answering an undeclared endpoint 404 and a WebSocket one 400 itself; and `host.emit(event, payload)`, with `emit`, sends the payload, JSON-encoded, to each socket open on the endpoint named `event` at that moment (`_handlePluginSocketEndpoint`), buffering nothing, and throws without the permission. So the plugin declares `skin` and `changed` (`plugin/manifest.json`), answers `skin` with no surfaces and `changed` to listen on, and pushes `{"what":"workflow"}` there once Decaid has taken each post of `recipes` (`plugin/src/skins.ts`): never for a write that fails, is refused or posts nothing, nor for `baskets` or `equipment`, which the strip does not show. It pushes the same once Decaid has taken each `PUT /workflow` of the plugin's that changed the Workflow, Decaid's answer differing from the Workflow read just before (ticket #207): the server's Loaded Recipe writes, unloads and clears of the Workflow's grinder, batch and Basket, and the plugin's loads of the recipe the Workflow names and its clears of `recipeId` before a post of `recipes` that removes or gives away the record it names. So the tiles show them at once rather than at the 20 s poll: the server writes a Recipe's record before the Loaded Recipe write, one round trip apart, and a skin reads the Workflow on the record's push before the write reaches it. Not for a write Decaid refuses or does not answer, one of what the Workflow held already, nor for one with nothing to write. A push that throws is logged and changes nothing of the write's answer, or of the load. A push no socket hears is lost, and the skin's focus and visibility refresh catches up.
- **Decaid's store** (`KvStoreHandler` in `decaid:lib/src/services/webserver/kv_store_handler.dart`, the same at v0.8.7, v0.8.8 and v0.9.0): `GET /api/v1/store/{namespace}/{key}` answers the value, `null` for a key never set, and `POST` keeps the body read as JSON and answers `{}`. Each request opens its namespace, which `HiveStoreService` (`decaid:lib/src/services/storage/hive_store_service.dart`) creates empty where it is missing, and `KvStoreExportSection` then includes in backups.

What the plugin serves a Skin of its own (ticket #507, ADR-0030; `site/src/content/docs/technical/skin-authors.md`), read in Decaid's source at v0.9.1 and v0.9.2 and not yet run on a tablet (#516 is to):

- **A handler may answer with a promise.** `__dispatchPluginHttp` (`decaid:lib/src/plugins/plugin_manager.dart`) calls `plugin.__httpRequestHandler(event)` and, where what it returns has a `then`, answers with what that settles to, or with 500 and the error where it rejects. `registerPendingHttp` gives the plugin `pluginHttpTimeout`, 30 s, after which `_handlePluginApiEndpoint` answers 500, "Plugin did not respond in time". So the `status` endpoint returns a promise, and settles it within 10 s. A request carries its method, headers, query and a JSON body of up to 1 MiB (`largeRequestBodyBytes`), and no path beyond the endpoint's name; an answer's `body` has no size limit. The simulated tablet's `callEndpoint()` awaits the promise and gives up after 30 s of the tablet's time, as Decaid does.
- **New endpoints need no approval.** An update waits for approval only where `_addedPermissions` (`decaid:lib/src/plugins/plugin_source_service.dart`) finds a permission the installed manifest lacks: it compares `permissions` alone, at v0.9.1 and v0.9.2, for a release and a branch install alike. v0.9.2 adds only that a bundled plugin's update from its canonical repository may take the permissions its bundled manifest has (`_mayAutoApproveAddedPermissions`), and a confirmation for `manage.extensions`. The `status` and `changes` endpoints use `api` and `emit`, which the plugin already declares, so the update that adds them installs by itself.
- **Pushes go on an endpoint of their own.** `_handlePluginSocketEndpoint` sends each `host.emit(event, payload)` to the sockets open on the endpoint named `event`, and reads nothing a socket sends. Streamline takes any push on `changed` but `{"what":"skin"}` as a change of the Workflow (above), so the plugin pushes what a Skin is told of on `changes`.

What Decaid v0.9.3 does with Skins, run on its Linux release headless on 2026-11-24 for ticket #661 (`server/test/fixtures/decaid/tablet-software-v0.9.3/skin-management.json`; `server/test/support/decaid-skins.ts` simulates it), and on the owner's Android tablet in #659's trial:

- **A Skin's id is its own manifest's** (`skin-manifest.json`), whatever it was installed from, and its folder is named by it; so a `dist` build (`streamline.js-dist`, `streamline-cafe.js-dist`) installs beside the release rather than over it, and over a Skin of the same id only.
- **An install answers what was asked, never the Skin's id**, so the plugin finds the Skin installed as the one new to the list or whose `reaMetadata.installedAt` changed; an update check moves only `lastChecked`.
- **A commit given as a Skin's branch fails**, 500, as Decaid downloads `archive/refs/heads/<branch>.zip`; `install/url` with `archive/<commit>.zip` installs it, and the Skin then follows that URL.
- **Update check results name a Skin Decaid comes with by its repository** (`owner/name`) and any other by its id.
- **Removing the default Skin is not refused** (200): the default falls back to Streamline, while the server serves the removed folder, 404 for every page, until it is stopped and started. Removing a bundled Skin answers 403, an unknown one 500.
- **Choosing the default changes nothing served**; a stop and start serves it, on a port of its own (each Skin's folder keeps a port, `webUISkinPorts`), so browser storage, per origin, is not shared between Skins (inferred).
- **Stop and start rebuild the Skin view** on the tablet: white with a loading icon while stopped, then the default Skin, with the files on disk, about 1.5 s after the start (#659's trial, comment 7133362055). `stop` answers "Not serving" when stopped, `start` "Already serving" when serving, and a start that throws 500 `Failed to start: …` (from `_handleServerStart`; not recorded). Neither checks the Machine's state.
- **`host.localApi` takes every Skin route the plugin uses**: `PUT /webui/skins/default`, the installs, `POST /webui/skins/update`, `DELETE /webui/skins/{id}`, and the server's stop, start and status.
- **Decaid's own update over its socket**: `{"command":"install"}` answers `local_approval_required` at once where Android's permission to install apps is off, and nothing shows on the tablet; with it on, Decaid checks, downloads (`downloading`, then `available`), sends `installing` as `_installAttempt` starts, before it checks the download, and `installing` again once Android's installer opens, or `error` where it fails (`UpdateCheckService.requestRemoteInstall`, `requestPermission: false`). While `checking`, `downloading` or `installing` it ignores the command and says nothing (`downloadAndInstall` returns at `_inProgress`). The Linux release answers "In-app install is not supported on this platform". A remote install's taps and whether Decaid reopens were not seen (#659); Decaid's own Update button took one tap, Open, and Decaid did not reopen.

Which Skin a tablet runs, and which DYE2 (ticket #236, `COLLECTIONS.md`, Plugins and Skins). ## Identity and attribution

`preferredMachineId` is a connection identifier, not the hardware identity. Inspect `decaid:lib/src/services/webserver/settings_handler.dart` and the relevant machine implementation for Bluetooth/USB behavior. Use model and serial per ADR-0004 and ADR-0015; serial `"0"` is not a real identity. `GET /machine/info` fails while no machine is connected, so the plugin may have to send `hello` without hardware and send a new one once the machine reports it. Decaid sends `stateUpdate` only while a machine is attached (`PluginManager._replaceSnapshotSubscription`), which the plugin takes as its cue to read `/machine/info` again.

Shots and Steam Records include a Workflow; inspect `decaid:lib/src/models/data/shot_record.dart`, `steam_record.dart` and `workflow.dart` for capture-time identity. Only Shots carry it: `de1_state_manager` stamps `workflow.machine` (with `provenanceStatus` `captured` or `unavailable`) when a shot starts, and only since v0.7.6. Older Shots lack it; Decaid's imports from the legacy Tcl app (`de1app-*`) are not captured at all. Steam Records never carry it, because the steam sequencer stores the current Workflow. Apply ADR-0015's crediting rules instead of attributing every record to whichever tablet sent it.
