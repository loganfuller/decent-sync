References use the checkout convention in `AGENTS.md`. Audited against local Decaid commit `a45961b3` on 2026-10-03; the `fetch` discrepancy and the record shapes below were also checked at v0.8.6 and v0.8.7 (no changes under `lib/src/plugins` or `lib/src/models/data` between them), and re-checked at v0.9.0 on 2026-10-16. ## Loading and settings

The plugin supports the Decaid versions ADR-0017 names (v0.9.0 or newer) and declares `log`, `api`, `events.machine`, `events.shots`, `events.workflow` and `network.websocket`, as specified in issue #1, `pluginStorage`, for the tablet's id (ticket #79), and `emit`, to tell skins it changed DYE2's recipes (ticket #168, Skins below). Unknown permissions can prevent loading; check `decaid:lib/src/plugins/plugin_manifest.dart` before adding one. Decaid installs a plugin update by itself only when the update adds no permission: one that does waits as the source's `pendingUpdate` until someone approves it on that tablet, in Settings, Plugins (**Review**, then **Approve and update**) or with `POST /api/v1/plugins/{id}/update/approve` (`decaid:lib/src/plugins/plugin_source_service.dart`, `_updatePlugin` and `approvePendingUpdate`). Say so in `UPGRADING.md` for any release that adds one.

## Plugin storage

With `pluginStorage`, `host.storage(command)` sends a `{ type: "read", key }` or `{ type: "write", key, data }` command to Decaid and returns nothing. Decaid answers a read with a `storageRead` event of `{ key, value }`, `value` null for a key never written, and a write with a `storageWrite` event whose payload is only the data written, not its key (`_handlePluginStorage` in `decaid:lib/src/plugins/plugin_manager.dart`, unchanged in v0.8.8 and v0.9.0). A command that fails is logged by Decaid and never answered, so a plugin waits for each with a timeout. Commands travel as JSON, values are kept in a Hive box named after the plugin's id, and a write the plugin sends while it unloads still lands: Decaid finishes a retiring generation's writes before the next generation loads. Decaid's `HiveStoreService.set` takes no null, so a write of null fails and `host.storage` can delete no key (Decaid's store API can, with `DELETE /api/v1/store/{plugin id}/{key}`, which the plugin does not use), and Hive opens a box whole into memory (`decaid:lib/src/services/storage/hive_store_service.dart`, the same in v0.8.7, v0.8.8 and v0.9.0): what the plugin keeps there must be bounded, as the outbox's kept deliveries are, in a fixed ring of keys. The plugin sends its commands one at a time (`plugin/src/storage.ts`), matching a read's answer by its key and a write's by the string written, since its answer carries no key; once Decaid leaves a write unanswered, it sends writes without waiting until Decaid answers anything again, and as it unloads it sends the writes still queued, the one awaiting an answer again first. Without the permission, `host.storage` throws a `PluginPermissionError`. The same Hive box is what `GET /api/v1/store/{plugin id}/{key}` reads.

Decaid's backup (`GET /api/v1/data/export`, and the app's own backup) holds a plugin's storage only once the store API has opened it since Decaid started: `KvStoreExportSection` lists the `namespaces` of the store behind `KvStoreHandler`, which knows only the boxes it has opened itself, and `host.storage` opens them through the plugin loader's own store (`decaid:lib/src/services/storage/hive_store_service.dart`, the same in v0.8.7, v0.8.8, `main` on 2026-10-07 and v0.9.0). On Decaid v0.8.7's Linux release, a backup left out `decent-sync.reaplugin` until `GET /api/v1/store/decent-sync.reaplugin/tabletId` had been answered, and left it out again after Decaid restarted. So the plugin reads its storage through the store API once it knows the tablet's id (`keepStorageInBackups` in `plugin/src/decaid.ts`), asking again every 30 s until it is answered; a backup taken after that holds the id. Restoring a backup (`POST /api/v1/data/import`) keeps a key the tablet already has unless asked to overwrite: Decaid's onboarding restores with `onConflict=skip`, before any plugin is installed, and Settings, Data Management asks whether to skip or overwrite existing data. Backups do not hold installed plugins.

Decaid calls the global `createPlugin(host)` entry point and calls `plugin.onLoad(settings)` synchronously without awaiting a returned promise (`decaid:lib/src/plugins/plugin_manager.dart`). Keep `onLoad` short and schedule connection work through a timer. The loader has a load watchdog; inspect `decaid:lib/src/plugins/plugin_loader_service.dart` when changing startup behavior.

The target build is one ES2020 `plugin.js` with no module syntax. Decaid pastes it into a function body and then checks `typeof createPlugin`, so `createPlugin` must be declared at the top level of the script: `plugin/build.mjs` bundles an esbuild IIFE and assigns `var createPlugin` after it. The plugin's `id` must equal the manifest's. Use the host APIs and timer callbacks; do not assume a browser or Node environment. Run the built file in the simulated host, not just the TypeScript source.

The manifest (v0.8.7 and v0.9.0, `PluginManifest.fromJson`) has no field for a minimum Decaid version, and unknown keys are ignored. The server enforces the minimum instead: the plugin sends Decaid's `fullVersion` from `GET /info` (the tag it was built from plus a build number, from `flutter_with_commit.sh`) in every `hello`, and does not connect until it can read it. The server refuses an older or unreadable version with `decaid_too_old` (ADR-0017).

Secure settings are supplied to the loaded plugin, while the settings REST response reports whether they are set rather than exposing their values (`PluginLoaderService.pluginSettings`). The token must be declared secure. Settings changes can reload the plugin, so startup and unload must tolerate a new runtime generation.

## CPU time

Plugin JavaScript runs on Decaid's main isolate: `PluginLoaderService` is created in `decaid:lib/main.dart`, nothing in `lib/src/plugins` starts another isolate, and on Android flutter_js runs QuickJS synchronously. A long stretch of plugin work therefore holds up Decaid itself, its interface included. QuickJS interprets JavaScript and regular expressions, so costs differ from Node's. On 5 MiB of a Shot's JSON, on an Apple M5 with QuickJS 2025-04-26 (2026-10-05), `JSON.parse` and `JSON.stringify` of the Shot took 40 to 60 ms each, a `charCodeAt` loop over it about 140 ms, and a sticky regular expression matching its runs of ASCII about 15 ms. Each match costs as much as dozens of steps of a loop, though, so matching run by run is slow where runs are short: counting the UTF-8 bytes of 5 MiB of text alternating between ASCII and Japanese that way took 2.7 s. `utf8Length()` (`protocol/src/chunking.ts`) therefore matches only long runs of ASCII and steps through the rest. Chunking (`frames()`) took 35 ms for a 5 MiB Shot, 40 ms for one with 2 MB of Japanese notes, about 230 ms for 5 MiB of accented prose, and about 280 ms at worst, for text whose runs of ASCII are each exactly `ASCII_STEPS` (32) characters long. A tablet's CPU is several times slower. To measure, bundle the code with esbuild as an ES2020 IIFE and run it with `qjs` from Alpine's `quickjs` package in Docker.

## Server transport

Inspect `decaid:lib/src/plugins/plugin_transport_service.dart`, especially `_openWebSocket`, `send` and `_reserveOutbound`:

- `host.transport` opens `ws://` or `wss://` connections with `network.websocket`. The WebSocket open options support URL and subprotocols, not custom headers. Authenticate in the protocol handshake.
- `send` acceptance is not a server acknowledgment. Keep delivery state until the server acknowledges the stored logical message.
- A plugin generation may hold 8 transports, counting opens still in progress. `open()` has no timeout and cannot be cancelled: an upgrade the server never answers holds its slot until TCP gives up, possibly never. The plugin abandons an attempt after its connect deadline and counts its own transports so it never asks for a ninth (`plugin/src/connection.ts`); eight hung opens stop it reconnecting until it is reloaded.
- Default pending outbound and queued inbound limits are each 1 MiB per transport. The outbound check covers both a single payload and the sum already pending; sends exceeding it fail with `transport_resource_limit`.
- `send` resolving says only that the frame was queued, and nothing tells the plugin when it has been written, so frames just below 1 MiB would not do: several pending at once still pass the limit. The plugin sends frames of at most 256 KiB, measured in UTF-8 with their envelope and escaping, and counts what it has sent until the server confirms it, keeping at most 512 KiB unconfirmed (`plugin/src/sender.ts`; see `AI_PROTOCOL_NOTES.md`). The simulated host enforces the pending-byte limit, writes frames in order and can slow the writing, so tests exercise this.
- Unloading retires the plugin's transports. The outbox keeps its Workflow and machine state deliveries in plugin storage until acknowledged, and sends them first after a reload (ticket #93, `WORKFLOW-AND-STATE.md`, Kept across unloads); everything else it holds is in memory, and the record history it held is recovered by backfill.

## Local API and events

Use plugin-scoped `fetch` for Decaid's local API. It sends a request's method, headers and body as given (`init.method`, `init.headers`, and `init.body`, a string sent as its UTF-8), so the plugin writes through it too. `PluginManager._performFetch` has response-size (`maxFetchResponseBytes`, 10 MiB by default) and timeout (30 s) constraints; it does not provide a streaming response to JavaScript. Never rely on fetching an unbounded list in one response.

ADR-0009's original rationale and the original Further Notes in issue #1 stated that private-IP fetch is blocked; both have been clarified. **Source discrepancy:** `_performFetch` at v0.8.6, v0.8.7, v0.9.0 and `a45961b3` passes the URL to `HttpClient.openUrl` without a private-address check. Treat documented restrictions as host policy, not proof of enforcement. The agreed architecture still uses WebSocket for all server traffic.

## Skins

A skin is the app baristas use on a tablet in place of Decaid's own screens. It reads and changes the Workflow through Decaid's API, as the plugin does, and the plugin hears of its changes only through `workflowUpdated`. Streamline (`streamline-js`, checked on `main` at `07be2b3`, 2026-10-14, which v0.2.14 (`3a4bd23`) includes) remembers some of the steam, hot water and flush settings, and adopts a Workflow change made elsewhere rather than pushing its own back, so the plugin writes the Workflow, as a Loaded Recipe's steam, hot water and flush settings, and sets none of them but the steam temperature it turns steam back on at: `keepStreamlineSteamTemperature` sets `last-steam-temp` to the Recipe's with each load and Loaded Recipe write carrying one, interim until decentespresso/streamline-js#156 (ADR-0021, `plugin/src/streamline.ts`). Decent Sync supports only streamline-js `main` from `cec5664`, which adopts it, not v0.2.13 or earlier, which pushed them back, nor v0.2.18 or earlier (ADR-0017):

- **What it remembers.** The `*_LAST_VALUE_KEY` constants in `streamline-js:src/modules/api.js` name its keys in Decaid's store namespace `streamline-app` (`SETTINGS_NAMESPACE`): `last-steam-duration`, `last-steam-flow`, `last-steam-temp`, `last-milk-stop`, `last-flush-duration`, `last-hot-water-volume` and `last-hot-water-temp`, and `last-brightness`, which is not a Workflow setting. `persistSharedValue` writes each as JSON through `POST /api/v1/store/streamline-app/{key}` (`setValueInStore`), and `readSharedValue` reads it back (`getValueFromStore`), null meaning never set.
- **Its setters keep the value first.** `setTargetHotWaterVolume`, `setTargetHotWaterTemp`, `setTargetSteamDuration`, `setTargetSteamFlow` and `setStopAtTemperature` keep the value and mark it pending before their `PUT /workflow`, and clear the mark once it took (`pushRemembered`); `setTargetSteamTemp` keeps it without a mark. `setTargetSteamTemp` and `setStopAtTemperature` keep only a value above 0, and `steamHeaterFor` turns steam back on at `last-steam-temp`. `updateFlushValue` in `src/modules/ui.js` keeps the flush time after its `PUT`.
- **It adopts a change made elsewhere** (decentespresso/streamline-js#109). `resyncIfDrifted` compares the Workflow with the kept value, and `decideResync` in `src/modules/resync-policy.js` decides: its own push the Workflow has not taken (`pending`) is pushed again; a setting the Workflow lacks is filled from the kept value; a value seen within `ECHO_WINDOW_MS` (10 s) of its own push that differs from it is ignored; any other difference is adopted, kept in the store with nothing pushed. `resyncDriftedShotSettings` in `src/modules/app.js` runs it on every shot-settings frame from the machine, which echoes a Workflow change, for steam time and hot water volume and temperature (`SHOT_SETTINGS_KV_FIELDS`). `loadInitialData` runs it on every load for each key but `last-steam-temp`, and the milk stop only while it is on (`resyncMilkStopIfDrifted`).
- **It shows a change made elsewhere** (decentespresso/streamline-js#132, decentespresso/streamline-js#137). `refreshWorkflowTiles` reads the Workflow back after its own writes, on a machine state change and every 20 s (`WORKFLOW_POLL_MS`), and repaints the steam, hot water, milk stop and flush tiles from it.
- **But not its steam temperature.** `steamHeaterFor` sends `last-steam-temp` along with a steam time but 0 that `setTargetSteamDuration` sets into a Workflow whose steam temperature is 0 (since decentespresso/streamline-js#143, `98b6b90`, in `c006dac`; before it with every such steam time), as on a barista's steam time change, a profile switch carrying a saved steam time (`applySavedSteamSettings` in `src/modules/profileManager.js`) or a retried push, and `setSteamHeaterEnabled(true)` sends it after descaling. Nothing compares it with the Workflow. Streamline sets it only from `setTargetSteamTemp`, its settings page, and from the Workflow as steam is switched off (duration 0).
- **Nor each profile's steam settings.** `saveContextToActiveProfile` keeps the main page's steam time and flow for the active profile under `streamlineProfileOverrides` (`OVERRIDE_KEYS` in `src/modules/profile-overrides.js`), and `applySavedSteamSettings` in `src/modules/profileManager.js` sends them on every switch to it and on every wake with a wake profile set (`loadProfileForWake`). Nothing takes a Workflow change into them. Auto steam mode (`src/modules/auto-steam-session.js`) keeps the steam settings it found on entering it and writes them back on leaving it.
- **Up to v0.2.13**, `resyncIfDrifted` pushed the kept value back whenever the Workflow held another. Seen on the test tablet (Decaid 0.8.8+2900, [#130](https://github.com/loganfuller/decent-sync/issues/130)): a hot water volume written as 120 was back at Streamline's 100 0.27 s after Decaid applied it, and a steam flow of 2.0 went back to Streamline's 2.5 when the DE1 reconnected.
- **It refreshes when a plugin pushes a change** (decentespresso/streamline-js#120 and #127, `streamline-js:docs/plugin-surfaces.md`, checked on `main` at `07be2b3`, which v0.2.14 (`3a4bd23`) includes). On load, every minute and on focus or visibility, `skinPlugins` in `src/modules/plugin-surfaces.js` picks the plugins `GET /api/v1/plugins` lists as loaded with an `http` endpoint `skin`, and `GET /api/v1/plugins/{id}/skin` is read (`parseSkinAnswer`, which takes `{"version":1,"surfaces":[],"live":{"endpoint":"changed"}}` with no surfaces). `liveEndpoint` takes `live.endpoint` only if the plugin's manifest declares it as a `websocket` endpoint, and while the page is visible Streamline keeps one reconnecting socket per plugin open to `/ws/v1/plugins/{id}/{endpoint}`, closing it while the page is hidden. A push of `{"what":"skin"}` re-reads only `skin` (`pushWants`); any other dispatches `streamline:workflow-refresh`, on which Streamline re-reads the Workflow and the DYE strip DYE2's favourites and recipes, at least 2 s apart (`src/modules/dyeStrip.js`). Nothing is written to the machine. In Decaid, already at v0.8.7, an `api` entry is read by `ApiEndpoint.fromJson` (`decaid:lib/src/plugins/plugin_manifest.dart`), which needs its `id`, a `type` of `http` or `websocket`, and a `data` object, or the manifest is invalid; `_handlePluginApiEndpoint` (`decaid:lib/src/services/webserver/plugins_handler.dart`) dispatches a request to a declared `http` endpoint to the plugin's `__httpRequestHandler`, with `api`, answering an undeclared endpoint 404 and a WebSocket one 400 itself; and `host.emit(event, payload)`, with `emit`, sends the payload, JSON-encoded, to each socket open on the endpoint named `event` at that moment (`_handlePluginSocketEndpoint`), buffering nothing, and throws without the permission. So the plugin declares `skin` and `changed` (`plugin/manifest.json`), answers `skin` with `changed` to listen on, and no surfaces but the Clear button (below), and pushes `{"what":"workflow"}` there once Decaid has taken each post of `recipes` (`plugin/src/skins.ts`): never for a write that fails, is refused or posts nothing, nor for `baskets` or `equipment`, which the strip does not show. It pushes the same once Decaid has taken each `PUT /workflow` of the plugin's that changed the Workflow, Decaid's answer differing from the Workflow read just before (ticket #207): the server's Loaded Recipe writes, unloads and clears of the Workflow's grinder, batch and Basket, and the plugin's loads of the recipe the Workflow names and its clears of `recipeId` before a post of `recipes` that removes or gives away the record it names. So the tiles show them at once rather than at the 20 s poll: the server writes a Recipe's record before the Loaded Recipe write, one round trip apart, and a skin reads the Workflow on the record's push before the write reaches it. Not for a write Decaid refuses or does not answer, one of what the Workflow held already, nor for one with nothing to write. A write made as two `PUT /workflow`, for a change of profile (ADR-0022), pushes once, after both. A push that throws is logged and changes nothing of the write's answer, or of the load. A push no socket hears is lost, and the skin's focus and visibility refresh catches up.
- **The Clear button** (ticket #203, ADR-0022, checked on streamline-js `main` at `cec5664`). While the Machine has a Loaded Recipe, the plugin's `skin` answer holds a `header-button` labelled "Clear", with the text "Unload <name>" (Streamline's tooltip and, after the label, its accessible name), the name as the DYE strip's `recipeLabel` gives it from the Recipe's record, cut to Streamline's 40 UTF-16 code units by whole code points, so Streamline's own cut never splits a character (`CAPS.text` and `cleanText` in `src/modules/plugin-surfaces.js`). The plugin reads nothing to answer it, as it follows the Loaded Recipe already (`LoadedRecipes.loadedName`), and a plugin with no settings, which follows none, never shows it. Its action is `open` of view `clear` as a page, which Streamline sends to the plugin's `ui` endpoint (`pluginUiUrl` in `src/settings/plugin-view.js`) with `returnTo`, the dashboard's URL. A header button can only `open`. As a page, the dashboard reloads with the unload made, and its strip reads the Workflow afresh, rather than on the plugin's `{"what":"workflow"}` push, which it takes at most every 2 s (`streamline:workflow-refresh` in `src/modules/dyeStrip.js`). The `ui` page has the plugin write `{"context":{"extras":{"dye":{"recipeId":null}}}}` into the Workflow (`LoadedRecipes.unloadNow`), waits at most 3 s for it, and answers 303 to `returnTo` where that is an `http:` or `https:` URL without credentials in printable ASCII, with `Cache-Control: no-store`, so the dashboard reloads with nothing selected and the page never sits in the history, and 204 otherwise. Decaid awaits a promise a plugin's `__httpRequestHandler` answers with (`__dispatchPluginHttp` in `decaid:lib/src/plugins/plugin_manager.dart`). Declaring `ui` also gives the plugin's card in Streamline's settings an **Open** button (`renderPluginCard` in `src/settings/settings.js`), which opens `ui` with no view: any view but `clear` is sent straight back to `returnTo`, unloading nothing, or answered 404 without one. Any method but GET is answered 405. A failed unload is logged and not tried again. The plugin pushes `{"what":"skin"}` on `changed`, which has Streamline read only `skin` again, as the button is to show, hide or change its name: as the Loaded Recipe changes, as the Machine becomes capture-only or DYE2 goes, and as the Recipe is renamed. Streamline draws one plugin header button in total, the first plugin's in Decaid's plugin list whose `skin` read succeeds (`streamline-js:docs/plugin-surfaces.md`, Limits): no other plugin offers one today, and one that does would take the slot from decent-sync by that order.
- **Decaid's store** (`KvStoreHandler` in `decaid:lib/src/services/webserver/kv_store_handler.dart`, the same at v0.8.7, v0.8.8 and v0.9.0): `GET /api/v1/store/{namespace}/{key}` answers the value, `null` for a key never set, and `POST` keeps the body read as JSON and answers `{}`. Each request opens its namespace, which `HiveStoreService` (`decaid:lib/src/services/storage/hive_store_service.dart`) creates empty where it is missing, and `KvStoreExportSection` then includes in backups.

Which Skin a tablet runs, and which DYE2 (ticket #236, `COLLECTIONS.md`, Plugins and Skins). Decaid v0.9.0 lists its Skins at `GET /api/v1/webui/skins` (`WebUIHandler` in `decaid:lib/src/services/webserver/webui_handler.dart`), each `{ id, name, path, description, version, isBundled, reaMetadata }`, where `id` is the Skin's manifest id, `version` its manifest's, and `path` the folder Decaid keeps it in; `GET /webui/skins/default` answers the Skin `defaultSkinId` names, or else `streamline.js`, a bundled Skin or the first installed (`WebUIStorage.defaultSkin`), and 404 only with none installed; and `GET /webui/server/status` answers `{ serving, path, port, ip }`, `path` the folder the WebUI server serves (`WebUIService.serverPath`), null while it serves none. Decaid starts serving the default Skin as it starts (`initialization_step.dart`, or the folder `--skin-path` names), and Quick Settings and `POST /settings` with `webUiPath` serve another folder without changing the default (`quick_settings_widget.dart`, `settings_handler.dart`); a change of default is served only from the next start. So the active Skin is the one whose `path` is the status's `path`, compared exactly, or the default where none is. On Decaid's v0.9.0 Linux release, run headless, Decaid served its default Skin as it started, and the status's `path` was that Skin's `path` in the list character for character, as it was for each Skin served through `webUiPath` (`server/test/fixtures/decaid/plugins-and-skins-v0.9.0/`). On the test tablet's Android build, `GET /settings` (whose `webUiPath` is the folder served) answered `/data/user/0/net.tadel.reaprime/app_flutter/web-ui/streamline.js` with `defaultSkinId` `streamline.js-dist` (`server/test/fixtures/decaid/de1pro-v0.9.0/`, 2026-10-16): the release served, the build of `main` only the default, and the served folder in the form Decaid keeps a Skin's `path` in; #232 is to check that its Skins list gives the same string. Streamline's release installs as `streamline.js`, and its `dist` branch, a build of `main`, as `streamline.js-dist`, the id its `skin-manifest.json` declares (`streamline-js:RELEASE.md`), with `reaMetadata.commitHash` `branch:dist` and no commit; a build of `main` reports the version of the release before it. Decaid bundles a Streamline release among its Skins and replaces them with their latest releases in the background after it starts. DYE2 is `dye2.reaplugin` in `GET /api/v1/plugins`, with `loaded`, `autoLoad` and `source` (`PluginsHandler`; `PluginSource` in `decaid:lib/src/plugins/plugin_source.dart`); a branch install's `source.kind` is `github_branch`, with its `branch` and `commit`, and DYE2's branch installs come from its `dist` branch, since its `main` holds no plugin at its root. Right after Decaid starts, before it has loaded its plugins and Skins, it lists neither, answers the default 404 and serves nothing.

## Identity and attribution

`preferredMachineId` is a connection identifier, not the hardware identity. Inspect `decaid:lib/src/services/webserver/settings_handler.dart` and the relevant machine implementation for Bluetooth/USB behavior. Use model and serial per ADR-0004 and ADR-0015; serial `"0"` is not a real identity. `GET /machine/info` fails while no machine is connected, so the plugin may have to send `hello` without hardware and send a new one once the machine reports it. Decaid sends `stateUpdate` only while a machine is attached (`PluginManager._replaceSnapshotSubscription`), which the plugin takes as its cue to read `/machine/info` again.

Shots and Steam Records include a Workflow; inspect `decaid:lib/src/models/data/shot_record.dart`, `steam_record.dart` and `workflow.dart` for capture-time identity. Only Shots carry it: `de1_state_manager` stamps `workflow.machine` (with `provenanceStatus` `captured` or `unavailable`) when a shot starts, and only since v0.7.6. Older Shots lack it; Decaid's imports from the legacy Tcl app (`de1app-*`) are not captured at all. Steam Records never carry it, because the steam sequencer stores the current Workflow. Apply ADR-0015's crediting rules instead of attributing every record to whichever tablet sent it.
