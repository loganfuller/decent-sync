Subsequent tickets extend it; read the assigned ticket for scope.

Validators report problems by field name, never by value, because a `hello` carries the token; keep it that way, and never log frames. The only exception is a Decaid version's release numbers, which cannot hold a token. The few values a tablet chooses that the server does log (a `hello`'s plugin and Decaid versions and reported hardware, and an ignored record's id) are escaped, and quoted where they stand alone in a line (`escaped` and `quoted` in `server/src/sync/sync.gateway.ts`; a refusal's message, which may name reported hardware, is logged escaped), so a tablet cannot forge log lines or control a terminal; log any other the same way. The server checks a `hello`'s protocol version and wire revision before its shape, so a plugin speaking an older version is told it is too old, then a valid `hello`'s Decaid version (ADR-0017, ADR-0025). A version refusal keeps a string `token`, so the server can show the reason on a valid token's Machine (an invalid token changes nothing). Every refusal is an `error` message followed by a close with that error's code. The plugin stops reconnecting after a bad-token, plugin-too-old or Decaid-too-old close, waits for the machine to report other hardware after a hardware-dismissed close, waits 5 minutes and then sends a `yielding` hello after a replaced or machine-held close (below), and retries with backoff after anything else, a superseded close included.

Identity is settled only at `hello` (ADR-0015). The plugin reconnects with a new `hello` when the machine first reports its hardware or reports different hardware, checking `GET /machine/info` on `stateUpdate` events (at most every 5 s) and every poll interval. It also reconnects when the machine its `hello` reported comes back after being seen gone, by such a check or by Decaid refusing a write into the Workflow for want of a machine, as of a Loaded Recipe's hot water, so the server writes it again (`LIBRARY.md`, How the plugin writes).

Supported versions follow ADR-0017 and ADR-0025. The protocol stays at version 1, and the plugin and server each work with the other's previous release, never one before it, which the wire revision keeps (below). The server closes the connection on a message type it doesn't know; the plugin logs it ("Ignoring a message from the server") and carries on. The mixed-versions suite fails on either. The archived prototype's protocol was never released and is not supported.

The spec also requires unknown-field tolerance, opaque Decaid payloads, at-least-once delivery, idempotent handlers and acknowledgment after storage, where a delivery set aside counts as stored (below). It specifies whole-message chunking for any oversized message. Define those behaviors in the shared package and verify them through the simulated tablet, including raw-frame cases.

## Wire revision

`hello` and `welcome` carry `wireRevision`, the sender's `WIRE_REVISION`, a whole number from 1 (ticket #279, ADR-0025). A peer that sends none, as every release up to 1.3.1 does, is at revision 1 (`FIRST_WIRE_REVISION`, read by `wireRevisionOf`). The field is one the receiver may ignore for good, which 1.3.1 does, so it raised nothing. The Live View's messages (ticket #260), the first change after 1.4.0 the receiver can't ignore, raised it to 2 (`LIVE_VIEW_WIRE_REVISION`).

- **Raising it.** Any change to the wire the receiver can't ignore for good, a new message, field or value included, raises `WIRE_REVISION`. The first such change after a release raises it by one, and later changes before the next release share that number. A change begun before a release and merged after it counts as after it, as that release went out without it: its checks ask for the revision above the release's, and it raises `WIRE_REVISION` to that if no change has yet. While `WIRE_REVISION` is still the release's, no test can tell, as a check for the release's own revision looks the same either way; once another change has raised it, such a check throws, saying to delete it or to ask for the current revision. A field the receiver may ignore for good raises nothing and needs no check until a release relies on it; that reliance is such a change, and the release relies on the field only from a peer at the revision it raises. A test fails when `WIRE_REVISION` is more than one above the latest release's, or below it, read from the release's tag without a build (`protocol/test/wire-revision.test.ts`, which needs the tags).
- **Checks where something new is sent.** What a revision adds goes only to a peer at that revision: each check asks `peerHasWireRevision` with the peer's revision and the revision the addition arrived in. Once the wire has moved past that revision, every peer accepted has it, and asking throws, saying to delete the check, so tests find one left over. Asking about a revision above `WIRE_REVISION` throws too, saying to raise it.
- **The window.** `acceptsWireRevision` accepts a peer no more than one revision behind, or any revision ahead, as each revision's wire holds the last's. The server checks a `hello`'s wire revision after its protocol version and before its shape: one more than one behind is refused with `plugin_too_old`, which its token's Machine shows, as for a protocol version, and one that isn't a whole number from 1 with `protocol_error`. A plugin welcomed by a server more than one behind logs, once per connection, that the server needs upgrading, and carries on.
- **Unreleased builds.** `main` builds between releases share a revision, so a plugin and server from different `main` commits, as on staging, may differ and aren't held to this.

## Live frames

Live frames are the one thing the plugin sends outside its outbox (ADR-0024, ticket #260). The server sends `liveStart` while the Machine has an unexpired lease, which each open Live View holds and keeps 30 s after it closes, unless its session has ended (#261), and `liveStop` once it has none, each with no payload, only to a plugin at `LIVE_VIEW_WIRE_REVISION`, and the plugin sends `liveFrame` only to a server at it: a server of 1.4.0 or earlier closes the connection on `liveFrame`, and a plugin of 1.4.0 or earlier ignores `liveStart`, logging that it did. `liveReceived` frees the plugin's live budget (#269), below.

- **What a frame is.** `liveFrame` has no id: it is never acknowledged, kept, sent again after a reconnect, or chunked, and takes no part in the check for already-handled ids. It carries its `source` (`LIVE_SOURCES`: `machine`, and `waterLevels`, `scale`, `shotSettings` and `devices` from Decaid's local sockets since #262, the sensors' later), a `sensorId` for `sensor`, `receivedAt`, the plugin's time it received it in UTC, `stateSince` for `machine`, the plugin's time the Machine State's name began, and `frame`, Decaid's data as Decaid sent it, opaque. Only the envelope is validated. Decaid's own `timestamp` in a frame is the tablet's local time without an offset, and is never compared with the plugin's times.
- **The plugin.** It streams from `liveStart` until `liveStop` or the connection's end; a `liveStart` while streaming changes nothing, and it keeps nothing across an unload (`plugin/src/live-view.ts`). Meanwhile it holds Decaid's local sockets open, each frame of one a live frame of its source, as Decaid sent it (`AI_RUNTIME_NOTES.md`, The Live View's sockets). It tracks the time in state from every `stateUpdate`, streaming or not, and keeps it across reconnects: a change of the Machine State's name (`nameMachineState` in `protocol/src/machine-states.ts`) restarts it, a change of detail alone doesn't. During `espresso`, `steam`, `hotWater` and `flush` every frame goes; otherwise each source sends at most one a second, the latest winning, and a change of Machine State goes at once. A frame whose relayed notification would pass PostgreSQL's limit (`liveFrameFits`) is dropped before it is sent, as is one Decaid's transport refuses. Its `send` is the sender's for a message without an id that fits a frame: at once, not counted toward the outbox's unconfirmed bytes.
- **The live budget.** Decaid's `send` resolves once a frame is queued, so live frames on a slow or stalled link would fill its 1 MiB queue, which the outbox's 512 KiB of unconfirmed frames, `hello` and heartbeats rely on, and a refused heartbeat or delivery drops the connection. So the plugin sends a live frame only while the bytes of live frames it has sent on the connection, less those the server says it received, stay within 64 KiB (`LiveBudget` in `plugin/src/live-view.ts`). Past it, each source (`liveSourceOf`: a sensor is a source of its own) holds at most one unsent frame, which a newer one replaces, and every frame waits behind those held; they go, in the order they came, as `liveReceived` frees room. The server answers live frames with `liveReceived`, at most once a second as they arrive, at once if a second has passed since the last and otherwise once it has, whether it relays them or not. Its `bytes` is the UTF-8 length of every `liveFrame` it has received on the connection, each frame's text as sent, which the plugin counts the same way, so the count is exact on a slow link too. A frame Decaid refuses never left the tablet, so its bytes are freed. A `liveStop` drops the frames held and keeps the count, and each connection starts with nothing counted.
- **The server.** A welcomed connection's `liveFrame` is handled as it arrives, ahead of its queue of deliveries, as a heartbeat is answered; one arriving before the welcome, or in chunks, is dropped. A frame from a connection the server didn't start, or since stopped, is dropped, and one too large for a notification too, as are those past a connection's `MAX_LIVE_FRAMES_PER_SECOND` (1000) in a second, counted in the instance's memory (ADR-0016), which the plugin's own never reach: the most to arrive at once, as a stalled link recovers, is its live budget, fewer than 750 frames. The rest are relayed one at a time for each connection, the latest of each source waiting, by `pg_notify` on `live_frames` in a statement of its own that finds the Machine still held by that connection, so a frame from a connection another hello has replaced is dropped even if received before. A failed relay is logged and dropped, and never closes the connection. The notification's payload is `relayedLiveFrame`: the Machine's id and the frame's envelope without its type, which every instance writes, as is, as one event to its own streams of that Machine; a stream whose lease isn't held yet is sent the latest of each source once it is.
- **A viewer joining.** Decaid sends the shot settings, the device list, a steady tank's water level and the scale's connection status only as the plugin opens its socket or as they change (the device list once a minute too), so a viewer joining a stream already running, or a page reloaded within its linger, would never see them. So the connection's instance keeps the latest frame of each of those sources it has taken to relay, in its memory for that connection (ADR-0016), and relays each again, unless a newer one waits its turn, once a decision finds a lease of its Machine it hadn't seen while the connection streams: each decision reads the ids of the unexpired leases, so renewals and lingers, announced too, relay nothing again. The viewers already watching receive them twice. Machine snapshots come several times a second, asleep too, and aren't relayed again. What it keeps is dropped with `liveStop`, after which the plugin opens the sockets afresh.

## Tablet ids

ADR-0006 keys the server's id map by tablet, so every `hello` names the tablet it comes from. Decaid gives plugins no installation id, so the plugin makes a random UUID when its `tabletId` key in Decaid's plugin storage was never written (Decaid answers `null`), writes it there, and otherwise uses the stored one (`plugin/src/tablet-id.ts`). It reads the id once per load, before its first connection; a read Decaid leaves unanswered, as it does one that fails, is given up on after 10 s and retried with the reconnect backoff, never taken for a key never written. Something other than a UUID under the key is replaced with a new id. Losing the storage only makes a tablet look new (ADR-0006). Decaid's backups hold the id only because the plugin also reads its storage through Decaid's store API (`AI_RUNTIME_NOTES.md`, Plugin storage).

The server records each tablet when it accepts a `hello`, in the same transaction, against whoever the connection resolved to, as its records are (ADR-0015): the token's Machine, or for a mismatch the reported hardware's Machine, or its Pending Machine until a Machine takes it over (`server/src/machines/tablets.ts`). Identity resolution does not change. A tablet is `tablets` (its id and when it was first seen) and `machine_tablets` (one row per tablet and Machine or Pending Machine, upserted, so connections through any instance find one row). Each row has PostgreSQL's times of its first accepted `hello` and of its last sighting, which a connection's heartbeats keep current while it holds its Machine. Each also has `last_hello`, a number from its column's sequence. Once a `hello` has recorded its tablet, with no contested work left, it takes an advisory lock every hello takes (`TABLET_ORDER_LOCK`), numbers the record under it, and holds it until it commits. Numbers therefore rise in the order hellos are accepted, whatever their holders and tokens, on any instance, and never tie, and records joined by adoption keep the higher. The lock covers only that statement, the Machine's last-seen time the hello then writes on a row it holds already, and the commit, which can still wait (as on the lock PostgreSQL takes to queue the hello's NOTIFY, or on writing its log), and hellos queued for the lock wait with it. A Machine's view lists the tablet of its record with the highest as `tablet`, its latest connection's, and the rest as `earlierTablets`; heartbeats never change that order. A heartbeat finds its row by the tablet and whoever the connection's records go to now (`recordOf`), not by a row id, since adoption may have taken a Pending Machine's row over, or joined it into its Machine's, meanwhile. The join deletes the held row and reads it in one statement, so a heartbeat it waits for is kept. A heartbeat that waited for an adoption finds no row, as its query looked for the hardware's holder before the adoption committed, so it looks again in a query of its own.

## Replaced connections and takeovers

An accepted `hello` makes its connection the one holding its Machine (`connected_session_id`), with its tablet beside it (`connected_tablet_id`), in the transaction that decides it under the Machine's row lock, so hellos through any instance are decided one at a time (ADR-0016). Every instance then checks its connections to that Machine (`MachinesService.standings`) and closes any that no longer holds it: as `replaced` if the holder's tablet is another, and as `superseded` if it is the same tablet or none holds the Machine any longer. A tablet routinely reconnects while the server still holds its old connection, unheard for up to `MISSED_HEARTBEATS` intervals, and a `hello` its plugin gave up on may commit after the plugin's next one; either way the connection closed is from the same tablet, and its plugin reconnects with its normal backoff. A heartbeat that finds its connection no longer holds the Machine reads who does in queries of their own, since its own may have looked before the hello that replaced it committed.

When the connection replaced was live, heard from within `MISSED_HEARTBEATS` intervals by PostgreSQL's clock, and came from another tablet, the `hello` took the Machine over. An accepted hello writes its Machine's last-seen time with `clock_timestamp()` last, after numbering its tablet's record under `TABLET_ORDER_LOCK`, when only its commit is left to wait for, so a hello that waited on locks longer than that window is still live for the next. The same transaction records the takeover on the Machine (`takeovers`, one row per Machine, replaced by the next; `server/src/machines/takeovers.ts`): PostgreSQL's time, and for each connection its tablet, the address it came from (its socket's, or with `CLIENT_ADDRESS_HEADER` set, the client's as the proxy's header gives it; `server/src/sync/client-address.ts`), its connection id, and its plugin and Decaid versions. A Machine's view shows it as `takeover`, apart from `lastRefusal`, and keeps it until the next. Replacing a dead connection, or one from the same tablet, records nothing.

A plugin told its connection was `replaced` keeps capturing, whether or not the close after the error reaches it, and even if a send fails as the connection ends (a send can fail before the events received ahead of the transport's end are handled, as the simulated host delivers them, so the plugin lets those be handled first and drops the connection after `SEND_FAILURE_GRACE_MS` only if none ends it), as while the server is unreachable, and after 5 minutes connects with `yielding: true`, asking not to replace a live connection from another tablet. The server refuses such a `hello` with `machine_held` while one holds the Machine, recording no refusal, and otherwise accepts it as any other; one from the holder's own tablet replaces it. After `machine_held` the plugin waits and tries again the same way until a `hello` is welcomed. So two tablets with one token never take turns: the one connected last keeps the Machine until it goes away, and the other then connects again by itself.

## Chunked messages

Decaid holds at most 1 MiB of a transport's frames awaiting the network, one frame or all those queued together, and its `send` resolves once a frame is queued, not once it is written (`AI_RUNTIME_NOTES.md`). `frames()` in `protocol/src/chunking.ts` sends a message whose encoding is at most `MAX_FRAME_BYTES` (256 KiB, measured as Decaid measures it: UTF-8, with envelope and JSON escaping) as one frame, and a larger one as `chunk` frames of at most that size. A chunk carries `id` (the delivery's own id, or one the plugin makes up for a message without one), `index`, `count` and `data`, the message's JSON in pieces that never split a surrogate pair. `Reassembly` puts them back together.

Every delivery waits in the plugin's one outbox (`plugin/src/outbox.ts`) until acknowledged, one awaiting acknowledgment at a time, and is sent again with the same id on the next connection if it was not; a Workflow or machine state delivery also after a reload, from Decaid's plugin storage (ticket #93, `WORKFLOW-AND-STATE.md`, Kept across unloads). The plugin sends every message, `hello` included, through one `Sender` per connection (`plugin/src/sender.ts`). A delivery or a chunk counts against 512 KiB from when it is handed to Decaid until the server confirms it, a chunk by `chunkReceived` and a whole delivery by its `ack`; since Decaid writes frames in order, a confirmation covers every earlier frame too. `hello` and `heartbeat` are not counted and go out at once, so a large message never holds up heartbeats.

The server sends a `write` too large for one frame the same way, as chunks named by its id, since Decaid closes a transport whose inbound frames pass 1 MiB; the plugin puts them back together with `Reassembly` under `CHUNK_LIMITS`, confirms none, and drops the connection, to reconnect, if they do not fit together. The server sends one write at a time per connection, each once the one before it is answered, so no flow control is needed.

The server reassembles each connection's chunks in memory, confirms every chunk it receives with `chunkReceived`, and handles a completed message as if it had arrived whole: de-duplicated by its id, stored, then acknowledged once. A message repeated whole after its `ack` is acknowledged again, as any repeated delivery is. Chunks may arrive in any order, between other frames and more than once. A chunk that contradicts an earlier one, or that would hold more than `CHUNK_LIMITS` allow, closes the connection with `protocol_error`, and so does a message whose chunks do not decode as a whole message; nothing of either is stored or acknowledged. The limits count everything held for messages still incomplete: their ids and data, at most 16 Mi characters (1 Mi before `hello` is accepted), and their chunks, at most 1024, counting those yet to arrive from a message's first chunk on. A dropped connection's partial chunks go with it, and the plugin sends the message again whole, from its first chunk, on its next connection, whichever instance that reaches.

## Delivery ids and replays

A delivery's or chunk's `id` is at most `MAX_ID_LENGTH` (128) UTF-16 code units; the plugin's are about 30 (`Outbox.nextId`). A longer one closes the connection with `protocol_error`, naming the field and never its value, and nothing of that message is stored or acknowledged. Plugins already sent ids this short, so the limit needs no new protocol version. A `hello`'s machine model, serial and connection id are likewise at most `MAX_HARDWARE_LENGTH` (100), the longest serial an Admin may enter: the server keeps them in unique indexes, which refuse an entry over about 2.7 KB every time it is tried. A longer one refuses the `hello` as `protocol_error`, which writes nothing; Decaid reports far shorter ones. A Shot recording a longer model or serial is credited as recording no hardware (`SHOTS.md`).

Each connection remembers the deliveries it handled most recently (`HandledDeliveries` in `server/src/sync/handled-deliveries.ts`), with the request each index was answered with: at most 64, holding at most 256 Ki code units of ids, those of the requests included, forgetting the oldest first. Heartbeats keep a connection open indefinitely, so remembering every delivery would grow without bound. A delivery sent again on the connection while remembered is acknowledged without being handled again, after its index's request if it is one. One forgotten is handled again, which changes nothing: storage decides every delivery once (a Shot by its edit time, a Steam Record by its id, Workflow, machine state and collection deliveries by their recorded delivery ids), and an index is answered from what is stored by then. The plugin sends a delivery again only on a new connection, so it never relies on what a connection remembers.

## Deliveries set aside

The plugin sends one delivery at a time, oldest first, and sends an unacknowledged one again first on every connection, so a delivery the server fails to store every time it arrives would hold up everything queued behind it, and indexes and `welcome` would bring it back after every reload (ticket #60). No supported Decaid is known to send one, but PostgreSQL refuses some values Decaid's JSON can carry: a NUL (`\u0000`) in any string, which jsonb refuses with SQLSTATE 22P05 and text columns with 22021, a lone UTF-16 surrogate, which jsonb refuses with 22P02, and a value too long for an index entry, such as a Shot's recorded hardware, refused with 54000.

So when storing a `shot`, `shotUpdated`, `steam`, `workflow`, `machineState` or `collection` fails with an error that repeats for the same payload, the sync gateway sets the delivery aside and acknowledges it as stored (`SyncGateway.capture`). Those errors are PostgreSQL's class 22 (data exception), 23514 (check violation) and 54000 (program limit exceeded), read from the SQLSTATE in the cause Prisma's driver adapter gives a known request error (`repeatingFailure` in `server/src/set-aside-deliveries/repeating-failures.ts`). Every other error closes the connection with 1011 and leaves the delivery unacknowledged, as before: lost connections, socket errors, connections not opened in time, statements past their query timeout, lock and transaction timeouts, deadlocks and serialization failures, and errors with no SQLSTATE or not from the database at all. `server/test/set-aside-deliveries.test.ts` simulates those with a trigger, a lock the test holds and a stand-in pooler that resets its connections.

A delivery set aside is recorded in `set_aside_deliveries` for the Machine whose token delivered it, with its type and id, its Shot's or Steam Record's id, PostgreSQL's SQLSTATE and message, PostgreSQL's time, and the message as received: its JSON text, from its frame or put back together from its chunks, escapes such as `\u0000` intact. It is recorded once per Machine and delivery id, by an insert that skips a conflict, so a resend reaching any connection or instance adds nothing (ADR-0016); storing a resend is tried again first, and fails the same way. A Shot or Steam Record set aside counts as known when the server answers that Machine's `shotIndex` and `steamIndex`, whatever version an index offers, so it is not requested again; another Machine's indexes still request it. Payloads that store are still stored as sent: nothing is stripped or rewritten. An Admin, or Staff, sees how many were set aside and each one's time, type, record id and error on the Machine's page (`GET /api/machines/:id/set-aside-deliveries`), never its message; replaying and deleting them come later.

A Shot or Steam Record id must also be one the server can store and index: at most `MAX_RECORD_ID_LENGTH` (128) UTF-16 code units, without NUL (`isRecordId` in `protocol/`). Decaid's are UUIDs. The plugin neither sends nor indexes a record with another id; the server acknowledges a `shot`, `shotUpdated` or `steam` with one without storing it or closing the connection, and never requests an index entry with one. Refusing them as protocol errors would close the connection and bring them back on every reconnect.

## Mixed Decaid versions

Machines may run different supported Decaid versions, whose host capabilities and record fields vary independently of our protocol version. A missing endpoint means the collection is unavailable, not empty. Extraction and display must tolerate missing optional and unfamiliar fields without discarding the original payload. Write no fallbacks for layouts older than the oldest supported Decaid: a record missing what every supported version sends is ignored. The server logs each Shot or Steam Record it ignores this way, by its id, quoted and escaped, and what it lacks, never a field's value (`SHOTS.md`, `STEAM_RECORDS.md`). Inspect the oldest supported Decaid release and the one in question when depending on a field or host behavior; see `AI_RUNTIME_NOTES.md`.

Besides control messages (welcome, acknowledgments, backfill requests, requests for every collection afresh, and errors), the server sends only the Library's writes, one at a time to each connection that holds its Machine, is not mismatched and whose Machine is at a Location (`LIBRARY.md`, ADR-0009).

## The Loaded Recipe on the wire

Tickets #177, #189, #216 and #235 (ADR-0022) carry the Loaded Recipe without raising the protocol version (ADR-0017):

- **The Workflow's recipe.** The Loaded Recipe rides in the Workflow, in the field DYE2 and Streamline set as they apply a recipe (`DYE2_RECIPE_FIELD`, `context.extras.dye.recipeId`, read by `dye2RecipeIdOf`), the id of the tablet's record of it, which the server resolves through the tablet's map. Every `write` of the `loadedRecipe` kind carries `expected[DYE2_RECIPE_FIELD]`, that record id, and the plugin writes nothing unless the Workflow it has just read still names it there. The unload `write` names that field alone, null, which the plugin writes into the Workflow as DYE2 does; its answer's `writtenFields` names the field, or nothing where the Workflow named another recipe by then. A write that changes the profile, by DYE2's fingerprint (`dye2Fingerprint` in `protocol/`, which the server reads too), is made on the tablet as two `PUT /workflow`, and the Workflow is delivered once, after both (interim, until decentespresso/dye2#38).
- **`workflow.dye2Absent`**, optional, from #189: true while DYE2 is not there on the tablet (absent from Decaid's plugins, disabled, or not loaded for longer than twice the plugin's poll interval), so the recipe the Workflow names names no Loaded Recipe, whatever was last written there. The plugin delivers the Workflow again as it changes, where it names a recipe, and sets it on every delivery meanwhile.
- **`workflow.recipeNamedAt`**, optional, from #235: where the plugin held a Workflow change back while the recipe it names changed, as during a write of its own, when Decaid first reported the Workflow naming that recipe, in UTC. The server loads the Recipe from then, so a Shot pulled with it meanwhile is pulled with it; `observedAt` stays the latest report's time, which times the Workflow's other parts, as its edits of the Recipe.
- **`captureOnly`**, from the server: `{ type: "captureOnly", captureOnly }`, whether the Machine is a Capture-only Machine, at no Location or with sharing off, sent by its tablet's writer once it first finds where the Machine takes part after `welcome`, and whenever that changes. The plugin loads no Recipe into a Capture-only Machine's Workflow, saves nothing into its recipes, nor runs ADR-0022's workarounds there.

`workflow.loadBefore`, which #177 added for the rule on DYE2's dashboard copy, went with that rule in #216, as decentespresso/dye2#31 has DYE2's dashboard send only its own edits. The plugin delivers a Workflow change it saves into the Loaded Recipe after the recipes DYE2 saved, so the server takes in the edit first; changes of the machine's state are no longer held back.
