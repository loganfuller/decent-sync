# AI Protocol Notes

Read when changing messages, validators, authentication, delivery or backfill.

## Contract ownership

[Milestone 1's Protocol package section](https://github.com/loganfuller/decent-sync/issues/1) defines the requirements. `protocol/src/index.ts` is the single definition of wire types and runtime validators used by the plugin and server, and `protocol/src/chunking.ts` of how a message too large for one frame is sent. Ticket #5 defined the handshake: `hello`, `welcome`, `heartbeat`, `error`, the close codes in `CLOSE_CODES` and the `/sync` path. Ticket #9 adds Shot delivery, indices, requests and acknowledgments; see `SHOTS.md` for the contract and delivery behavior. Ticket #10 adds chunked messages, below. Ticket #12 adds Steam Record delivery, with the UTC time the plugin places each record at; see `STEAM_RECORDS.md`. Ticket #13 adds `workflow` and `machineState`, timed events each carrying when the plugin observed it (`observedAt`, in UTC); the server records every one's delivery id for 90 days, so a resend changes nothing, whichever instance gets it. See `WORKFLOW-AND-STATE.md`. Ticket #14 adds `collection`, the latest value of one of a tablet's collections (library, settings, paired devices) or that it is unavailable, delivered and recorded the same way; see `COLLECTIONS.md`. Ticket #79 makes `hello` require `tabletId`, the tablet's id (a UUID, `isTabletId`); see Tablet ids below. Subsequent tickets extend it; read the assigned ticket for scope.

Validators report problems by field name, never by value, because a `hello` carries the token; keep it that way, and never log frames. The only exception is a Decaid version's release numbers, which cannot hold a token. The server checks a `hello`'s protocol version before its shape, so a plugin speaking an older version is told it is too old, then a valid `hello`'s Decaid version (ADR-0017). A version refusal keeps a string `token`, so the server can show the reason on a valid token's Machine (an invalid token changes nothing). Every refusal is an `error` message followed by a close with that error's code. The plugin stops reconnecting after a bad-token, plugin-too-old, Decaid-too-old or replaced close, waits for the machine to report other hardware after a hardware-dismissed close, and retries with backoff after anything else.

Identity is settled only at `hello` (ADR-0015). The plugin reconnects with a new `hello` when the machine first reports its hardware or reports different hardware, checking `GET /machine/info` on `stateUpdate` events (at most every 5 s) and every poll interval.

Supported versions follow ADR-0017. Before v1 the protocol stays at version 1 and the server accepts only what the current plugin sends: a wire change raises no version, and a plugin from before it fails validation, as one without ticket #79's `tabletId` does, with no handling for what an older plugin sent. From v1, a change the previous release's plugin can't follow raises `PROTOCOL_VERSION`, and the server also accepts the previous release's version (`OLDEST_SUPPORTED_PROTOCOL_VERSION`); a change it already follows or can ignore, such as a field it already sends or a message it skips, needs no new version. The archived prototype's protocol was never released and is not supported.

The spec also requires unknown-field tolerance, opaque Decaid payloads, at-least-once delivery, idempotent handlers and acknowledgment after storage, where a delivery set aside counts as stored (below). It specifies whole-message chunking for any oversized message. Define those behaviors in the shared package and verify them through the simulated tablet, including raw-frame cases.

## Tablet ids

ADR-0006 keys the server's id map by tablet, so every `hello` names the tablet it comes from. Decaid gives plugins no installation id, so the plugin makes a random UUID when its `tabletId` key in Decaid's plugin storage was never written (Decaid answers `null`), writes it there, and otherwise uses the stored one (`plugin/src/tablet-id.ts`). It reads the id once per load, before its first connection; a read Decaid leaves unanswered, as it does one that fails, is given up on after 10 s and retried with the reconnect backoff, never taken for a key never written. Something other than a UUID under the key is replaced with a new id. Losing the storage only makes a tablet look new (ADR-0006). Decaid's backups hold the id only because the plugin also reads its storage through Decaid's store API (`AI_RUNTIME_NOTES.md`, Plugin storage).

The server records each tablet when it accepts a `hello`, in the same transaction, against whoever the connection resolved to, as its records are (ADR-0015): the token's Machine, or for a mismatch the reported hardware's Machine, or its Pending Machine until a Machine takes it over (`server/src/machines/tablets.ts`). Identity resolution does not change. A tablet is `tablets` (its id and when it was first seen) and `machine_tablets` (one row per tablet and Machine or Pending Machine, upserted, so connections through any instance find one row). Each row has PostgreSQL's times of its first accepted `hello` and of its last sighting, which a connection's heartbeats keep current while it holds its Machine. Each also has `last_hello`, a number from its column's sequence. Once a `hello` has recorded its tablet, with no contested work left, it takes an advisory lock every hello takes (`TABLET_ORDER_LOCK`), numbers the record under it, and holds it until it commits. Numbers therefore rise in the order hellos are accepted, whatever their holders and tokens, on any instance, and never tie, and records joined by adoption keep the higher. The lock covers only that last statement and the commit, which can still wait (as on the lock PostgreSQL takes to queue the hello's NOTIFY, or on writing its log), and hellos queued for the lock wait with it. A Machine's view lists the tablet of its record with the highest as `tablet`, its latest connection's, and the rest as `earlierTablets`; heartbeats never change that order. A heartbeat finds its row by the tablet and whoever the connection's records go to now (`recordOf`), not by a row id, since adoption may have taken a Pending Machine's row over, or joined it into its Machine's, meanwhile. The join deletes the held row and reads it in one statement, so a heartbeat it waits for is kept. A heartbeat that waited for an adoption finds no row, as its query looked for the hardware's holder before the adoption committed, so it looks again in a query of its own.

## Chunked messages

Decaid holds at most 1 MiB of a transport's frames awaiting the network, one frame or all those queued together, and its `send` resolves once a frame is queued, not once it is written (`AI_RUNTIME_NOTES.md`). `frames()` in `protocol/src/chunking.ts` sends a message whose encoding is at most `MAX_FRAME_BYTES` (256 KiB, measured as Decaid measures it: UTF-8, with envelope and JSON escaping) as one frame, and a larger one as `chunk` frames of at most that size. A chunk carries `id` (the delivery's own id, or one the plugin makes up for a message without one), `index`, `count` and `data`, the message's JSON in pieces that never split a surrogate pair. `Reassembly` puts them back together.

Every delivery waits in the plugin's one outbox (`plugin/src/outbox.ts`) until acknowledged, one awaiting acknowledgment at a time, and is sent again with the same id on the next connection if it was not. The plugin sends every message, `hello` included, through one `Sender` per connection (`plugin/src/sender.ts`). A delivery or a chunk counts against 512 KiB from when it is handed to Decaid until the server confirms it, a chunk by `chunkReceived` and a whole delivery by its `ack`; since Decaid writes frames in order, a confirmation covers every earlier frame too. `hello` and `heartbeat` are not counted and go out at once, so a large message never holds up heartbeats.

The server reassembles each connection's chunks in memory, confirms every chunk it receives with `chunkReceived`, and handles a completed message as if it had arrived whole: de-duplicated by its id, stored, then acknowledged once. A message repeated whole after its `ack` is acknowledged again, as any repeated delivery is. Chunks may arrive in any order, between other frames and more than once. A chunk that contradicts an earlier one, or that would hold more than `CHUNK_LIMITS` allow, closes the connection with `protocol_error`, and so does a message whose chunks do not decode as a whole message; nothing of either is stored or acknowledged. The limits count everything held for messages still incomplete: their ids and data, at most 16 Mi characters (1 Mi before `hello` is accepted), and their chunks, at most 1024, counting those yet to arrive from a message's first chunk on. A dropped connection's partial chunks go with it, and the plugin sends the message again whole, from its first chunk, on its next connection, whichever instance that reaches.

## Delivery ids and replays

A delivery's or chunk's `id` is at most `MAX_ID_LENGTH` (128) UTF-16 code units; the plugin's are about 30 (`Outbox.nextId`). A longer one closes the connection with `protocol_error`, naming the field and never its value, and nothing of that message is stored or acknowledged. Plugins already sent ids this short, so the limit needs no new protocol version.

Each connection remembers the deliveries it handled most recently (`HandledDeliveries` in `server/src/sync/handled-deliveries.ts`), with the request each index was answered with: at most 64, holding at most 256 Ki code units of ids, those of the requests included, forgetting the oldest first. Heartbeats keep a connection open indefinitely, so remembering every delivery would grow without bound. A delivery sent again on the connection while remembered is acknowledged without being handled again, after its index's request if it is one. One forgotten is handled again, which changes nothing: storage decides every delivery once (a Shot by its edit time, a Steam Record by its id, Workflow, machine state and collection deliveries by their recorded delivery ids), and an index is answered from what is stored by then. The plugin sends a delivery again only on a new connection, so it never relies on what a connection remembers.

## Deliveries set aside

The plugin sends one delivery at a time, oldest first, and sends an unacknowledged one again first on every connection, so a delivery the server fails to store every time it arrives would hold up everything queued behind it, and indexes and `welcome` would bring it back after every reload (ticket #60). No supported Decaid is known to send one, but PostgreSQL refuses some values Decaid's JSON can carry: a NUL (`\u0000`) in any string, which jsonb refuses with SQLSTATE 22P05 and text columns with 22021, a lone UTF-16 surrogate, which jsonb refuses with 22P02, and a value too long for an index entry, such as a Shot's recorded hardware, refused with 54000.

So when storing a `shot`, `shotUpdated`, `steam`, `workflow`, `machineState` or `collection` fails with an error that repeats for the same payload, the sync gateway sets the delivery aside and acknowledges it as stored (`SyncGateway.capture`). Those errors are PostgreSQL's class 22 (data exception), 23514 (check violation) and 54000 (program limit exceeded), read from the SQLSTATE in the cause Prisma's driver adapter gives a known request error (`repeatingFailure` in `server/src/set-aside-deliveries/repeating-failures.ts`). Every other error closes the connection with 1011 and leaves the delivery unacknowledged, as before: lost connections, socket errors, lock and transaction timeouts, deadlocks and serialization failures, and errors with no SQLSTATE or not from the database at all. `server/test/set-aside-deliveries.test.ts` simulates those with a trigger, a lock the test holds and a stand-in pooler that resets its connections.

A delivery set aside is recorded in `set_aside_deliveries` for the Machine whose token delivered it, with its type and id, its Shot's or Steam Record's id, PostgreSQL's SQLSTATE and message, PostgreSQL's time, and the message as received: its JSON text, from its frame or put back together from its chunks, escapes such as `\u0000` intact. It is recorded once per Machine and delivery id, by an insert that skips a conflict, so a resend reaching any connection or instance adds nothing (ADR-0016); storing a resend is tried again first, and fails the same way. A Shot or Steam Record set aside counts as known when the server answers that Machine's `shotIndex` and `steamIndex`, whatever version an index offers, so it is not requested again; another Machine's indexes still request it. Payloads that store are still stored as sent: nothing is stripped or rewritten. An Admin, or Staff, sees how many were set aside and each one's time, type, record id and error on the Machine's page (`GET /api/machines/:id/set-aside-deliveries`), never its message; replaying and deleting them come later.

A Shot or Steam Record id must also be one the server can store and index: at most `MAX_RECORD_ID_LENGTH` (128) UTF-16 code units, without NUL (`isRecordId` in `protocol/`). Decaid's are UUIDs. The plugin neither sends nor indexes a record with another id; the server acknowledges a `shot`, `shotUpdated` or `steam` with one without storing it or closing the connection, and never requests an index entry with one. Refusing them as protocol errors would close the connection and bring them back on every reconnect.

## Mixed Decaid versions

Machines may run different supported Decaid versions, whose host capabilities and record fields vary independently of our protocol version. A missing endpoint means the collection is unavailable, not empty. Extraction and display must tolerate missing optional and unfamiliar fields without discarding the original payload. Write no fallbacks for layouts older than the oldest supported Decaid: a record missing what every supported version sends is ignored. Inspect the oldest supported Decaid release and the one in question when depending on a field or host behavior; see `AI_RUNTIME_NOTES.md`.

Milestone 1 captures data only. The server still sends control messages (welcome, acknowledgments, backfill requests and errors); shared-library writes to tablets come later. See the spec's Out of Scope section and ADR-0009.
