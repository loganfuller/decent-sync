# AI Storage Notes

## Capture storage

Milestone 1 uses PostgreSQL through Prisma (ADR-0007 and ADR-0011). Follow [the spec's Capture and Schema outline sections](https://github.com/loganfuller/decent-sync/issues/1) for entities, identity attribution, editable Location history and idempotent storage.

Keep the Decaid record as sent, separating measurements into their own tables so lists do not load them. Extract analytics columns through optional fields. Record edits preserve existing measurements. Collections are the latest reported value per Machine in milestone 1 (`reported_collections`; an unavailable report keeps the value known), credited and handed over as Workflow events are; see `COLLECTIONS.md`. The Library is stored apart from them, as its items with their content as Decaid's record fields, each Location's state of them (whether a batch is there, its remaining weight there, the Locations offering a Bean with no batch there yet, the Grinders belonging to it, and whether a Profile is shown there), and each tablet's record of each, by tablet id; a tablet's report of its beans, bean batches, grinders or profiles is taken into it as the collection is stored; see `LIBRARY.md`.

Shots and Steam Records are stored once by their Decaid ids. Shots are credited by their recorded hardware, to a Machine or a Pending Machine, with ADR-0015's inferred fallback; Steam Records carry no hardware identity and are credited to the reporting Machine. Each record's Location is derived from its Machine's Location History at the record's time and stored beside the credit; history edits re-derive it, and neither touches the stored Decaid payload. Records deleted on a tablet stay on the server, and a tablet backfills its history on adoption. Workflow changes and machine state transitions are timed events, credited like inferred Shots: to the token's Machine, or for a mismatch to the reported hardware's Machine or Pending Machine, which hands them over. Each delivery is handled once, by its delivery id, which is recorded whether or not it changes anything and kept for 90 days; it is stored only if it differs from the latest stored for whoever it belongs to, decided under that Machine's row lock (or the hardware's lock), and the latest stored is the current one. See `WORKFLOW-AND-STATE.md`.

A delivery whose storage fails in a way that would repeat, such as one with a NUL in a string, is set aside in `set_aside_deliveries`, its message kept as received as text, which can hold the escapes jsonb refuses, and acknowledged as stored; see `AI_PROTOCOL_NOTES.md`, Deliveries set aside.

## Writing a migration

The server migrates as it starts, while the latest release may still serve from the same database (ADR-0025). `runMigrations` (`server/src/migrations.ts`) holds the advisory lock Prisma takes (72707369) on a connection of its own, trying it each second however long another instance holds it, and runs `prisma migrate deploy` with Prisma's own lock off (`PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK`). The latest release's instances take Prisma's lock and give up after 10 s, so they are kept out until it lets go, once migrated. The connection sets `idle_session_timeout` to 15 s and `statement_timeout` to 5 s, and the server queries it every 5 s while Prisma migrates, so PostgreSQL drops the lock of a holder whose host vanished within 20 s of its last query. TCP keepalives wouldn't: a proxy between the two, such as PgBouncer or the one fly.io puts in front of its Managed Postgres, answers their probes itself. Holding the lock, the server records as rolled back any migration Prisma left unfinished (`finished_at` and `rolled_back_at` both null in `_prisma_migrations`), both as it starts and as a migration fails, before exiting: past one, every later `migrate deploy` refuses to run (P3009), the latest release's included.

Every migration after `20261025200000_wake_schedule_edits`, the latest at v1.2.0, is in one of two forms, which `server/test/migration-format.test.ts` checks:

- **One transaction that sets `lock_timeout` locally:** `BEGIN; SET LOCAL lock_timeout = '5s'; ... COMMIT;`. Prisma 7.4 and later run a file's statements one at a time when they can parse it, so a file is atomic only as an explicit transaction. It waits at most 5 s for a lock the running release holds, so that release's queries queue behind it no longer, and then gives up whole, failing the deploy.
- **An index on a large table built concurrently,** in a migration of its own: `SET lock_timeout = '5s'; DROP INDEX IF EXISTS "x"; CREATE INDEX CONCURRENTLY "x" ...;`. The plain drop removes an invalid index a failed attempt left. Prisma can't split out `DROP INDEX CONCURRENTLY`, and would run the file in one transaction, which those statements refuse. The build also waits, under the same `lock_timeout`, for every query in the database holding a snapshot older than its own, so one that runs longer fails it, and the deploy is tried again. Such a query may be the running release's, or the wait for Prisma's lock of a previous-release instance restarting meanwhile: PostgreSQL keeps that query waiting, even once Prisma has given up after its 10 s, until the lock is free. That is why the server tries the lock each second rather than waiting in one query.

A migration leaves the schema the latest release's code needs:

- It adds no constraint, `NOT NULL` column without a default, or narrower type the latest release's writes would break: a delivery it then failed to store would be set aside and lost.
- A change the latest release would break on takes two releases. Add the new form beside the old and write both. Read the old form, or both, while the latest release may still write it. Remove the old in a later release, filing an issue for that removal when adding the new form.
- A large change to data runs in the server, in batches in the background, as the delivery id cleanup does (`server/src/machines/delivery-id-cleanup.ts`). The migration that removes the old form first checks that it is done, and otherwise fails, naming the release to run until it is.

A release that can't run beside the previous one, made only with the owner's approval (ADR-0025's escape hatch), is deployed with every instance stopped, so its migration may also change a small amount of data in place, still in the transactional form: `20261029000000_recipes_shown_by_slot` fixes what 1.5.0 left of Recipes' `showOnDashboard`.

A migration that fails is recorded as rolled back, and the server exits naming it; the next start applies it again. Prisma's output may not say why: when a statement in a transaction fails, Prisma reports "current transaction is aborted", from its attempt to record the failure, and PostgreSQL's log has the cause. A killed instance's migration ends only when PostgreSQL ends its dead connection: a transactional one within its `lock_timeout` and the idle-in-transaction timeout, some 35 s, while the tables it locked wait, and a concurrent index build runs to its end. Until then a retry fails on its lock. An instance killed between a migration's commit and Prisma's record of it leaves an applied migration unfinished, and every retry fails on what it creates already existing; the server's message, given for a migration tried before, says to check it was applied whole and then run `npx prisma migrate resolve --applied <name>` with that release, in its server directory (`/app/server` in the Docker image). Prisma's CLI runs in a process group of its own, with its schema engine. The server stops the group, and fails, if the lock's connection is lost while Prisma migrates, as another instance may then take the lock, or if it gets SIGINT, SIGTERM or SIGHUP. It also stops the group once the CLI exits, before recording anything or letting go of the lock, since a CLI that died may have left its engine migrating. Killed alone, rather than with its host or container, by SIGKILL or another signal it doesn't pass on, the server leaves them to finish the migration without the lock.

fly.io kills a new VM that hasn't passed its health check within `[deploy] wait_timeout`, and the server listens only once migrated, so a deploy's `wait_timeout` is above the time its migrations take plus the wait for another instance's lock, such as while another new instance migrates first. A migration expected to take long, such as a concurrent build on a large table, names the `wait_timeout` its release needs in the upgrade notes.

Seam 1 tests of migrations stage the next release's in a copy of the change's built server (`stageMigrations` in `server/test/support/staged-migrations.ts`, run with `startTestServer({ buildDir })`), as `server/test/migrations.test.ts` does.
