# Skins take a Workflow change made elsewhere, and the plugin sets nothing of Streamline's

Streamline, a skin for Decaid, remembers what the barista last set for steam time, flow, temperature and milk stop, hot water volume and temperature, and flush time, in Decaid's store under its namespace `streamline-app`. Up to v0.2.13, whenever the Workflow held another value, whoever set it, Streamline pushed the remembered one back through `PUT /workflow` (`resyncIfDrifted` in `streamline-js:src/modules/api.js`). So when the plugin wrote a Location's settings to a Streamline tablet (ADR-0014, superseded since), Streamline put its own value back, the plugin reported that as the tablet's edit, and it became the Location's value, written to its other Machines. Two Streamline tablets remembering different values would undo each other's in turn. The same holds for whatever else the plugin writes into the Workflow, as a Loaded Recipe's steam, hot water and flush settings (ADR-0022).

This ADR first had the plugin set the value Streamline remembers of each setting it was about to write, then write the Workflow, the order Streamline's own setters use (`plugin/src/streamline.ts`, from #130 until 2026-10-14). We rejected asking Streamline to take a Workflow change made elsewhere as the new value, as its resync then counted "a value set from another device" as drift to undo, and as with DYE2 (ADR-0005) we would not tie this project to someone else's release. We also rejected having the server ignore a change back to the value it overwrote, made just after its write: it can't tell such a revert from a barista's change, and the tablet would keep the other value anyway.

## The rule for skins

Where the plugin writes into the Workflow, as a Machine's Loaded Recipe's values (ADR-0022), the Workflow holds the current value. A skin may remember what the barista last set, but when the Workflow changes through something other than the skin itself, it takes that as the new value rather than writing its own back. A skin built for a Decent Sync deployment, such as a Location's own custom skin, follows this rule and needs nothing set for it. When it applies a recipe, it names it in the Workflow (`context.extras.dye.recipeId`), as Streamline's DYE strip does, so the Machine's Loaded Recipe follows (ADR-0022).

## Streamline follows the rule

Streamline made that change itself. Since decentespresso/streamline-js#109 (`b13cffd`, merged 2026-10-13), it adopts a Workflow value that differs from the one it remembers: it writes the Workflow's value into its store and pushes nothing back (`decideResync` in `streamline-js:src/modules/resync-policy.js`, called by `resyncIfDrifted`). It still pushes its own write that has not reached the Workflow yet, and the value it remembers for a setting the Workflow lacks. It ignores a differing value seen within 10 s of its own push, rather than adopting it. Since decentespresso/streamline-js#132 and decentespresso/streamline-js#137, it also shows a steam flow, milk stop or flush time changed elsewhere, as it reads the Workflow back after its own writes, on a machine state change and every 20 s. Both are in Streamline v0.2.14 (`3a4bd23`, released 2026-10-15), its first release after v0.2.13, and in every build since, v0.2.21, the supported floor, included.

Decent Sync supports only Streamline releases with this change, from v0.2.21 (ADR-0017). So the plugin sets none of the values Streamline remembers for what it writes.

Streamline never compares the steam temperature it remembers (`last-steam-temp`) with the Workflow. Its heater switch (`setSteamHeaterEnabled`, which descaling uses) turns steam back on only from a Workflow whose steam temperature is 0, so a steam temperature set elsewhere while steam is on stays (decentespresso/streamline-js#143, `98b6b90`). While Streamline's own DYE2 switch is on (`streamline.dye2Enabled`, off by default), it turns it back on at the steam temperature, 135 °C or more, of the recipe DYE2's selection names, and at the one it remembers only where that names none; with that switch off, always at the one it remembers (`steamHeaterFor` in `streamline-js:src/modules/api.js`, since decentespresso/streamline-js#156, `19d3f01`, in v0.2.15 and `cec5664`). DYE2 derives that selection from the recipe the Workflow names (ADR-0022), and the tablet's record of a Loaded Recipe holds the Recipe's steam temperature, so with that switch on, steam comes back on at the Recipe's, one edited while it was off included. A steam time of 0 is no timer, and turns nothing on or off (ADR-0022). Streamline refreshes the value it remembers when a barista sets the steam temperature in it, or switches steam off, when it keeps the Workflow's.

Three ways of turning steam on do not take the recipe's. The heater switch above, with Streamline's DYE2 switch off, takes the one Streamline remembers, while a Recipe loaded through DYE2's own dashboard stays loaded. The heater switch on its Settings › Calibration › Steam page (`setSteamHeaterOn` in `streamline-js:src/settings/settings.js`) turns steam back on at the temperature that page last switched off, held in memory, or 150 °C, which its Save then writes into the Workflow, and never reads `last-steam-temp`. Auto Steam, choosing a pitcher while the heater is off, takes the one Streamline remembers (`createAutoSteamSession` in `streamline-js:src/modules/auto-steam-session.js`). With a Recipe loaded, Decent Sync turns steam back on at the Loaded Recipe's steam temperature itself in each, as turning it off is no edit, writing it into the Workflow before it has DYE2 save the change, so the temperature steam came back at reaches no Recipe (ADR-0022, Steam on and off, #374).

Since #173, the steam, hot water and flush settings a Recipe holds follow the Machine's Loaded Recipe, and the plugin writes them into the Workflow (ADR-0022). Streamline's own steam settings, as each profile's saved steam time and flow (`streamlineProfileOverrides`), which it sends on a switch to that profile and on a wake with a wake profile set, are that Machine's; one that reaches the Workflow while a Recipe stays loaded is saved into it, as any change is (ADR-0022).

From #173 until 2026-10-28 (#186), the plugin also set `last-steam-temp` to the Recipe's steam temperature with each load and Loaded Recipe write carrying one, written into the Workflow or left out of one whose steam is off, as an interim stand-in for decentespresso/streamline-js#156 (`keepStreamlineSteamTemperature`). It went on 2026-10-28, as every supported build has that fix. The key still matters where Streamline's DYE2 switch is off, and to Auto Steam's pitcher choice with the heater off; the owner chose to accept those cases, beside the Settings › Calibration › Steam switch, which never reads it, as a gap ADR-0022 recorded, rather than keep the workaround: steam coming back on at another temperature is an edit of the Recipe only because Decent Sync saves every change, so a rule of its own closes it, which #374 made.

## Consequences

- **No adapter for any other skin.** Streamline v0.2.13 or earlier, or another skin that pushes remembered values back, undoes what the plugin writes into its Machine's Workflow, as a Loaded Recipe's steam, hot water and flush settings, and its own value then becomes that Machine's edit of the Recipe. Decent Sync supports no such skin (ADR-0017).
- **Nothing in Streamline's namespace.** The plugin reads and sets none of Streamline's keys in Decaid's store (`streamline-app`).
- **Narrow windows remain.**
  - The plugin reads the Workflow, then writes what it still holds as the server expects. A change made on the tablet in the moments between is overwritten, and its Workflow event, held until the write's answer is queued, carries only the Workflow after it, so the server never sees that change.
  - A Workflow change the plugin makes within 10 s of a barista's change in Streamline of the same steam time or flow, milk stop, or hot water volume or temperature, the setters that go through `pushRemembered`, is ignored as a stale echo of that change: Streamline's store keeps the barista's value until its next comparison after the window, as on its next load, adopts the Workflow's. Nothing is pushed, so the Workflow keeps the plugin's value meanwhile.
- **A barista's own change is still pushed, for most settings, and wins.** If Decaid refuses a change of one of those settings made in Streamline, as while the machine is off, Streamline keeps it pending on that device and pushes it again at its next comparison, as on the machine's echo of a write of the plugin's once it is back. That is the barista's change, over what the plugin wrote meanwhile; of a setting the Loaded Recipe holds, it is the Machine's edit of the Recipe, saved into it as any change is.
