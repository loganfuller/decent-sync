# Skins take a Workflow change made elsewhere; the plugin sets at most Streamline's steam temperature

Streamline, a skin for Decaid, remembers what the barista last set for steam time, flow, temperature and milk stop, hot water volume and temperature, and flush time, in Decaid's store under its namespace `streamline-app`. Up to v0.2.13, whenever the Workflow held another value, whoever set it, Streamline pushed the remembered one back through `PUT /workflow` (`resyncIfDrifted` in `streamline-js:src/modules/api.js`). So when the plugin wrote a Location's settings to a Streamline tablet (ADR-0014, superseded since), Streamline put its own value back, the plugin reported that as the tablet's edit, and it became the Location's value, written to its other Machines. Two Streamline tablets remembering different values would undo each other's in turn. The same holds for whatever else the plugin writes into the Workflow, as a Loaded Recipe's steam, hot water and flush settings (ADR-0022).

This ADR first had the plugin set the value Streamline remembers of each setting it was about to write, then write the Workflow, the order Streamline's own setters use (`plugin/src/streamline.ts`, from #130 until 2026-10-14). We rejected asking Streamline to take a Workflow change made elsewhere as the new value, as its resync then counted "a value set from another device" as drift to undo, and as with DYE2 (ADR-0005) we would not tie this project to someone else's release. We also rejected having the server ignore a change back to the value it overwrote, made just after its write: it can't tell such a revert from a barista's change, and the tablet would keep the other value anyway.

## The rule for skins

Where the plugin writes into the Workflow, as a Machine's Loaded Recipe's values (ADR-0022), the Workflow holds the current value. A skin may remember what the barista last set, but when the Workflow changes through something other than the skin itself, it takes that as the new value rather than writing its own back. A skin built for a Decent Sync deployment, such as a Location's own custom skin, follows this rule and needs nothing set for it. When it applies a recipe, it also selects it in DYE2, as Streamline's DYE strip does, so the Machine's Loaded Recipe follows (ADR-0022).

## Streamline follows the rule, but for its steam temperature

Streamline made that change itself. Since decentespresso/streamline-js#109 (`b13cffd`, merged 2026-10-13), it adopts a Workflow value that differs from the one it remembers: it writes the Workflow's value into its store and pushes nothing back (`decideResync` in `streamline-js:src/modules/resync-policy.js`, called by `resyncIfDrifted`). It still pushes its own write that has not reached the Workflow yet, and the value it remembers for a setting the Workflow lacks. It ignores a differing value seen within 10 s of its own push, rather than adopting it. Since decentespresso/streamline-js#132 and decentespresso/streamline-js#137, it also shows a steam flow, milk stop or flush time changed elsewhere, as it reads the Workflow back after its own writes, on a machine state change and every 20 s. Both are in Streamline v0.2.14 (`3a4bd23`, released 2026-10-15), its first release after v0.2.13, and in streamline-js `main` at `c006dac`, the supported floor.

Decent Sync supports only Streamline builds with this change, from `c006dac` (ADR-0017). So the plugin sets none of the values Streamline remembers for what it writes, but the steam temperature (below). Streamline never compares the steam temperature it remembers (`last-steam-temp`) with the Workflow, but since decentespresso/streamline-js#143 (`98b6b90`, before `c006dac`) it sends it only with a steam time that turns steam back on from a Workflow whose steam temperature is 0 (`steamHeaterFor`): so a steam temperature set elsewhere while steam is on stays. It refreshes the value when a barista sets the steam temperature in it, or switches steam off, when it keeps the Workflow's.

Since #173, the steam, hot water and flush settings a Recipe holds follow the Machine's Loaded Recipe, and the plugin writes them into the Workflow (ADR-0022). Streamline's own steam settings, as each profile's saved steam time and flow (`streamlineProfileOverrides`), which it sends on a switch to that profile and on a wake with a wake profile set, are that Machine's; DYE2 records one that reaches the Workflow while a Recipe stays loaded into it, as any change (ADR-0022).

## Interim: Streamline's remembered steam temperature

A Recipe's steam temperature is written into the Workflow on a load and with each Loaded Recipe write, but never into a Workflow whose steam is off, as it would turn steam on (ADR-0022). Streamline turns steam back on at the temperature it remembers (`last-steam-temp`), which is out of date where the Recipe's changed while steam was off there, as by an edit made on another Machine meanwhile, and DYE2 would record it into the Recipe, undoing that edit (decentespresso/streamline-js#156).

So with each load and each Loaded Recipe write carrying a steam temperature of 135 °C or more (`STEAM_ON_FROM`), whether or not it writes it into the Workflow, the plugin sets `last-steam-temp` to it (`keepStreamlineSteamTemperature` in `plugin/src/streamline.ts`): a store write, no Workflow write, and only where the key already holds a number, so a tablet that never ran Streamline gets no Streamline keys. It ignores a lower temperature, as Streamline keeps no other, and a key already equal. Streamline never compares the key with the Workflow, so it is set after the Workflow write, not before as the adapter did, and a refused write leaves nothing to set back. Streamline then turns steam back on at the Recipe's temperature, and the server needs no rule for steam coming back on. We rejected leaving it to Streamline: until it re-arms steam with the selected recipe's temperature, a Recipe's steam temperature changed while a Machine's steam is off would be undone as it is turned back on there.

## Consequences

- **No adapter for any other skin.** Streamline v0.2.13 or earlier, or another skin that pushes remembered values back, undoes what the plugin writes into its Machine's Workflow, as a Loaded Recipe's steam, hot water and flush settings, and its own value then becomes that Machine's edit of the Recipe. Decent Sync supports no such skin (ADR-0017).
- **One value in Streamline's namespace.** The plugin reads and sets only `last-steam-temp`, and only for a load or Loaded Recipe write carrying a steam temperature. A failure to read or set it is logged, and costs only this: Streamline may put its own temperature back the next time it turns steam back on. Decaid's store creates a namespace a request names where it is missing (`HiveStoreService` in `decaid:lib/src/services/storage/hive_store_service.dart`), so such a write on a tablet that never ran Streamline leaves an empty `streamline-app`, which its Decaid backups then include. Nothing is ever set in it.
- **Narrow windows remain.**
  - The plugin reads the Workflow, then writes what it still holds as the server expects. A change made on the tablet in the moments between is overwritten, and its Workflow event, held until the write's answer is queued, carries only the Workflow after it, so the server never sees that change.
  - A Workflow change the plugin makes within 10 s of a barista's change in Streamline of the same steam time or flow, milk stop, or hot water volume or temperature, the setters that go through `pushRemembered`, is ignored as a stale echo of that change: Streamline's store keeps the barista's value until its next comparison after the window, as on its next load, adopts the Workflow's. Nothing is pushed, so the Workflow keeps the plugin's value meanwhile.
- **A barista's own change is still pushed, for most settings, and wins.** If Decaid refuses a change of one of those settings made in Streamline, as while the machine is off, Streamline keeps it pending on that device and pushes it again at its next comparison, as on the machine's echo of a write of the plugin's once it is back. That is the barista's change, over what the plugin wrote meanwhile; of a setting the Loaded Recipe holds, it is the Machine's edit of the Recipe, as DYE2 records it.
- **Upstream ask.** Streamline sends the remembered steam temperature only when turning steam back on since decentespresso/streamline-js#143. It is to re-arm steam with the selected recipe's steam temperature (decentespresso/streamline-js#156). Then the plugin sets nothing of Streamline's.
