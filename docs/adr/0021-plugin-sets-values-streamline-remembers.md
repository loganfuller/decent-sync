# Skins take a Workflow change made elsewhere; the plugin sets only Streamline's steam temperature

Streamline, a skin for Decaid, remembers what the barista last set for steam time, flow, temperature and milk stop, hot water volume and temperature, and flush time, in Decaid's store under its namespace `streamline-app`. Up to v0.2.13, whenever the Workflow held another value, whoever set it, Streamline pushed the remembered one back through `PUT /workflow` (`resyncIfDrifted` in `streamline-js:src/modules/api.js`). So when the plugin wrote a Location's settings to a Streamline tablet (ADR-0014), Streamline put its own value back, the plugin reported that as the tablet's edit, and it became the Location's value, written to its other Machines. Two Streamline tablets remembering different values would undo each other's in turn.

This ADR first had the plugin set the value Streamline remembers of each setting it was about to write, then write the Workflow, the order Streamline's own setters use (`plugin/src/streamline.ts`, from #130 until 2026-10-14). We rejected asking Streamline to take a Workflow change made elsewhere as the new value, as its resync then counted "a value set from another device" as drift to undo, and as with DYE2 (ADR-0005) we would not tie this project to someone else's release. We also rejected having the server ignore a change back to the value it overwrote, made just after its write: it can't tell such a revert from a barista's change, and the tablet would keep the other value anyway.

## The rule for skins

On a Machine that shares these settings, the Workflow holds the current value. A skin may remember what the barista last set, but when the Workflow changes through something other than the skin itself, it takes that as the new value rather than writing its own back. A skin built for a Decent Sync deployment, such as a Location's own custom skin, follows this rule and needs nothing set for it. When it applies a recipe, it also selects it in DYE2, as Streamline's DYE strip does, so the Machine's Loaded Recipe follows (ADR-0022).

## Streamline follows the rule, but for its steam temperature and each profile's steam settings

Streamline made that change itself. Since decentespresso/streamline-js#109 (`b13cffd`, merged 2026-10-13), it adopts a Workflow value that differs from the one it remembers: it writes the Workflow's value into its store and pushes nothing back (`decideResync` in `streamline-js:src/modules/resync-policy.js`, called by `resyncIfDrifted`). It still pushes its own write that has not reached the Workflow yet, and the value it remembers for a setting the Workflow lacks. It ignores a differing value seen within 10 s of its own push, rather than adopting it. Since decentespresso/streamline-js#132 and decentespresso/streamline-js#137, it also shows a steam flow, milk stop or flush time changed elsewhere, as it reads the Workflow back after its own writes, on a machine state change and every 20 s. Both are in Streamline v0.2.14 (`3a4bd23`, released 2026-10-15), its first release after v0.2.13, and in streamline-js `main` at `c006dac`, the supported floor.

Decent Sync supports only Streamline builds with this change, from `c006dac` (ADR-0017). So the plugin no longer sets the values Streamline remembers, but one. Streamline never compares the steam temperature it remembers (`last-steam-temp`) with the Workflow, yet sends it with a steam time other than 0 that turns steam back on, from a Workflow whose steam temperature is 0 (`steamHeaterFor`; up to v0.2.14 with every steam time other than 0, until decentespresso/streamline-js#143): on a barista's steam time change, a profile or favourite switch carrying a saved steam time, its own retry of a pending or missing steam time (`resyncIfDrifted`, `resyncSteamFromStore`), or turning the steam heater back on after descaling. It refreshes the value only when a barista sets the steam temperature in it, or switches steam off. So once the plugin has written a Location's steam temperature into a tablet's Workflow, Streamline on that tablet would put its own back the next time steam is turned back on there, and it would become the Location's, on DE1s and Bengles alike.

So once Decaid has taken a steam temperature the plugin wrote into the Workflow, the plugin sets `last-steam-temp` to it (`keepStreamlineSteamTemperature` in `plugin/src/streamline.ts`). It sets it only to a temperature that turns steam on (at least 135 °C, `STEAM_ON_FROM`), as Streamline keeps no other, and only where the key holds a number, so a tablet that never ran Streamline gets no Streamline keys. Streamline never compares the key with the Workflow, so it is set after the Workflow write, not before as the adapter did, and a refused write leaves nothing to set back. We rejected leaving it to Streamline: until it adopts the steam temperature too, which is asked upstream, a Location's steam temperature changed anywhere but on the tablet would be undone by the first steam time change on any other Streamline tablet.

Streamline also keeps a steam time and flow for each profile, in Decaid's store under `streamlineProfileOverrides` (`OVERRIDE_KEYS` in `streamline-js:src/modules/profile-overrides.js`), saved there whenever a barista changes either on the main page (`saveContextToActiveProfile`). It sends them on every switch to that profile, from a favourite or the profile selector, and on every wake from sleep with a wake profile set (`applySavedSteamSettings` in `src/modules/profileManager.js`, called by `loadProfileForWake`), and never takes a Workflow change into them. Such a switch is a change made on that tablet, so the plugin reports it, and it becomes the Location's: a Location's steam time changed elsewhere is undone by the next switch to a profile that saved another, on any of its Streamline tablets, as when they wake in the morning. The plugin does not set these, as a profile's own steam settings are a barista's choice to apply, and they are not one value but one per profile. Its Auto steam mode, with the Auto Steam Calculator extension, likewise keeps the steam settings it found on entering it (`auto-steam-session.js`), and writes them back on leaving it.

## Consequences

- **Profiles' steam settings override the Location's.** A Location whose tablets run Streamline with per-profile steam times, or a wake profile, has its steam time and flow set by the last profile switched to on any of them. Turning sharing off on such a Machine, or saving no steam settings in its profiles, avoids it. #131's warning would name such Machines.
- **No adapter for any other skin.** Streamline v0.2.14 or earlier, or another skin that pushes remembered values back, undoes its Location's changes on its Machine and shares its own. Such a Machine's settings sharing needs to be turned off (ADR-0014). #131 tracks warning about such Machines.
- **One value in Streamline's namespace.** The plugin reads and sets only `last-steam-temp`, and only for a settings write carrying a steam temperature. A failure to read or set it is logged, and costs only this: Streamline may put its own temperature back with its next steam time. Decaid's store creates a namespace a request names where it is missing (`HiveStoreService` in `decaid:lib/src/services/storage/hive_store_service.dart`), so such a write on a tablet that never ran Streamline leaves an empty `streamline-app`, which its Decaid backups then include. Nothing is ever set in it.
- **Narrow windows remain.**
  - The plugin reads the Workflow, then writes the settings it still holds as the server expects. A change made on the tablet in the moments between is overwritten with the Location's value, and its Workflow event, held until the write's answer is queued, carries only the Workflow after it, so the server never sees that change.
  - Streamline's sending of a steam time in the moments between the plugin's Workflow write and its setting of the steam temperature still sends the old temperature: a barista's change, or Streamline's own retry of a pending steam time, which the machine's echo of the plugin's write sets off, as when a steam time refused while the machine was off is retried once it is back.
  - If Decaid applies the Workflow write but the plugin hears no answer, the write is refused and the key is never set, until the Location's steam temperature next changes.
  - Streamline's settings page writes the whole of the steam settings as it loaded them. A barista's change there to one, on a page loaded before a Location change, writes back the others as they were.
  - A Workflow change the plugin makes within 10 s of a barista's change in Streamline of the same steam time or flow, milk stop, or hot water volume or temperature, the setters that go through `pushRemembered`, is ignored as a stale echo of that change: Streamline's store keeps the barista's value until its next comparison after the window, as on its next load, adopts the Workflow's. Nothing is pushed, so the Workflow keeps the plugin's value meanwhile.
- **A barista's own change is still pushed, for most settings, and wins.** If Decaid refuses a change of one of those settings made in Streamline, as while the machine is off, Streamline keeps it pending on that device and pushes it again at its next comparison, as on the machine's echo of the Location's settings written once it is back. That is the barista's edit, and becomes the Location's, over a Location change made since. Streamline's steam temperature and flush setters mark nothing pending, so a refused change of either is not pushed again. A refused flush time is not even kept, as `updateFlushValue` keeps it only once the Workflow took it.
- **Upstream ask.** Streamline sends the remembered steam temperature only when turning steam back on since decentespresso/streamline-js#143. It is to re-arm steam with the selected recipe's steam temperature (decentespresso/streamline-js#156). Then the plugin sets nothing of Streamline's. A profile's steam settings are a separate question for Streamline: whether a switch to a profile should change steam settings a Location shares.
