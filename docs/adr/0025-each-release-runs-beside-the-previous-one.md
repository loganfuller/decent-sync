# Each release runs beside the previous one

An upgrade takes nothing offline. Release N works beside release N-1 wherever the two meet: as two server instances on one database, with N's migrations applied under N-1's code, as either release's plugin connected to either release's server, and as a page of the management interface loaded from one release talking to a server of the other. It never has to work beside N-2. Several instances are upgraded by starting the new release beside the old and moving traffic over, and no release asks for a step that stops service: no stopped server, no recreated database, nothing its upgrade notes ask to be redone. The one step left by hand is updating tablets before a release raises the Decaid, DYE2 or Streamline minimum (ADR-0017), which happens while everything runs. Both directions matter for the plugin: Decaid installs each plugin release within 12 hours, whatever its server runs, so a plugin meets the previous release's server as well as the next one's.

- **The database.** A change N-1 would break on is made over two releases. N adds the new form beside the old and keeps both in step, and a later release removes the old once no release still running reads it. Migrations change the schema only, quickly. Each one gives up rather than queue for a lock (`lock_timeout`), and builds an index on a large table concurrently, because it runs while N-1 serves, and a new instance answers its health check only once it has migrated. A large change to data, such as rewriting Shots' measurements, is made by the new release's server in batches in the background, as the delivery id cleanup works, and the release that removes the old form waits for it to finish.
- **The wire.** `hello` and `welcome` carry a wire revision, a whole number. A peer that sends none is at revision 1, the wire of 1.2.0. The first change to the wire after a release raises it by one, and later changes before the next release share that number. A message, or a value the other side would refuse, that is new in a revision is sent only to a peer at that revision or later. The server refuses a plugin more than one revision behind its own with `plugin_too_old`, which the Machine's page shows. So once the wire has moved on to a later revision, every peer within the window has the earlier one, and its checks are deleted. A release that leaves the wire alone keeps them, as a plugin two releases behind is then still only one revision behind. The protocol version stays 1, and a message of a type a side doesn't know still closes the connection.
- **Between instances.** `NOTIFY` payloads follow the same rule: N reads what N-1 sends and sends nothing N-1 misreads. N-1 never listens on a channel new in N, so whatever it announces may wait until no instance of N-1 is left.
- **The management interface.** The REST API serves N-1's pages. Every response names the server's release. A page reloads itself at its next navigation once that differs from its own release, or once loading one of its chunks fails, since a server of another release doesn't have them. It never reloads in the middle of a form.
- **Checks.** CI holds every pull request and every push to `main` to the latest release. That release's whole server test suite runs against databases migrated by the change, as CI migrates PostgreSQL's `template1`, from which each test database is made. A mixed-versions suite runs that release's plugin against the change's server, the change's plugin against that release's server, and both servers as two instances on one database. Both checks are required.
- **The escape hatch.** A release may break this rule only with the owner's approval, never on an agent's judgment. It bumps the major version. Its upgrade notes open by saying it can't be deployed without downtime, and how to deploy it: stop every instance, then start the new release. It loses no data its notes don't name. The pull requests that make the break carry the `breaking-release` label, which only the owner applies, and which skips the two checks.
- **Deploying.** Deploys stay by hand. A plugin more than one release ahead of its server falls outside the window, and tablets take each plugin release within 12 hours. So each release is deployed before the next is tagged (the README's Releasing section), and a self-hoster keeps their server within one release of the newest. A server that has skipped a release can't be upgraded side by side: it is stopped first, or taken up one release at a time.
- **fly.io.** The deployment the README describes runs two machines in one region, which fly.io places on separate hosts, and deploys them blue-green. fly.io starts a new machine beside each old one, moves traffic once they all pass the health check, then destroys the old ones, whose tablets reconnect within about a second. Roux's staging keeps one machine, which a blue-green deploy pairs with a new one only for the switch. One instance, as in the Docker Compose example, still restarts to upgrade, for a few seconds.

## Considered Options

- **Stopping every instance to upgrade**, as ADR-0016 and ADR-0017 asked. It needs no compatibility work, but each deploy is an outage: tablets hold their deliveries until it ends and the management interface is down. Rejected: the owner wants no outages.
- **fly.io's rolling deploys**, replacing one machine at a time. They need the same compatibility, but both releases serve side by side for minutes, so a page or a tablet may reach either one on each request. A blue-green deploy moves traffic over once. Rolling deploys still work, for anyone who runs them.
- **A list of features in `hello` and `welcome`.** It suits peers that each implement a different subset. Here there are two, built from one repo, each release's wire a superset of the last, so one number says the same.
- **Checking the release version**, which `hello` already carries as `pluginVersion`. Staging runs unreleased `main` builds, which report the last release's version, so their new features would be withheld from each other.
- **Raising the protocol version.** A 1.2.0 server refuses a `hello` of a newer protocol version, so every plugin that updated would be cut off until its server was upgraded.
- **Ignoring messages of an unknown type.** A missing check would then fail quietly, and a message awaiting an answer would never be answered. The checks find a missing one before a release instead.
- **Deploying releases automatically.** It could be done within the 12 hours, but deploys stay by hand for now.
- **A wider window**, such as N-2. Every change would carry its old forms longer, and nothing needs it while tablets update within 12 hours.

## Consequences

- **ADR-0016 and ADR-0017 are amended.** During an upgrade, instances of two releases share a database. Decent Sync supports the previous release of its own plugin and server beside the current one, and migrates its database in place.
- **Every change to the database or the wire costs more.** A removal or rename takes two releases. Each new message needs a check where it is sent, deleted once the wire moves on to a later revision.
- **What is new in N works only between peers of N.** During an upgrade, and until every tablet has the new plugin, a new feature may be missing wherever a peer of N-1 is involved. What N-1 did keeps working.
- **In flight at a switch.** A Settings Edit whose connection closes comes back not confirmed (ADR-0023), a Live View stream reconnects by itself (ADR-0024), and a request in flight on an old instance may fail once. A stopping instance takes no new request and finishes those it has under way.
- **The database stays one primary.** A failover to a replica takes the database away for some seconds, which no deploy hides: requests fail, and tablets keep their deliveries until it is back. The server rides through its database restarting, which CI tests.
- **The first release under this rule** works beside 1.2.0, which has no wire revision, so its first change to the wire is checked against revision 1 like any later one.
