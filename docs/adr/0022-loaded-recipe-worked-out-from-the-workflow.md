# A Machine's Loaded Recipe is the recipe its Workflow names, and every change on the Machine is saved into it

A Recipe is the day's dial for one roast, which baristas keep current through the day. When a barista on one Machine moves the Brazil's grind from 2.4 to 2.5, every other Machine with the Brazil loaded has to take that at once: the grinder is physically at 2.5, and their next Shots would otherwise record 2.4. The owner also counts which Recipe a Machine has loaded as part of its state, for analytics.

## What DYE2 and Streamline do

DYE2 v0.1.33 and Streamline v0.2.21, the supported floor (ADR-0017), name the recipe a Workflow is dialled in to in the Workflow itself, and keep no selection of their own (decentespresso/dye2#36). What DYE2 v0.1.32 does otherwise than v0.1.26 is recorded in `server/test/fixtures/decaid/dye2-v0.1.32/`, and what v0.1.33 and Streamline v0.2.21 do otherwise again in `server/test/fixtures/decaid/dye2-v0.1.33/`.

- **The Workflow's recipe.** `context.extras.dye.recipeId` holds the id of DYE2's record of the recipe being dialled in, or null for none, which DYE2 reads as text (`recipeIdOf`). DYE2's dashboard, its Select Recipe page and Streamline's DYE strip set it as they apply a recipe, in the same `PUT /workflow` as the recipe's values (`applyRecipe` and `recipeIdPatch` in `streamline-js:src/modules/dyeStrip.js` and `dye-selection.js`). Decaid copies it onto every Shot pulled with that Workflow, offline ones included.
- **When it is cleared.** DYE2 clears it, by `PUT /workflow` of `recipeId: null`, once the Workflow's profile moves off the one it held when that id first appeared, whatever moved it (`workflowChanged` in `dye2:dye2-plugin/src/plugin.ts`, `idProfileChanged` in `dye2:dye2-plugin/src/utils/workflow-record.ts`), even where the same write names the same id, but where the profile that arrives is the recipe's own, as applying it again after its profile changed sends, which it takes as the new baseline (`recipeProfileChanged`, decentespresso/dye2#38, from v0.1.27). It tells a profile by its fingerprint (`profileFingerprint`): the title, tank temperature and steps, but each step's temperature, and a step limiter of value 0 read as none, so neither a brew temperature nor a yield Streamline writes into the profile's target weight changes it (decentespresso/dye2#18, #32). The fingerprint sorts every object's keys (`sortKeysReplacer`, decentespresso/dye2#43, from v0.1.33), so the profile a record holds is the Workflow's whatever key order each holds it in: Decaid's own, or PostgreSQL's `jsonb` order, in which Decent Sync's server writes a record. So applying a Recipe again after its Profile changed keeps it named, and so does one `PUT /workflow` of the record's profile naming the same id, as the plugin writes one (`dye2-v0.1.33/applies.json`, `reapplyEdited` and `ownProfileSameId`). The profile it compares with is held in memory from the id's first appearance. After DYE2 restarts, as on every auto-update, it would compare the recipe record's own profile with the Workflow's once, but Decaid sends a plugin the Workflow as it loads it (`loadPlugin` in `decaid:lib/src/plugins/plugin_manager.dart`), which DYE2 takes first, as a change with no baseline, so the Workflow as DYE2 finds it becomes the baseline and the check compares it with itself: a recipe stays named across a restart, whatever changed while DYE2 was away (`server/test/fixtures/decaid/dye2-v0.1.26/`, `restart.json`). Streamline clears the id itself as it sends a profile, from its picker, on a wake onto its wake profile and on a reset of its defaults (`sendProfileRecordToMachine` and `loadProfileForWake` in `streamline-js:src/modules/profileManager.js`), and as it applies a favourite (`applyFavourite`); DYE2's dashboard does too as it applies a recent favourite, the only favourites DYE2 makes, as its Auto Favourites page saves a recipe instead. Nothing clears it on a change of batch or grinder, and nothing when the recipe leaves DYE2's list.
- **No stored selection.** DYE2's `GET /api/v1/plugins/dye2.reaplugin/selection` answers a selection derived from the Workflow, and a `POST` there only writes `recipeId`. DYE2 sets the field it wrote its stored selection into before, `context.extras.dye.selection`, to null once as it loads, and never writes it again.
- **When DYE2 pushes.** `{"what":"workflow"}` on its `changed` socket as the derived selection changes, after it saves into a recipe, and after it refreshes its recent favourites.
- **What DYE2 saves.** DYE2 writes a change of the Workflow into the recipe it names only when asked: `POST /api/v1/plugins/dye2.reaplugin/record` (`handleRecord`), the call Streamline's Save changes makes (`saveChanges` in `streamline-js:src/modules/dyeStrip.js`). It writes into the record each value of the Workflow that differs from the one the record holds (`itemPatch` in `dye2:dye2-plugin/src/utils/workflow-record.ts`): the dose, yield, grind setting and RPM, each where the record holds one, the grind setting as a number where it reads as one and otherwise as the text (`grindValue`, from v0.1.31); the Basket where the record holds one, or holds none once it moves off the one the Workflow held as the recipe was applied (`movedSinceArming`, `163a7c8`, from v0.1.33), its id and name together; the brew temperature only once it moves off the value it had as the recipe was applied; and each steam, hot water and flush setting the record holds, or holds none of once it moves off the value it had at the apply. It writes no steam setting while the Workflow's steam is off, no value cleared, so it never removes a Basket, and never the batch, the grinder or the Profile. Until a Basket picked since the apply is saved, DYE2's selection marks the recipe modified, which Streamline's strip stars (`cf98e25`; `dye2-v0.1.33/baskets.json`). It reads the flush temperature and flow from the machine's settings, keeping a read 60 s, but afresh as a recipe is applied and once the Workflow's flush settings move (`MACHINE_TTL_MS`, decentespresso/dye2#40, from v0.1.32). It answers `{saved, kind, id}`.
- **A recipe made on the Machine.** DYE2's `save-recipe` (`handleSaveRecipe`), which Streamline's strip calls from its long-press menu ("Save to recipe N" on an empty button, and "Save to recipes", in no slot, on a favourite's, from v0.2.20), makes a recipe of the live Workflow under an id `recipe-…`, in the slot asked for, whose previous holder keeps its record out of any slot, and then sets `recipeId` to it. So the Workflow can name a recipe before the plugin has read its record. DYE2's editor makes one under a UUID, and so does its Auto Favourites page's save, which keeps the profile by its title only.
- **Ids and slots.** A recipe's id is opaque: DYE2's editor gives a new one a UUID. Its Recipe Slot is its `stripSlot`, 1 to 5, the button of Streamline's strip it is on (`recipeStripCells` in `streamline-js:src/modules/dye-selection.js`), or null for none; DYE2 keeps any number of recipes, and its Select Recipe page lists and applies them all (ADR-0005). DYE2 gave the records with ids `1` to `5` their `stripSlot` once, as it loaded (`migrateRecipeSlots`). Its editor moves a recipe by setting `stripSlot`, clearing it on the slot's previous holder (`takeSlot` in `dye2:dye2-plugin/src/utils/dev-api.ts`). A recipe is on the strip exactly while it is in a slot (from v0.1.32): Streamline's strip and DYE2's leave out one hidden from it (`showOnStreamlineDashboard` false) whatever its `stripSlot` (`stripTargetOf` in `dye2:dye2-plugin/src/utils/recipe-strip.ts`), DYE2 saves one it saves hidden in no slot, its editor's switch off releasing the slot and a slot targeted turning it on, while Streamline's long-press "Clear button" writes `showOnStreamlineDashboard: false` and keeps the `stripSlot`. From v0.2.20, Streamline's "Replace <name>" on a filled button, and "Select recipe" on an empty one, open DYE2's Select Recipe to assign one of its recipes to that button, which saves it there shown, as the editor does, the slot's previous holder left shown in no slot, and applies nothing (`dye2-v0.1.33/streamline.json`).
- **A recipe naming no bean.** It means no bean (from v0.1.32): DYE2's dashboard and Select Recipe apply one with the Workflow's `coffeeName`, `coffeeRoaster` and `beanBatchId` null, and the Workflow it embeds holds the three null, which Streamline's strip applies as they are; DYE2 gave the records it held so once as it loaded (`clearBeanlessRecipeWorkflows`, under `recipeBeansMigrated`). Its `save-recipe` of a Workflow naming no bean still saves none of the three (`save-recipe.json`).
- **DYE2's dashboard.** It sends only its own edits, as a patch over a fresh read of the Workflow (decentespresso/dye2#31), and reads a recipe again before applying it (decentespresso/dye2#28). Streamline's strip does nothing on a tap of its highlighted button, the recipe DYE2's selection names, from v0.2.20 (`0af3b9d`).
- **Streamline after a Shot.** It clears only the note, no longer the batch, coffee, grinder, Basket or RPM (decentespresso/streamline-js#164).

## The Loaded Recipe

A Machine's Loaded Recipe is the Recipe whose record id its Workflow's `context.extras.dye.recipeId` names, through its tablet's map of its recipes, while that Recipe is one of its Location's Recipes and not Archived, in a Recipe Slot or not. The server reads it from each Workflow the plugin delivers (`DYE2_RECIPE_FIELD` and `dye2RecipeIdOf` in `protocol/`). A Workflow naming no recipe, or a record that is no Recipe's, names none, and so does any Workflow while DYE2 is not there (below), which the plugin's deliveries then say (`dye2Absent`). A Capture-only Machine has none. As it starts, the plugin takes the Recipe its first Workflow names as the one already loaded, and writes no load for it.

- **A recipe named before its record arrives.** A Workflow can name a record the tablet's map does not hold yet, as one `save-recipe` made and named at once. The server keeps the id it named and when the plugin observed the Workflow first naming it (`tablet_loaded_recipes.named_at`), and once the record joins the Location's Recipes (ADR-0018), the Recipe is loaded from then, never before the Machine's latest entry, and the Shots pulled meanwhile are linked to it; the plugin writes its load once a read of the tablet's recipes finds that record carrying the Recipe's global id. A Workflow naming a Recipe the map held already never loads another the map gives that id later, so a Machine that moves to another Location never loads one of that Location's Recipes through an id its Workflow still names.
- **Unloading.** A profile change unloads the Recipe, as DYE2 decides, and so does a favourite applied, as both clear the field, which the owner accepted on 2026-10-24 and may revisit. Another recipe applied loads that one instead. As the server unloads a Recipe itself, as one Archived, of a Location the Machine left, or the Machine made capture-only, it has the plugin write `{"context":{"extras":{"dye":{"recipeId":null}}}}` into the Workflow, as DYE2 does, which the plugin writes only while the Workflow still names that Recipe's record. Before the plugin posts DYE2's recipes removing the record the Workflow names, or giving its id to another Recipe's record, as when a joining Machine's own recipes are replaced by its new Location's, which may have the same slot-number ids (ADR-0005, ADR-0008), it clears the field first (`vacatedIds` in `plugin/src/loaded-recipe-rules.ts`), so the Workflow never names a Recipe it did not apply.
- **The plugin's check.** Before any write into the Workflow while a Recipe is loaded, a load's and the server's, the plugin checks that the Workflow it has just read still names that Recipe's record, and otherwise writes nothing, so a write only rarely lands in a recipe a barista applied in the moment between.
- **DYE2 not there.** The Machine has no Loaded Recipe where `GET /api/v1/plugins` lists no DYE2, or lists it neither loaded nor to load at startup (`loaded` and `autoLoad` both false, as disabling it leaves it), at once; or lists it not loaded for longer than twice the plugin's poll interval, as a DYE2 that fails to load or one unloaded in Decaid's settings. The plugin then delivers the Workflow again, saying so, where it names a recipe, and says so with every Workflow until DYE2 is back. A loaded DYE2 is available whatever its `autoLoad`. While DYE2 is not there, the plugin writes no load and saves nothing.

## The records a recipe is applied from

DYE2's dashboard applies a recipe's dial, its batch with the Bean's name and roaster (clearing the Workflow's where the recipe names a Bean and no batch, and the Bean too where it names none), its brew temperature, as Streamline's Brew tile sets one (`shiftedTemperatures` in `streamline-js:src/modules/brew-temp.js`): the profile's first step goes to it, and every other step moves by the same amount (decentespresso/dye2#26 and #27), and every steam, hot water and flush setting the recipe holds. Streamline's strip applies the record's embedded Workflow as it is, with the steam, hot water and flush settings its modes name (`mergeRecipeLiveSettings`), until decentespresso/streamline-js#154. So into each recipe record the server writes, as DYE2's own record builder does, the Recipe's batch beside its Bean, the Bean's name, roaster and batch in the embedded Workflow's context, all three null for a Recipe naming no Bean, written once to a record lacking them, as one the server wrote before and one `save-recipe` made (`lacksBeanNulls`), which the plugin posts though they compare as none held, the Recipe's profile at its brew temperature, by the same rule, in that Workflow's profile, and each steam, hot water and flush setting the Recipe holds, in DYE2's field of it and in partial `steamSettings`, `hotWaterData` and `rinseData` of that Workflow, none where it holds none; `profileSnapshot` holds the Profile as the Library does, which DYE2's dashboard moves to the brew temperature as it applies it. A profile with no usable first step temperature is applied as it is. So DYE2's and Streamline's own applies set the batch and brew temperature. The record's embedded profile is the same profile, by DYE2's fingerprint, as a load or the server's write of the Recipe's Profile leaves in the Workflow, so DYE2 keeps the Recipe named through that write (Loading, below), and its check as it restarts would keep it loaded even where it fired.

## Loading

On a load, the plugin writes into the Workflow what applying a DYE2 recipe leaves out, or a stale copy got wrong (`loadWrite`): the Recipe's current dial, its Bean Batch, grinder, Basket and RPM, every steam, hot water and flush setting it holds but a steam temperature into a Workflow whose steam is off (Steam on and off, below), and its Profile where the Workflow holds another, at the Recipe's brew temperature, as the record's embedded Workflow holds it. A setting the Recipe holds none of is left as the Machine has it, but a Recipe naming no Bean has the Workflow's batch, coffee and roaster cleared, as DYE2 applies one, where a copy without its nulls left them. Decaid refuses to change the steam, hot water and flush settings while no machine is connected (`MACHINE_SETTING_PARTS`), so the rest is then written without them. It writes no brew temperature: a stale copy's is written back by the server's Loaded Recipe write that follows the load (To other Machines, below). So a Machine that applied an out-of-date copy of the Recipe ends with its current values, worked out from which Recipe is loaded, never by matching values. The Workflow change that loads a Recipe is not saved into it, as it may be a stale copy's.

A load also gains the Recipe each value it holds none of that Decent Sync records itself (Every change is saved into the Loaded Recipe, below), from the Workflow as it stands: so a Recipe made without a grinder, Basket, RPM or dose takes the ones the Machine is using as a barista first loads it, but no Bean: a Recipe naming none means no bean as it is loaded, as DYE2 applies one. A value the Recipe holds is never taken from a load. The server takes the Workflow as holding, of the Recipe's parts, only those it holds already as the Recipe does, so every other part the Recipe holds is written into it once.

A write of the plugin's that changes the Workflow's profile, by DYE2's fingerprint (`dye2Fingerprint` in `protocol/`, the copy of DYE2's v0.1.33 fingerprint, every object's keys sorted), as a load from a stale copy or a Loaded Recipe write after the Recipe's Profile was edited does, writes the profile the tablet's record of the recipe holds, which DYE2 keeps the recipe named through (What DYE2 and Streamline do, above). A load writes the record's own. The server holds the Profile back from a Loaded Recipe write until that record holds it, by its id and, where the record holds a profile at all, as DYE2 compares none otherwise, by DYE2's fingerprint (`heldByRecord` in `server/src/library/loaded-recipe-intake.ts`): an edit of a Profile's title keeps its id (ADR-0006), and a record written before it holds the old title until the server's rewrite of it lands. So the write is one `PUT /workflow` (`putWorkflow` in `plugin/src/loaded-recipes.ts`), and the Recipe stays loaded. It names no recipe itself: the Workflow names the Recipe, as the plugin's check has just read it, and Decaid merges the write into it. A write naming it too would, where a barista applied another recipe in the moment since that read, name the Recipe again over the apply, and the plugin would then save that recipe's values into it; a write naming none leaves the other recipe named on the Recipe's profile, which DYE2 clears it on where that profile isn't the other recipe's own; either way the plugin decides on it as another recipe applied, and nothing is saved into the Recipe. On a DYE2 below v0.1.33, which is unsupported (ADR-0017), such a write unloads it. The previous release's plugin, which runs beside this one during an upgrade (ADR-0025), makes it as two, `recipeId` cleared and then the write with it named again, holding the Workflow's changes across both, which DYE2 takes as a new apply of the recipe, so that keeps it loaded too. The previous release's server holds the Profile back by its id alone, so beside it this plugin unloads the Recipe in one race, accepted while the two run side by side: a Loaded Recipe write of a Profile retitled since the tablet's record was written, whose rewrite the tablet refused.

## Every change is saved into the Loaded Recipe

Every change on a Machine with a Recipe loaded is saved into that Recipe, which the owner chose on 2026-10-24, and may revisit. It is Decent Sync's own rule, not DYE2's, which saves only on a barista's Save changes since v0.1.23: the Recipe is the day's dial, and a change of it on one Machine has to reach the others at once, so it does not wait on a barista remembering to save.

- **DYE2's save.** After each change of the Workflow while a sharing Machine has a Recipe loaded, the plugin calls DYE2's `record`, the call Streamline's Save changes makes (`recordIntoRecipe` in `plugin/src/dye2.ts`). It holds that Workflow change back until DYE2 answers, and where DYE2 saved, reads DYE2's recipes and reports them first, so the server takes the edit before the Workflow that brought it. It makes no such call for the Workflow changes of its own writes, for the change that loads a Recipe (the load write follows instead), or for a change that changes the profile, by the fingerprint above: DYE2's profile picker changes only the profile, and DYE2 clears `recipeId` a moment later, so a save in between would write the new profile's brew temperature into the Recipe. Its calls take their turn among the plugin's reads and writes of the tablet's lists (`LibraryAccess.run`), so they never overlap its posts of `recipes`, as both rewrite the whole list; one call waiting its turn covers the changes after it, as DYE2 saves the Workflow as it is then. A call that fails is tried again at the next change. DYE2 pushes after it saves, and the plugin reports DYE2's recipes on each push, so a Save changes made in Streamline reaches the server within seconds too, not only on the plugin's poll of the tablet's lists.
- **What Decent Sync records itself.** What DYE2 saves none of, the server records from each Workflow of the Machine's that goes on naming the Recipe, as that tablet's edit of the Recipe (ADR-0020), timed as the plugin observed the Workflow (`valuesFromWorkflow` in `server/src/library/loaded-recipe-intake.ts`): a dose, yield, grind setting or RPM the Recipe holds none of, a grind setting as typed, a number where it reads as one; a Basket the Recipe holds none of only on the load, as DYE2 takes the Machine's as the recipe is applied as its starting point and never saves it, while one picked after the load is DYE2's to save (What DYE2 saves, above), which reaches the Recipe as the tablet's edit of its record; a grinder, one of the Location's; and a batch of the Recipe's own Bean, a Recipe naming no Bean taking the batch's Bean too, but not on the load, which leaves it no batch to take. It skips a Workflow that changed the profile from the one before it, as for DYE2's save. Once the Recipe holds a value, DYE2 saves its changes. The previous release's server, which runs beside this one during an upgrade (ADR-0025), still records a Basket picked after the load, which changes nothing where DYE2 saved it, as the Recipe holds it by then, and takes one in the accepted gap below (Interim).
- **What stays the Machine's own.** A batch of another Bean, which keeps the Recipe loaded, its Shots linked to it; a value cleared on the Machine; steam turned off; and a steam setting changed while steam is off, which DYE2 does not save. None is the Recipe's, and the server never writes the Recipe's value back over one. Nor is the temperature steam is turned back on at, which the Recipe's replaces (Steam on and off, below).
- **How the server keeps them so.** The server keeps, per tablet, what its Workflow last named, the Workflow's parts that follow the Recipe as it last held them (`tablet_loaded_recipes.held`), updated by every Workflow delivery, and the Recipe's parts as that Workflow last took them, written there or held already (`base`). A Workflow is due a part the Recipe holds that it holds otherwise only where the Recipe's changed since that Workflow took it (`dueParts`). So what stays the Machine's own is left as it is, and an edit of the Recipe still writes every part it changed into the Workflow of every Machine that has it loaded, the Machine it was made on finding its Workflow holding it already.
- **What DYE2 saved that is no edit.** A value DYE2 saved that the Recipe holds already is no edit, as DYE2 saving the plugin's own write back. Nor is one that is what the Workflow held of a part whose write of the server's is still to land, while the Recipe holds another (`unwritten` in `recordedByDye2`, `server/src/machine-events/loaded-recipes.ts`): DYE2 then saved the Workflow left behind the record, and the Recipe's value is written back into the record and the Workflow. With a save after every change, a barista's change landing between the plugin's write of the record and its write of the Workflow is common, so the rule stays. A save of DYE2's editor, which stamps the record's `capturedAt` anew where DYE2's `record` keeps it, is no save from the Workflow: its values are written into the Workflow of every Machine that has the Recipe loaded, the saving one's included.
- **To other Machines.** An edit of the Recipe from anywhere is written into its record on each tablet at its Location, then into the Workflow of every Machine that has it loaded, each part changed since that Workflow took it, the brew temperature as on a load, and a steam temperature into none whose steam is off (Steam on and off, below). DYE2's save there finds its record holding the values, and saves nothing.
- **Capture-only.** As a Machine is made capture-only, the Recipe the server last had as its Loaded Recipe is unloaded, and cleared from the Workflow where it still names it. One loaded on the tablet before the server heard of it, as while offline, or applied there afterwards, which nothing there shares, stays named in the Workflow, but is not its Loaded Recipe, and the plugin writes and saves nothing for it; once its sharing is turned back on, it is, where it is one of its Location's Recipes. A Capture-only Machine is written nothing else of the Library or its Loaded Recipe; Settings Edits still reach it (ADR-0023).
- **Slots.** A Recipe's record keeps its id when it moves to another Recipe Slot, so it stays loaded. A Recipe is on the strip exactly while it is in a slot, as DYE2 holds one, so its records are written `showOnStreamlineDashboard` true exactly then, and its content holds nothing of it: the management interface has no switch for it. Releases up to 1.6.0 kept a `showOnDashboard` of its own in a Recipe's content, which could leave one in a slot and hidden, as its switch or a tablet's hide did, which Streamline showed as an empty button. The release that follows DYE2 v0.1.32 drops it: its migration, a change of data the owner approved on 2026-10-29 (`docs/AI_STORAGE_NOTES.md`), takes each Recipe 1.6.0 left so out of its slot, as a version from the server, so the strip shows what it showed, removes `showOnDashboard` from every Recipe's content and latest edits, and dismisses each open Conflict over it. While 1.6.0 still serves beside it during a deploy, a hide 1.6.0 takes in, or the switch on its page, is undone, and a `showOnDashboard` it writes stays in the content, unread. A move made on a tablet, as DYE2's editor sets a record's `stripSlot` or hides it, and as Streamline's "Clear button" hides it keeping its `stripSlot`, a record hidden being in no slot (`recipeSlotOf` in `protocol/`), moves the Recipe at its Location, where it is still in the slot that tablet's record of it was in, and one made in the management interface is written to the tablets the same way: on each, the record's `stripSlot` and whether it is shown change together, and the same post clears the `stripSlot` of the slot's previous holder, as `takeSlot` does, since DYE2 de-duplicates slots only once and Streamline places the first record it finds for a slot; that holder, left shown in no slot, is written hidden next. A write of whether a record is shown is made only while the record is still in the slot the server knew, so a barista who put it in another slot meanwhile keeps it shown there, and the move reaches the server.

A skin built for a Decent Sync deployment applies a recipe as Streamline does: it writes the Workflow with `recipeId` set to the recipe's record id.

## Steam on and off

A Recipe holds a steam temperature, but steam on and off stays each Machine's own, which the owner settled on 2026-10-16: an espresso-only Machine, or one being descaled, turns its steam off without changing the Recipe or the other Machines. Decaid has no steam on/off flag: steam is off below `STEAM_ON_FROM` (135 °C), as Decaid judges it (`steamOff`).

- **Steam off is no edit.** DYE2 saves no steam setting while the Workflow's steam is off, and Decent Sync records none, so steam turned off, and a steam setting changed while it is off, stay the Machine's. A steam time of 0 DYE2 saves is a value, as Streamline v0.2.18 reads it as "no timer" and keeps a heater switch of its own. A steam temperature of "Off" (0) saved in DYE2's editor is no edit, and the Recipe's is written back into the record (`steamOffPaths`).
- **No steam temperature written while off.** A steam temperature is never written into a Workflow whose steam is off, as it would turn steam on. The plugin enforces it, as a barista may turn steam off after the server plans a write: the server's Loaded Recipe write carries the Recipe's steam temperature, and the plugin leaves it out of `PUT /workflow` where the Workflow it has just read has steam off; the load write does the same with the record's `steamTempC`. The answer to such a write holds the Workflow as having taken the Recipe's steam temperature, so the write is not planned again until the Recipe's changes. The steam time, flow and milk stop are written as usual, as they do not turn steam on. So a steam edit made on one Machine reaches another while its steam is off without turning it on.
- **Steam turned back on takes the Recipe's.** Turning steam back on takes the Loaded Recipe's steam temperature, which the owner chose on 2026-10-28 (#374), so the temperature steam comes back at is no edit either. It is a rule of Decent Sync's own, not an upstream ask: DYE2 saves into a recipe only when asked, so for its own users steam back on at another temperature only marks the recipe modified, and it is Decent Sync saving every change that would make it an edit. Streamline's heater switch, while Streamline's own DYE2 switch is on, turns steam back on at the steam temperature of the recipe the Workflow names already, which the tablet's record of it holds as the Recipe's, one edited while steam was off included (ADR-0021). Steam comes back on at another temperature from that switch with Streamline's DYE2 switch off (`streamline.dye2Enabled`, off by default), which takes the one Streamline remembers (`last-steam-temp`, `steamHeaterFor` in `streamline-js:src/modules/api.js`), as a Recipe loaded through DYE2's own dashboard stays loaded; from its Settings › Calibration › Steam switch, at the temperature that page last switched off, held in memory, or 150 °C (`setSteamHeaterOn` in `streamline-js:src/settings/settings.js`), which its Save writes into the Workflow; from Auto Steam choosing a pitcher with the heater off, at the one Streamline remembers (`createAutoSteamSession` in `streamline-js:src/modules/auto-steam-session.js`); and from any other skin or Decaid's own screens. Each takes the Recipe's.
  - **In the plugin, before DYE2's save.** A change of the Workflow naming the Loaded Recipe that turns steam on, its steam temperature at or above `STEAM_ON_FROM` (`steamOnAt` in `plugin/src/loaded-recipe-rules.ts`) where it was below it since the plugin decided on the change before, in any Workflow Decaid reported or answered the plugin's writes with meanwhile, as one turned off and back on while a write of the plugin's was under way, whose changes it decides on together once that is done, is saved as any change is, but in the save's turn, once it has read the Workflow still naming the Recipe, the plugin first writes into it the steam temperature the tablet's record of the Recipe holds (`steamBackOnFirst` in `plugin/src/loaded-recipes.ts`, `steamBackOnWrite`), and only then calls `record`. DYE2 then finds the Workflow's steam temperature the record's, and saves only the change's other values, as it does any change's. So the temperature steam came back at is never saved into the tablet's record, nor reaches the Recipe or another Machine. The Workflow change is held back across both, as for any save, so the server is delivered the Workflow at the Recipe's steam temperature, or, where the write waits for a Shot (below), at the one steam came back at, which it takes as no edit, as it records no steam setting from a Workflow.
  - **Only the temperature it came back at.** The write is made only while the Workflow still holds the temperature steam came back at: one set since, with steam on, is the Recipe's edit, as any steam temperature changed while steam is on is, and steam turned off again is no edit. A temperature picked in the same change that turns steam on, as on Streamline's Calibration page before its Save, is replaced too, and the barista changes it after.
  - **Not where the Recipe holds none.** A Recipe holding no steam temperature, or a record holding "Off" (0), as DYE2's editor saves it until the server writes the Recipe's back, has none to take: DYE2 saves the temperature steam came back at where it moved off the one it had at the apply, as any setting the Recipe holds none of (What DYE2 saves, above).
  - **Not on a load.** A change that loads a Recipe is no change of the Loaded Recipe, and applying a recipe that holds a steam temperature turns steam on at it (below): the load write writes the record's where the Workflow holds another (Loading, above). A Recipe applied again while it is loaded is a change, so a copy's steam temperature turning steam on is replaced by the Recipe's.
  - **Beside 1.6.0.** The rule needs nothing of the server and adds nothing to the wire or to the plugin's storage on the tablet, so a tablet with this plugin keeps it on either release's server during a deploy (ADR-0025). One still running 1.6.0's plugin, until Decaid updates it, has DYE2 save the temperature steam came back at into the Recipe, as 1.6.0 did, which reaches every Machine with it loaded.

## During a Shot

The plugin makes no write into the Workflow while its Machine pulls a Shot, which the owner settled on 2026-10-24 (ticket #217). Decaid writes a Workflow's profile to the machine the moment it changes, whatever the machine is doing (`WorkflowDeviceSync._onChange` and `_drain`, which call `setProfile`, in `decaid:lib/src/controllers/workflow_device_sync.dart`), and `setProfile` rewrites the profile's header, every step frame and its tail, which the DE1 runs a Shot from by index. Decaid sends a Bengle the Workflow's yield as it changes too (`BengleSawBridge`), so a yield written mid-Shot moves where that Shot stops. And Decaid stores a Shot with the Workflow as it holds it once the Shot ends, up to its 4 s stopping backstop after the machine leaves `espresso` (`_persistShotIfNeeded` in `decaid:lib/src/controllers/de1_state_manager.dart`), so a write landing first would record values, or a `recipeId`, the Shot was not pulled with. Streamline v0.2.18 holds its own profile switches while the machine is in `espresso` for the same reason (`profileSendBlocked` and `setPendingProfileSend` in `streamline-js:src/modules/profile-send-gate.js`), but nothing guards the plugin's writes, and with every change saved into the Recipe (above), a brew temperature nudged on one Machine would rewrite the frames of a Shot running on another.

- **When.** From the machine state `espresso`, as Decaid's `stateUpdate` reports it (`SHOT_STATE`), until Decaid stores the Shot (`shotStored`), or 10 s after the state left `espresso`, for one Decaid stores nothing of, as a cleaning profile's (`plugin/src/shot-gate.ts`). An unknown state, before the first update or once no machine is connected, is no Shot, as for Streamline: Decaid sends no update as its machine goes, so a read finding no machine ends a Shot once Decaid has reported no state for 3 s.
- **Every write is held.** Not only those that carry a profile: the load write, the write of the Recipe's steam temperature as steam is turned back on, the server's Loaded Recipe writes and unloads, its clears of a joining Machine's Workflow, and every other change the server asks for, as a post of DYE2's recipes may clear the Workflow's `recipeId` first. Nothing in the Workflow needs to change during a Shot, and one rule is simpler than telling which writes reach the machine.
- **Only the latest is written.** The plugin holds one load, the latest decided on. It holds the server's change until the Shot ends, or at most two minutes, within the server's wait for an answer, and answers it as asked during a Shot (`PULLING_SHOT`); the server then plans what the tablet is due afresh, so a Recipe edited twice during the Shot is written once, with its latest values.
- **Checked again.** A held write is made as any other, so it first checks that the Workflow still names the Recipe it was for (The plugin's check, above).
- **Nothing lost.** A load held as the plugin stops is kept in Decaid's plugin storage, and made once the plugin loads again, where the Workflow still names that Recipe. The server's changes are planned again on the tablet's next connection. Steam turned back on is not kept, an accepted gap (below).
- **Saving is not held.** DYE2's `record` is no write into the Workflow, so a change made on a Machine during its own Shot is saved into the Recipe at once, and reaches the other Machines straight away, unless they are pulling a Shot too. But once steam is turned back on during a Shot, with a Recipe loaded that holds a steam temperature, the saves wait with the write of that temperature until the Shot ends, while the Workflow still holds the temperature steam came back at, as DYE2 would save it (Steam on and off, above), and another recipe applied before then leaves them unsaved, an accepted gap (below).

## Interim: workarounds and accepted gaps

Each workaround here does on DYE2's or Streamline's behalf what an upstream ask would have them do, and goes when they do (AGENTS.md):

- **The load write's steam, hot water and flush settings.** A load writes each one the Recipe holds that the Workflow holds otherwise, as DYE2's dashboard applies them, standing in for Streamline's strip applying every one the recipe holds, not only those its modes name (decentespresso/streamline-js#154, #186). Its leaving a steam temperature out of a Workflow whose steam is off stands.

And these gaps are accepted until fixed upstream:

- A Shot begun in the moment between the plugin's check that no Shot runs and its write into the Workflow has the write land in it: the plugin judges a Shot by the state Decaid last reported, and Decaid takes no write conditional on the machine's state.
- A recipe applied from a stale copy during a Shot, and changed on the Machine before the Shot ends, has the copy's values saved into the Recipe with the change: its load, which would bring it to the Recipe's values first, is held, but the save is not, and DYE2 saves every value of the Workflow that differs from the record.
- A recipe applied in the moment between the plugin's last check of the Workflow before a save and DYE2's `record` reading the Workflow has the change saved into it: `record` saves into the recipe the live Workflow names, and takes no recipe it expects to save into. The plugin checks again once its read of the Workflow is answered, so the window is the one request. Steam turned back on in that moment has the temperature it came back at saved by that save, which the plugin hears of only after, and so does a barista's Save changes in Streamline made before the plugin's write of the Recipe's lands: `record` saves every value of the Workflow the record holds otherwise.
- A recipe applied again from a stale copy while it is loaded, as a strip button tapped on a Streamline dashboard that has not re-read its recipes, is a change of the Workflow, not a load, so the copy's values are saved into the Recipe. Streamline reads its recipes again on focus, on becoming visible and on the plugin's push after each post of them (ADR-0005), and from v0.2.20 does nothing on a tap of the button its highlight puts on the recipe the Workflow names, so this needs a strip whose highlight has not caught up with the Workflow either, and is rare.
- DYE2 reads the flush temperature and flow from the machine's settings, which Streamline's settings page writes without touching the Workflow. So flush temperature and flow set there reach the Recipe only at that Machine's next Workflow change (decentespresso/streamline-js#154). That page no longer puts its saved values back on the machine as it opens, from v0.2.20 (ADR-0023). And DYE2 keeps a read of the machine's settings 60 s, dropping it only as a recipe is applied or the Workflow's flush settings move (decentespresso/dye2#40, from v0.1.32), so one set there within a minute of DYE2's last read is missed even at that next change, and reaches the Recipe only at a change after the read expires.
- Applying a recipe that holds a steam temperature turns steam on: from DYE2's dashboard now, and from Streamline's strip after decentespresso/streamline-js#154. That is the apply, not a Recipe edit.
- A change made on a Machine between `save-recipe` and the server taking in the record it made is set back by the load that follows: a moment as a rule, but while the tablet's plugin cannot reach the server, every change until it reconnects, as the plugin has DYE2 save none into a recipe that is no Recipe yet. The load is the one a recipe made in DYE2's editor and applied before the server took it in needs, to write what Streamline's strip leaves out (decentespresso/streamline-js#154). Telling a record `save-recipe` made from the editor's would rest on the form of DYE2's generated ids, which DYE2 does not promise.
- A recipe `save-recipe` made on a tablet while its plugin could not reach the server, and another applied there before it reconnected, is never loaded, and the Shots pulled with it are linked to no Recipe: the server loads a recipe named before its record arrives only while the Machine's Workflow still names it.
- DYE2's editor saving a steam temperature of "Off" into the recipe a Machine has loaded applies the recipe there again (`reapplyIfSelected`), turning that Machine's steam off. The save is no edit, so the Recipe keeps its steam temperature and the other Machines theirs, but that Machine's steam stays off until a barista turns it back on, as the server writes no steam temperature into a Workflow whose steam is off; turned back on, it takes the Recipe's (Steam on and off, above), once the server has written that back into the record. Turned back on in the moment before, as the record still holds "Off", DYE2 saves the temperature steam came back at into it, which is the Recipe's edit.
- Steam turned back on is not kept across the plugin's loads, as a held load is (During a Shot, above): a plugin stopped before it has written the Recipe's steam temperature, as one updated during the Shot in which steam was turned back on, takes the Workflow as it stands once it loads again, so its next save has DYE2 save the temperature steam came back at into the Recipe. Keeping it would hold every save as the plugin loads until it has read Decaid's storage, which can take Decaid's 10 s.
- Steam turned back on during a Shot, with a Recipe loaded that holds a steam temperature, holds the save of that change's other values, and of every change on the Machine after it, until the Shot ends, while the Workflow still holds the temperature steam came back at (During a Shot, above). Where another recipe is applied before the Shot ends, they are saved into no Recipe: DYE2's `record` saves only into the recipe the Workflow names.
- A Recipe whose record holds no Basket takes one picked on a Machine only as DYE2 saves it, which it does only once the Basket moves off the one the Workflow held as the recipe was applied, a starting point DYE2 keeps in memory only (`armedMachine` in `workflowChanged`, `dye2:dye2-plugin/src/plugin.ts`; `movedSinceArming` in `itemPatch`), as Decent Sync records no Basket after the load (Every change is saved into the Loaded Recipe, above). A record holding a Basket takes every change of it, as DYE2 saves a Basket the record holds whatever its starting point.
  - **Saved late.** One picked in the seconds after an apply, before DYE2 has noted its starting point, as it first reads the machine's settings afresh, which its `record` does not wait for (`handleRecord`), and one whose save failed, reach the Recipe at that Machine's next change.
  - **Not saved.** One picked and not yet saved as DYE2 resets its starting point to the Workflow as it stands, as it does as it reloads, on every update of it, and as the recipe is named again on its own profile after a change of profile (decentespresso/dye2#38), as when the server writes an edited Profile into the Workflow, is never saved; nor is the Basket a Machine had as the recipe was applied, picked there again after the Recipe's Basket was cleared, in the management interface or DYE2's editor, while it was loaded. The Recipe then takes a Basket from that Machine only once a different one is picked.

## Rejected

We first worked the Loaded Recipe out by matching the Workflow against the Location's Recipes, on profile, dose, yield, grinder and grind setting, and read every Workflow change while one was loaded as an edit of it. Once DYE2 selected recipes and recorded every change into them, from #177, we rejected keeping that, and rejected recording the Workflow ourselves: the two would be separate models of the same thing, which disagree, and two recorders of one change count it twice or disagree about it. DYE2 then stopped recording on its own, from v0.1.23, and dropped its stored selection in v0.1.25 (decentespresso/dye2#36). So Decent Sync now follows the recipe DYE2's own field names, has DYE2 save each change through the call its own skin makes, and records itself only what DYE2 saves none of. We still reject two recorders of one field: Decent Sync records a dose, yield, grind setting or RPM only while the Recipe holds none, which DYE2 does not save, a Basket only as the Recipe is loaded, which DYE2 never saves, and never the brew temperature, steam, hot water or flush settings, which DYE2 does; and it keeps no selection of its own beside DYE2's field. So we rejected keeping the server's recording of a Basket picked after the load, which DYE2 saves from v0.1.33, as a backstop for one DYE2 saves late or never (Interim, below): it made the server a second recorder of every pick, though it changed something only then, as the plugin reports the recipes DYE2 saved before it delivers the Workflow change.

We rejected saving into the Recipe only when a barista asks, as DYE2 and Streamline now do, because Shots would record a dial the other Machines no longer have, and a barista forgetting to save would leave them grinding at the old setting. We rejected writing a Loaded Recipe's value back over any part the Workflow holds otherwise, as the server did until #216: it undid every change DYE2 had not saved, and would undo what stays the Machine's own. We rejected unloading the Recipe on another batch, as DYE2 did until v0.1.25 (decentespresso/dye2#19): a fresh bag of the same roast is the same dial, and a batch of another Bean is that Machine's own. We also rejected telling a stale copy applied by matching its values against the Recipe's earlier ones, as the server did until #190 and, for the hot water the Workflow edited, until #173: it cannot tell a barista choosing a value from an old copy being applied, and wrote back a flush time a barista set deliberately.

We rejected turning steam back on at the Recipe's steam temperature in the server's Loaded Recipe write, which carries one already, and which the plugin leaves out of a Workflow whose steam is off, counting it as taken (Steam on and off, above). The server hears of the change only after the plugin has had DYE2 save it, as the plugin reports the recipes DYE2 saved before it delivers the change, so DYE2 would have saved the temperature steam came back at into the tablet's record, and the server taken it as the Recipe's edit, before any write of the server's; and keeping DYE2 from saving it needs the plugin to know the rule anyway. We did not ask DYE2 or Streamline for it: neither is at fault, as DYE2 saves into a recipe only when asked.

We rejected sharing only the stored recipes, picked up the next time a barista loads one, because Shots would record a dial the Machine no longer has. We rejected naming the Loaded Recipe anywhere but the Workflow, because Shots pulled while the tablet is offline would then reach the server without their Recipe.

## Consequences

- **Every tweak is the Recipe's.** A change on a Machine with a Recipe loaded to its dose, yield, grind setting, brew temperature, RPM, Basket, grinder, a batch of its Bean, or a steam, hot water or flush setting changes it on every Machine at the Location. That is the intent: a dose is never changed for one customer. Turning steam off, clearing a value or picking a batch of another Bean changes no Recipe, and keeps it loaded, and turning steam back on takes its steam temperature.
- **A load fills in what a Recipe lacks.** A Recipe takes, as a barista first loads it, each value it holds none of that the Machine has, so a Recipe made in the management interface without a grinder or Basket gains the Machine's. Not a Bean: a Recipe naming none means no bean as it is loaded, so loading it leaves the Machine with no bean batch, as DYE2 v0.1.32 applies one, and takes none from the Workflow; a batch a barista picks once it is loaded is a change like any other, which it takes with its Bean.
- **Only an applied recipe is loaded.** Dialling in a Recipe's values by hand loads nothing. A profile change unloads it, and so does a favourite applied.
- **DYE2 is required.** A Machine without DYE2 v0.1.33 has no Loaded Recipe (ADR-0017). Nothing falls back to matching. The plugin still writes the recipe lists to every sharing tablet (ADR-0005).
- **The plugin writes more of the tablet.** Beyond the clearing on joining (ADR-0008), it writes a Loaded Recipe's values into the Workflow, clears `recipeId` there, has DYE2 save into its recipes, and writes each recipe record's embedded Workflow, with its batch, its profile at the Recipe's brew temperature and the settings the Recipe holds. A skin that remembers the steam, hot water and flush settings takes them as its own (ADR-0021).
- **Shots name their Recipe, and record its Basket.** Each Shot carries `recipeId` as it was pulled, and the Recipe's batch, grinder, Basket and RPM. A Shot is linked to the Recipe its tablet's map holds under that id, kept while it names the same id, only where its Machine had that Recipe loaded when it was pulled: a Capture-only Machine's Shots name a recipe that was never its Loaded Recipe. A Shot naming a record the map does not hold yet is linked once it does; one naming none has none. So Analytics (milestone 6) needs no inferred recipes.
