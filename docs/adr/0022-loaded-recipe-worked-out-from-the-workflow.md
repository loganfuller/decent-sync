# A Machine's Loaded Recipe is the recipe its Workflow names, and every change on the Machine is saved into it

A Recipe is the day's dial for one roast, which baristas keep current through the day. When a barista on one Machine moves the Brazil's grind from 2.4 to 2.5, every other Machine with the Brazil loaded has to take that at once: the grinder is physically at 2.5, and their next Shots would otherwise record 2.4. The owner also counts which Recipe a Machine has loaded as part of its state, for analytics.

## What DYE2 and Streamline do

DYE2 v0.1.40 and Streamline v0.2.31, the supported floor (ADR-0017), name the recipe a Workflow is dialled in to in the Workflow itself, and keep no selection of their own (decentespresso/dye2#36). What DYE2 v0.1.32 does otherwise than v0.1.26 is recorded in `server/test/fixtures/decaid/dye2-v0.1.32/`, what v0.1.33 and Streamline v0.2.21 do otherwise again in `server/test/fixtures/decaid/dye2-v0.1.33/`, what DYE2 v0.1.35 does otherwise again in its feed rate, grinders page, Auto Favourites and steam in `server/test/fixtures/decaid/dye2-v0.1.35/`, what Streamline v0.2.24 does otherwise in its steam settings, its strip, its profile switch and its Grind label, and DYE2 v0.1.36 on its Grinders page, in `server/test/fixtures/decaid/streamline-v0.2.24/`, and what DYE2 v0.1.37 to v0.1.40 and Streamline v0.2.25 to v0.2.27 do otherwise as they apply a recipe, pick a grinder or a profile, edit a recipe and save a favourite, in `server/test/fixtures/decaid/dye2-v0.1.40/`, and what Streamline v0.2.29 to v0.2.31 do otherwise as its strip applies a recipe's steam, hot water and flush settings, with DYE2 v0.1.42, in `server/test/fixtures/decaid/streamline-v0.2.31/`.

- **The Workflow's recipe.** `context.extras.dye.recipeId` holds the id of DYE2's record of the recipe being dialled in, or null for none, which DYE2 reads as text (`recipeIdOf`). DYE2's dashboard, its Select Recipe page and Streamline's DYE strip set it as they apply a recipe, in the same `PUT /workflow` as the recipe's values (`applyRecipe` and `recipeIdPatch` in `streamline-js:src/modules/dyeStrip.js` and `dye-selection.js`). Decaid copies it onto every Shot pulled with that Workflow, offline ones included.
- **When it is cleared.** DYE2 clears it, by `PUT /workflow` of `recipeId: null`, once the Workflow's profile moves off the one it held when that id first appeared, whatever moved it (`workflowChanged` in `dye2:dye2-plugin/src/plugin.ts`, `idProfileChanged` in `dye2:dye2-plugin/src/utils/workflow-record.ts`), even where the same write names the same id, but where the profile that arrives is the recipe's own, as applying it again after its profile changed sends, which it takes as the new baseline (`recipeProfileChanged`, decentespresso/dye2#38, from v0.1.27). It tells a profile by its fingerprint (`profileFingerprint`): the title, tank temperature and steps, but each step's temperature, and a step limiter of value 0 read as none, so neither a brew temperature nor a yield Streamline writes into the profile's target weight changes it (decentespresso/dye2#18, #32). The fingerprint sorts every object's keys (`sortKeysReplacer`, decentespresso/dye2#43, from v0.1.33), so the profile a record holds is the Workflow's whatever key order each holds it in: Decaid's own, or PostgreSQL's `jsonb` order, in which Decent Sync's server writes a record. So applying a Recipe again after its Profile changed keeps it named, and so does one `PUT /workflow` of the record's profile naming the same id, as the plugin writes one (`dye2-v0.1.33/applies.json`, `reapplyEdited` and `ownProfileSameId`). The profile it compares with is held in memory from the id's first appearance. After DYE2 restarts, as on every auto-update, it would compare the recipe record's own profile with the Workflow's once, but Decaid sends a plugin the Workflow as it loads it (`loadPlugin` in `decaid:lib/src/plugins/plugin_manager.dart`), which DYE2 takes first, as a change with no baseline, so the Workflow as DYE2 finds it becomes the baseline and the check compares it with itself: a recipe stays named across a restart, whatever changed while DYE2 was away (`server/test/fixtures/decaid/dye2-v0.1.26/`, `restart.json`). ## The Loaded Recipe

A Machine's Loaded Recipe is the Recipe whose record id its Workflow's `context.extras.dye.recipeId` names, through its tablet's map of its recipes, while that Recipe is one of its Location's Recipes and not Archived, in a Recipe Slot or not. The server reads it from each Workflow the plugin delivers (`DYE2_RECIPE_FIELD` and `dye2RecipeIdOf` in `protocol/`). A Workflow naming no recipe, or a record that is no Recipe's, names none, and so does any Workflow while DYE2 is not there (below), which the plugin's deliveries then say (`dye2Absent`). A Capture-only Machine has none. As it starts, the plugin takes the Recipe its first Workflow names as the one already loaded, and writes no load for it.

- **A recipe named before its record arrives.** A Workflow can name a record the tablet's map does not hold yet, as one `save-recipe` made and named at once. The server keeps the id it named and when the plugin observed the Workflow first naming it (`tablet_loaded_recipes.named_at`), and once the record joins the Location's Recipes (ADR-0018), the Recipe is loaded from then, never before the Machine's latest entry, and the Shots pulled meanwhile are linked to it; the plugin writes its load once a read of the tablet's recipes finds that record carrying the Recipe's global id. A Workflow naming a Recipe the map held already never loads another the map gives that id later, so a Machine that moves to another Location never loads one of that Location's Recipes through an id its Workflow still names.
- **Unloading.** A profile change unloads the Recipe, as DYE2 decides, and so does a favourite applied, as both clear the field, which the owner accepted on 2026-10-24 and may revisit. Another recipe applied loads that one instead. As the server unloads a Recipe itself, as one Archived, of a Location the Machine left, or the Machine made capture-only, it has the plugin write `{"context":{"extras":{"dye":{"recipeId":null}}}}` into the Workflow, as DYE2 does, which the plugin writes only while the Workflow still names that Recipe's record. Before the plugin posts DYE2's recipes removing the record the Workflow names, or giving its id to another Recipe's record, as when a joining Machine's own recipes are replaced by its new Location's, which may have the same slot-number ids (ADR-0005, ADR-0008), it clears the field first (`vacatedIds` in `plugin/src/loaded-recipe-rules.ts`), so the Workflow never names a Recipe it did not apply.
- **The plugin's check.** Before any write into the Workflow while a Recipe is loaded, a load's and the server's, the plugin checks that the Workflow it has just read still names that Recipe's record, and otherwise writes nothing, so a write only rarely lands in a recipe a barista applied in the moment between.
- **DYE2 not there.** The Machine has no Loaded Recipe where `GET /api/v1/plugins` lists no DYE2, or lists it neither loaded nor to load at startup (`loaded` and `autoLoad` both false, as disabling it leaves it), at once; or lists it not loaded for longer than twice the plugin's poll interval, as a DYE2 that fails to load or one unloaded in Decaid's settings. The plugin then delivers the Workflow again, saying so, where it names a recipe, and says so with every Workflow until DYE2 is back. A loaded DYE2 is available whatever its `autoLoad`. While DYE2 is not there, the plugin writes no load and saves nothing.

## Loading

A Recipe is the whole Shot, which the owner decided on 2026-11-15, as DYE2 and Streamline take a recipe from v0.1.37 and v0.2.25: a Machine that loads one is left with none of what the Recipe names none of, its dose, grind setting, RPM, feed rate, Grinder, Basket and Bean Batch, and with stop-at-weight off where it names no yield and no dose and ratio (`WHOLE_SHOT_PARTS` in `protocol/`). The steam, hot water and flush settings stay the exception: a Machine keeps its own for those the Recipe holds none of. A Recipe naming no Profile leaves the Workflow's profile, as DYE2's apply does.

On a load, the plugin brings the Workflow to the Recipe whole, whatever applied it (`loadWrite`): it writes what applying a DYE2 recipe leaves out, or a stale copy got wrong, the Recipe's current dial, its Bean Batch, grinder, Basket, RPM and feed rate, every steam, hot water and flush setting it holds, its steam switched on or off as the Recipe holds it (Steam on and off, below), and its Profile where the Workflow holds another, at the Recipe's brew temperature, as the record's embedded Workflow holds it; and it writes none for each of those parts the recipe names none of that the Workflow still holds, each field null, a yield of 0, as it clears the Bean, and as DYE2's and Streamline's applies clear them. So Decent Sync does not rest on each Skin clearing, and a Skin built for a Decent Sync deployment needs no clearing of its own. A recipe naming a Bean and no batch has the Workflow's batch cleared, its coffee and roaster the Bean's. A steam, hot water or flush setting the Recipe holds none of is left as the Machine has it. Decaid refuses to change the steam, hot water and flush settings while no machine is connected (`MACHINE_SETTING_PARTS`), so the rest is then written without them. It writes no brew temperature: a stale copy's is written back by the server's Loaded Recipe write that follows the load (To other Machines, below). So a Machine that applied an out-of-date copy of the Recipe ends with its current values, worked out from which Recipe is loaded, never by matching values. The Workflow change that loads a Recipe is not saved into it, as it may be a stale copy's.

The server takes nothing into a Recipe from the Workflow as it loads. Until #550 a load gained the Recipe each value it held none of that Decent Sync records itself, and the Machine's Basket; from DYE2 v0.1.37 the apply's write lands first and clears them, so there is nothing left to take, and taking from a Skin that clears nothing would make the Recipe depend on which Skin applied it. A Recipe gains a value it holds none of as a barista sets or picks it on a Machine that has it loaded (Every change is saved into the Loaded Recipe, below). The server takes the Workflow as holding, of the Recipe's parts, only those it holds already as the Recipe does, none of one included, so every other part is written into it once, or cleared from it, by its Loaded Recipe write (To other Machines, below), which is how a tablet whose plugin is the previous release's, whose load write clears nothing but the Bean, is cleared too.

A write of the plugin's that changes the Workflow's profile, by DYE2's fingerprint (`dye2Fingerprint` in `protocol/`, the copy of DYE2's v0.1.33 fingerprint, every object's keys sorted), as a load from a stale copy or a Loaded Recipe write after the Recipe's Profile was edited does, writes the profile the tablet's record of the recipe holds, which DYE2 keeps the recipe named through (What DYE2 and Streamline do, above). A load writes the record's own. The server holds the Profile back from a Loaded Recipe write until that record holds it, by its id and, where the record holds a profile at all, as DYE2 compares none otherwise, by DYE2's fingerprint (`heldByRecord` in `server/src/library/loaded-recipe-intake.ts`): an edit of a Profile's title keeps its id (ADR-0006), and a record written before it holds the old title until the server's rewrite of it lands. So the write is one `PUT /workflow` (`putWorkflow` in `plugin/src/loaded-recipes.ts`), and the Recipe stays loaded. It names no recipe itself: the Workflow names the Recipe, as the plugin's check has just read it, and Decaid merges the write into it. A write naming it too would, where a barista applied another recipe in the moment since that read, name the Recipe again over the apply, and the plugin would then save that recipe's values into it; a write naming none leaves the other recipe named on the Recipe's profile, which DYE2 clears it on where that profile isn't the other recipe's own; either way the plugin decides on it as another recipe applied, and nothing is saved into the Recipe. On a DYE2 below v0.1.33, which is unsupported (ADR-0017), such a write unloads it. The previous release's plugin, which runs beside this one during an upgrade (ADR-0025), makes it as two, `recipeId` cleared and then the write with it named again, holding the Workflow's changes across both, which DYE2 takes as a new apply of the recipe, so that keeps it loaded too. The previous release's server holds the Profile back by its id alone, so beside it this plugin unloads the Recipe in one race, accepted while the two run side by side: a Loaded Recipe write of a Profile retitled since the tablet's record was written, whose rewrite the tablet refused.

## Every change is saved into the Loaded Recipe

Every change on a Machine with a Recipe loaded is saved into that Recipe, which the owner chose on 2026-10-24, and may revisit. It is Decent Sync's own rule, not DYE2's, which saves only on a barista's Save changes since v0.1.23: the Recipe is the day's dial, and a change of it on one Machine has to reach the others at once, so it does not wait on a barista remembering to save.

- **DYE2's save.** After each change of the Workflow while a sharing Machine has a Recipe loaded, the plugin calls DYE2's `record`, the call Streamline's Save changes makes (`recordIntoRecipe` in `plugin/src/dye2.ts`). It holds that Workflow change back until DYE2 answers, and where DYE2 saved, reads DYE2's recipes and reports them first, so the server takes the edit before the Workflow that brought it. It makes no such call for the Workflow changes of its own writes, for the change that loads a Recipe (the load write follows instead), or for a change that changes the profile, by the fingerprint above: DYE2's profile picker changes only the profile, and DYE2 clears `recipeId` a moment later, so a save in between would write the new profile's brew temperature into the Recipe. Its calls take their turn among the plugin's reads and writes of the tablet's lists (`LibraryAccess.run`), so they never overlap its posts of `recipes`, as both rewrite the whole list; one call waiting its turn covers the changes after it, as DYE2 saves the Workflow as it is then. A call that fails is tried again at the next change. DYE2 pushes after it saves, and the plugin reports DYE2's recipes on each push, so a Save changes made in Streamline reaches the server within seconds too, not only on the plugin's poll of the tablet's lists.
- **What Decent Sync records itself.** What DYE2 saves none of, the server records from each Workflow of the Machine's that goes on naming the Recipe, as that tablet's edit of the Recipe (ADR-0020), timed as the plugin observed the Workflow (`valuesFromWorkflow` in `server/src/library/loaded-recipe-intake.ts`): a dose, yield, grind setting, RPM or feed rate the Recipe holds none of, a grind setting as typed, a number where it reads as one, and a feed rate as typed, but never a 0, which is none (What 0 means, below); a grinder, one of the Location's, as a tap on DYE2's dashboard's grinder tabs, its grinder picker's Confirm and, from v0.1.36, a tap of its card on DYE2's Grinders page write one into the Workflow (`fa1d93f`), with the grind setting and RPM the Workflow holds after it, none included, as the pick brings the grinder's own (What DYE2 and Streamline do, above): the ones the Recipe held were the other Grinder's, so every Machine with the Recipe loaded ends on the same Grinder and numbers, or on none, "dial me in"; and a batch, with its Bean where it is another Bean's, which the owner decided on 2026-11-18 for every Skin (#570), as a Grinder picked is: a bag of another coffee on the Machine is the Recipe's coffee now, whether a Skin's bean dialog or Streamline's picked it, and it reaches the other Machines at once. But not a batch the Library retired: one Archived, of an Archived Bean, or not at the Recipe's Location, never added there or finished there, which the Location does not offer, and which the server does not add there. A Basket is DYE2's to save: one picked on the Machine reaches the Recipe as the tablet's edit of its record (What DYE2 saves, above). Nothing is recorded from the Workflow that loads the Recipe (Loading, above). It skips a Workflow that changed the profile from the one before it, as for DYE2's save, but for one onto the profile the tablet's record of the Recipe holds, as a Skin writes the record first, which DYE2 keeps the recipe named through (#570). Once the Recipe holds a value, DYE2 saves its changes. A Grinder changed in the management interface, or in DYE2's recipe editor, leaves the Recipe's grind setting and RPM as typed, as DYE2's editor does.
- **What stays the Machine's own.** A batch the Library retired, Archived, of an Archived Bean or not at the Recipe's Location, which keeps the Recipe loaded, its Shots linked to it, until a change of the Bean of a Recipe naming no batch clears it (#572); a value cleared on the Machine, as DYE2's `record` saves no clear, the grind setting and RPM a Grinder's pick left being the one exception; steam turned off at the Machine, by its heater switch or a steam time of 0 set there; and a steam temperature or steam time changed while steam is off, which DYE2 does not save, though from v0.1.35 it saves a steam flow or milk stop changed then, the Recipe's edit; and a coffee name or roaster typed on the Machine, which DYE2 saves none of and Decent Sync takes in none of, as a value cleared, written over only by a later change of the Recipe's Bean (To other Machines, below; #572). None is the Recipe's, and the server never writes the Recipe's value back over one, but for a change of the Bean of a Recipe naming no batch, which is written over a typed coffee and clears a batch the Machine holds as its own (#572). Nor are the temperature and time steam is turned back on with, which the Recipe's replace (Steam on and off, below).
- **How the server keeps them so.** The server keeps, per tablet, what its Workflow last named, the Workflow's parts that follow the Recipe as it last held them (`tablet_loaded_recipes.held`), updated by every Workflow delivery, and the Recipe's parts as that Workflow last took them, written there or held already (`base`), with the Recipe's Bean as it last took it, the Bean of the Recipe's batch where the Workflow holds that batch among them, or another where it holds a coffee other than the Recipe's Bean's, as after a load from an out-of-date copy of the record (where the Recipe names no Bean, a coffee of no Bean, as one typed, stays the Machine's own) or a write carried as of an edit of the Bean since replaced, which a base saved before #572 holds none of and is read as having taken the Recipe's Bean as it is now, until an edit changing the Recipe's Bean keeps the Bean it named before in it (`keepBeanTaken`), so the deploy writes nothing and writes over no typed name. Nor is one that is what the Workflow held of a part whose write of the server's is still to land, while the Recipe holds another (`unwritten` in `recordedByDye2`, `server/src/machine-events/loaded-recipes.ts`): DYE2 then saved the Workflow left behind the record, and the Recipe's value is written back into the record and the Workflow. With a save after every change, a barista's change landing between the plugin's write of the record and its write of the Workflow is common, so the rule stays. A save of DYE2's editor, which stamps the record's `capturedAt` anew where DYE2's `record` keeps it, is no save from the Workflow: its values are written into the Workflow of every Machine that has the Recipe loaded, the saving one's included.

A steam, hot water or flush setting cleared from the Recipe stays each Machine's own. The write carries a cleared part as it carries any other value, a null the plugin writes as it is, so the previous release's plugin, which runs beside this one during an upgrade (ADR-0025), writes it too, and the wire is unchanged. A yield of 0 is stop-at-weight off. A Recipe holding no yield never takes a 0 from a Workflow, and a Shot's target yield of 0 is no target (`SHOTS.md`). The previous release's server may take a tablet's 0 in again while it serves beside this one, and takes a yield of 0 at a load of a Recipe holding none.

One loaded on the tablet before the server heard of it, as while offline, or applied there afterwards, which nothing there shares, stays named in the Workflow, but is not its Loaded Recipe, and the plugin writes and saves nothing for it; once its sharing is turned back on, it is, where it is one of its Location's Recipes. ## Steam on and off

Steam on and off follows DYE2's own rules, which the owner decided on 2026-11-22 (#616), replacing part of what was settled on 2026-10-16, when steam on and off stayed each Machine's own whatever its Recipe held. DYE2 from v0.1.35 applies a recipe's steam as it holds it (`recipeMachineSettings` in `dye2:dye2-plugin/src/utils/dev-api.ts`, decentespresso/dye2#46), and from v0.2.29 Streamline's strip does the same (`recipeSteamPatch` in `streamline-js:src/modules/steam-mode.js`, decentespresso/streamline-js#154), so a Machine's steam already followed the recipe applied on it from every Skin's own apply: a rule of Decent Sync's keeping it apart would have the plugin undo what the apply did.

Decaid has no steam on/off flag: steam is off below `STEAM_ON_FROM` (135 °C), as Decaid judges it (`steamOff`). From Streamline v0.2.22, the floor being v0.2.31 (ADR-0017, ADR-0021), a steam time of 0 is steam off too, its other half: Streamline writes `{targetTemperature: 0, duration: 0}` as it turns steam off, and writes a temperature and a steam time of 1 to 255 s as it turns steam back on (`steamOffPatch` and `steamOnPatch` in `streamline-js:src/modules/steam-mode.js`); its main page shows a steam time of 0 as "Off", with the heater on or not (`formatSteamDuration` in `src/modules/ui.js`). So a Recipe's steam time is 1 to 255 s (`STEAM_TIME_FROM`, `STEAM_TIME_TO`), the DE1 holding no longer one, or none, which the owner decided on 2026-11-05.

- **"Off" is the Recipe's.** A Recipe holds a steam temperature of 135 to 170 °C, none, or "Off", which is a steam temperature of 0 (`STEAM_OFF_VALUE`, `steamHeldOff` in `protocol/`). DYE2's editor saves "Off" as a steam temperature of 0 with a steam time of 0 beside it (decentespresso/dye2#46), and DYE2 and Streamline apply a record holding either half, a steam temperature below 135 °C or a steam time of 0, as steam off whole. So a tablet's record holding either half is the Recipe's edit to "Off" (`libraryValues`, `holdsSteamOff` in `server/src/library/recipe-intake.ts`), and the management interface and the MCP endpoint show, set and clear it, as a steam temperature of 0. The steam time of 0 beside it is the other half of "Off", no steam time of the Recipe's: the Recipe keeps the steam time it held, for when it holds a steam temperature again. A Recipe holding "Off" is written to every tablet as DYE2's editor saves it, a steam temperature and a steam time of 0 in the record's fields and in its embedded Workflow (`recipeRecord`), so a record holding it by one half alone is written so. A steam time above 255 s, which DYE2's editor holds one typed to from v0.1.35 but another writer may save, is taken and read as 255 s, as Streamline clamps one it writes, and the record is written back so. The server reads a Recipe's stored steam time of 0, as 1.6.2 may have taken one in, as none (`steamTimeOf`).
- **A load switches steam.** A Machine that loads a Recipe holding a steam temperature has its steam turned on at the Recipe's steam temperature and time, and one that loads a Recipe holding "Off" has it turned off whole, the same from DYE2's dashboard, Streamline's strip, the Streamline Cafe Skin and the plugin's own load write (`loadWrite`), which writes them whether the Workflow's steam is on or off, for a Skin that applies none of them and for a stale copy. That is the apply, not a Recipe edit. A Recipe holding neither a steam temperature nor a steam time leaves the Machine's steam as it is. Where it holds only one of the two, the plugin writes that one and leaves the other as the apply chose it: Streamline's strip, where the heater is off, turns steam on with a recipe holding either, at the temperature or time Streamline remembers for the one it holds none of, else 150 °C and 30 s (`steamOnPatch`), while DYE2's dashboard writes only what the recipe holds, so a Recipe holding a steam time and no steam temperature leaves steam off there, at that time. So an espresso-only Machine, or one being descaled, has its steam turned on by loading a Recipe that holds a steam temperature: such a Machine loads Recipes holding "Off", or none of steam.
- **The heater switch is the Machine's.** Steam turned off at a Machine, by Streamline's heater switch, its Calibration page or a steam time of 0 set there, changes no Recipe and no other Machine: DYE2 saves no steam temperature or steam time while the Workflow's steam is off (`STEAM_OFF_KEYS`), and Decent Sync records none, so steam turned off there, and a steam temperature or time changed while it is off, stay the Machine's; a steam flow or milk stop changed then DYE2 saves from v0.1.35.
- **An edit to "Off" turns steam off on every Machine with the Recipe loaded.** DYE2's editor applies the recipe again on the tablet it saved it on (`reapplyIfSelected`), turning that Machine's steam off, and the server's Loaded Recipe write carries "Off" to the others as a steam temperature and a steam time of 0 (`recipeParts` in `server/src/library/loaded-recipe-intake.ts`), which the plugin writes together into a Workflow whose steam is on, or not at all (`loadedRecipeFields` in `plugin/src/library-writes.ts`). DYE2's save there finds steam off and saves nothing, so no write of the plugin's comes back as a second edit.
- **Nothing written from elsewhere turns a Machine's steam on.** An edit from "Off" to a steam temperature, like an edit of the steam temperature or time alone, is left out of a Workflow whose steam is off, as before: only a load, or the Machine's own switch, turns its steam on. The plugin enforces it, as a barista may turn steam off after the server plans a write: the server's Loaded Recipe write carries the Recipe's steam temperature and time, and the plugin leaves them out of `PUT /workflow` where the Workflow it has just read has steam off. The answer to such a write holds the Workflow as having taken them, so the write is not planned again until the Recipe's change. The steam flow and milk stop are written as usual, as they do not turn steam on or off. Decent Sync can't tell a Machine that is off because its Recipe held "Off" from one switched off by hand, so both wait the same way: the Machine takes the Recipe's values as its steam is turned back on there, or at its next load. A steam temperature cleared from a Recipe, "Off" included, is each Machine's own again, and nothing is written.
- **Steam turned back on takes the Recipe's.** Turning steam back on at a Machine's own switch takes the Loaded Recipe's steam temperature, which the owner chose on 2026-10-28 (#374), and its steam time, which the owner chose on 2026-11-05 (#394), so the temperature and time steam come back with are no edit where the Recipe holds its own. It is a rule of Decent Sync's own, not an upstream ask: DYE2 saves into a recipe only when asked, so for its own users steam back on with other values only marks the recipe modified, and it is Decent Sync saving every change that would make it an edit. Streamline's heater switch, while Streamline's own DYE2 switch is on, turns steam back on at the steam temperature and time of the recipe the Workflow names already, which the tablet's record of it holds as the Recipe's, those edited while steam was off included (ADR-0021). Steam comes back on with others from that switch with Streamline's DYE2 switch off (`streamline.dye2Enabled`, off by default), which takes the ones Streamline remembers (`last-steam-temp`, `last-steam-duration`, `steamHeaterFor` in `streamline-js:src/modules/api.js`), as a Recipe loaded through DYE2's own dashboard stays loaded, which from v0.2.24 are the ones steam was at as Streamline turned it off (ADR-0021); from its Settings › Calibration › Steam switch, at the temperature and time that page last switched off in Streamline's session, or seeded from the ones Streamline remembers, each where above 0, else the Workflow's where above 0, else 150 °C and 30 s (`setSteamHeaterOn` in `streamline-js:src/settings/settings.js`), which its Save writes into the Workflow; from a steam time set on its main page while steam is off, which brings the heater back with it (`setTargetSteamDuration`); from Auto Steam choosing a pitcher with the heater off, at the temperature Streamline remembers and the pitcher's time (`createAutoSteamSession` in `streamline-js:src/modules/auto-steam-session.js`); and from any other skin or Decaid's own screens. Each takes the Recipe's.
  - **In the plugin, before DYE2's save.** A change of the Workflow naming the Loaded Recipe that turns steam on, its steam temperature at or above `STEAM_ON_FROM` (`steamOnWith` in `plugin/src/loaded-recipe-rules.ts`) where it was below it since the plugin decided on the change before, in any Workflow Decaid reported or answered the plugin's writes with meanwhile, as one turned off and back on while a write of the plugin's was under way, whose changes it decides on together once that is done, is saved as any change is, but in the save's turn, once it has read the Workflow still naming the Recipe, the plugin first writes into it the steam temperature and time the tablet's record of the Recipe holds, read afresh (`steamBackOnFirst` in `plugin/src/loaded-recipes.ts`, `steamBackOnWrite`), and only then calls `record`. It reads the record afresh as DYE2's editor saves a recipe and then applies it again, which turns steam back on with the temperature or time just saved where the Machine's steam was off: those are the Recipe's edit, which a copy read before the save would put back (#395). DYE2 then finds the Workflow's steam temperature and time the record's, and saves only the change's other values, as it does any change's. So the temperature and time steam came back with are never saved into the tablet's record, nor reach the Recipe or another Machine. The Workflow change is held back across both, as for any save, so the server is delivered the Workflow at the Recipe's steam temperature and time, or, where the write waits for a Shot (below), at those steam came back with, which it takes as no edit, as it records no steam setting from a Workflow.
  - **Only the ones it came back with.** Each of the temperature and the time is written only while the Workflow still holds the one steam came back with, and holds another than the record's: one set since, with steam on, is the Recipe's edit, as any steam setting changed while steam is on is, and steam turned off again is no edit, so nothing is written then. One picked in the same change that turns steam on, as on Streamline's Calibration page before its Save, a steam time set on its main page while steam is off, or Auto Steam's pitcher, is replaced too, and the barista changes it after; Auto Steam's flow, which turns nothing on, is saved as any change is.
  - **Not where the Recipe holds none, or "Off".** A Recipe holding no steam temperature has none to take, nor does one holding no steam time: DYE2 saves the temperature or time steam came back with where it moved off the one it had at the apply, as any setting the Recipe holds none of (What DYE2 saves, above), an accepted gap (below). A Recipe holding "Off" has none to take either (`steamBackOnWrite`): its record holds a steam temperature and time of 0, so DYE2 saves what steam came back with into it, which is the Recipe's edit, and the Recipe then holds steam on at those. The other Machines with it loaded stay off, as nothing written from elsewhere turns steam on, until steam is turned on at each, which takes the Recipe's, or the Recipe is loaded again.
  - **Not on a load.** A change that loads a Recipe is no change of the Loaded Recipe, and applying a recipe that holds a steam temperature turns steam on at it (A load switches steam, above): the load write writes the record's where the Workflow holds another (Loading, above), so after it there is nothing for this rule to write. A Recipe applied again while it is loaded is a change, so a copy's steam temperature turning steam on is replaced by the Recipe's.
  - **Beside the previous release.** The rules add nothing to the wire or to the plugin's storage on the tablet, and need no wire revision (ADR-0025): "Off" travels as a steam temperature and a steam time of 0, values both releases already carry in a record and in a Loaded Recipe write. A tablet still running the previous release's plugin, until Decaid updates it, leaves a Recipe's steam temperature and time out of a Workflow whose steam is off as it loads, so only the Skin's own apply turns its steam on there, as DYE2's dashboard and Streamline's strip do; it writes a Recipe's "Off" as a steam temperature of 0 without the steam time beside it where a Skin applied neither, and writes an edit to "Off" from the server as it writes any steam temperature and time into a Workflow whose steam is on. The previous release's server, while it serves beside this one during a deploy, takes "Off" saved on a tablet as no edit and writes the Recipe's steam back over it, as it did before, and refuses a steam temperature of 0 in the management interface; a Recipe this release's server took "Off" into, it writes to tablets with a steam temperature of 0 and no steam time, which DYE2 and Streamline apply as steam off whole all the same.

## Streamline's strip

Streamline's DYE strip applies a recipe from the Workflow its record embeds, its context and Profile, and then the record's own settings (`mergeRecipeLiveSettings` in `streamline-js:src/modules/dyeStrip.js`): from v0.2.29 every steam, hot water and flush setting it holds, whatever its modes, its steam temperature, flush temperature and flush flow among them, which up to v0.2.28 it left to the plugin's load write (decentespresso/streamline-js#154). Its steam is `recipeSteamPatch`'s (`src/modules/steam-mode.js`): the recipe's time and flow, each in the unit its steam mode names or where above 0, and its temperature; a recipe holding a steam time below 1 s, or a steam temperature below 135 °C, turns steam off whole (`steamOffPatch`); and with the heater off, one holding a steam time or a steam temperature turns it on (`steamOnPatch`), at the recipe's values and at the temperature or time Streamline remembers (`last-steam-temp`, `last-steam-duration`) for the one it holds none of, else 150 °C and 30 s. Before the write it keeps the temperature and time to come back to, the Workflow's where the apply turns steam off, and the flow. While an Auto Steam session is active it writes no steam time, flow or temperature (`isAutoSteamActive`). An apply that fails is undone on the strip, its highlight back where it was, with a "Could not apply recipe" notice. From v0.2.25 it clears, as it applies a recipe, what the recipe names none of, whatever its record's Workflow holds (What DYE2 and Streamline do, above), and applies a recipe holding a feed rate. `server/test/fixtures/decaid/streamline-v0.2.31/` holds what it writes with steam on and off.

## During a Shot

The plugin makes no write into the Workflow while its Machine pulls a Shot, which the owner settled on 2026-10-24 (ticket #217). Decaid writes a Workflow's profile to the machine the moment it changes, whatever the machine is doing (`WorkflowDeviceSync._onChange` and `_drain`, which call `setProfile`, in `decaid:lib/src/controllers/workflow_device_sync.dart`), and `setProfile` rewrites the profile's header, every step frame and its tail, which the DE1 runs a Shot from by index. Decaid sends a Bengle the Workflow's yield as it changes too (`BengleSawBridge`), so a yield written mid-Shot moves where that Shot stops. And Decaid stores a Shot with the Workflow as it holds it once the Shot ends, up to its 4 s stopping backstop after the machine leaves `espresso` (`_persistShotIfNeeded` in `decaid:lib/src/controllers/de1_state_manager.dart`), so a write landing first would record values, or a `recipeId`, the Shot was not pulled with. Streamline v0.2.18 holds its own profile switches while the machine is in `espresso` for the same reason (`profileSendBlocked` and `setPendingProfileSend` in `streamline-js:src/modules/profile-send-gate.js`), but nothing guards the plugin's writes, and with every change saved into the Recipe (above), a brew temperature nudged on one Machine would rewrite the frames of a Shot running on another.

- **When.** From the machine state `espresso`, as Decaid's `stateUpdate` reports it (`SHOT_STATE`), until Decaid stores the Shot (`shotStored`), or 10 s after the state left `espresso`, for one Decaid stores nothing of, as a cleaning profile's (`plugin/src/shot-gate.ts`). An unknown state, before the first update or once no machine is connected, is no Shot, as for Streamline: Decaid sends no update as its machine goes, so a read finding no machine ends a Shot once Decaid has reported no state for 3 s.
- **Every write is held.** Not only those that carry a profile: the load write, the write of the Recipe's steam temperature and time as steam is turned back on, the server's Loaded Recipe writes and unloads, its clears of a joining Machine's Workflow, and every other change the server asks for, as a post of DYE2's recipes may clear the Workflow's `recipeId` first. Nothing in the Workflow needs to change during a Shot, and one rule is simpler than telling which writes reach the machine.
- **Only the latest is written.** The plugin holds one load, the latest decided on. It holds the server's change until the Shot ends, or at most two minutes, within the server's wait for an answer, and answers it as asked during a Shot (`PULLING_SHOT`); the server then plans what the tablet is due afresh, so a Recipe edited twice during the Shot is written once, with its latest values.
- **Checked again.** A held write is made as any other, so it first checks that the Workflow still names the Recipe it was for (The plugin's check, above).
- **Nothing lost.** A load held as the plugin stops is kept in Decaid's plugin storage, and made once the plugin loads again, where the Workflow still names that Recipe. The server's changes are planned again on the tablet's next connection. Steam turned back on is not kept, an accepted gap (below).
- **Saving is not held.** DYE2's `record` is no write into the Workflow, so a change made on a Machine during its own Shot is saved into the Recipe at once, and reaches the other Machines straight away, unless they are pulling a Shot too. But once steam is turned back on during a Shot, with a Recipe loaded that holds a steam temperature or time other than the one it came back with, the saves wait with the write of them until the Shot ends, while the Workflow still holds the one steam came back with, as DYE2 would save it (Steam on and off, above), and another recipe applied before then leaves them unsaved, an accepted gap (below).

## Interim: workarounds and accepted gaps

Each workaround here does on DYE2's or Streamline's behalf what an upstream ask would have them do, and goes when they do (AGENTS.md). None stands now: the load write's steam, hot water and flush settings stood in for Streamline's strip applying every one a recipe holds, which it does from v0.2.29 (decentespresso/streamline-js#154, #186). The load write still writes them, as it clears what a Recipe names none of, so that a load ends the same whatever Skin applied it (Loading, above): after DYE2's or Streamline's apply it finds them held, and writes nothing of them.

And these gaps are accepted until fixed upstream:

- A Skin's write of DYE2's list that another write of the whole list overwrites at the same moment, DYE2's, the plugin's or another Skin's, is never heard of: Decaid's store takes no conditional write.
- A record a Skin writes with no Workflow change, as a name edited on its own, or again after DYE2 wrote over it, reaches the server at the plugin's next poll of the tablet's lists, as Decaid's store announces no write: only a Workflow change moving the bean or the profile has the plugin read the recipes at once (A Skin's write of the record, above).
- A Shot begun in the moment between the plugin's check that no Shot runs and its write into the Workflow has the write land in it: the plugin judges a Shot by the state Decaid last reported, and Decaid takes no write conditional on the machine's state.
- A recipe applied from a stale copy during a Shot, and changed on the Machine before the Shot ends, has the copy's values saved into the Recipe with the change: its load, which would bring it to the Recipe's values first, is held, but the save is not, and DYE2 saves every value of the Workflow that differs from the record.
- A recipe applied in the moment between the plugin's last check of the Workflow before a save and DYE2's `record` reading the Workflow has the change saved into it: `record` saves into the recipe the live Workflow names, and takes no recipe it expects to save into. The plugin checks again once its read of the Workflow is answered, so the window is the one request. Steam turned back on in that moment has the temperature and time it came back with saved by that save, which the plugin hears of only after, and so does a barista's Save changes in Streamline made before the plugin's write of the Recipe's lands: `record` saves every value of the Workflow the record holds otherwise.
- A recipe applied again from a stale copy while it is loaded, as a strip button tapped on a Streamline dashboard that has not re-read its recipes, is a change of the Workflow, not a load, so the copy's values are saved into the Recipe. Streamline reads its recipes again on focus, on becoming visible and on the plugin's push after each post of them (ADR-0005), and from v0.2.20 does nothing on a tap of the button its highlight puts on the recipe the Workflow names, so this needs a strip whose highlight has not caught up with the Workflow either, and is rare.
- DYE2 reads the flush temperature and flow from the machine's settings, which Streamline's settings page writes without touching the Workflow. So flush temperature and flow set there reach the Recipe only at that Machine's next Workflow change (decentespresso/streamline-js#154). That page no longer puts its saved values back on the machine as it opens, from v0.2.20 (ADR-0023). And DYE2 keeps a read of the machine's settings 60 s, dropping it only as a recipe is applied or the Workflow's flush settings move (decentespresso/dye2#40, from v0.1.32), so one set there within a minute of DYE2's last read is missed even at that next change, and reaches the Recipe only at a change after the read expires.
- A change made on a Machine between `save-recipe` and the server taking in the record it made is set back by the load that follows, one of a part the recipe names none of cleared with it, as a load takes nothing into the Recipe: a moment as a rule, but while the tablet's plugin cannot reach the server, every change until it reconnects, as the plugin has DYE2 save none into a recipe that is no Recipe yet. The same holds for a recipe made in DYE2's editor and applied before the server took it in. The load is the one such a recipe needs where a Skin applied less than the recipe holds. Telling a record `save-recipe` made from the editor's would rest on the form of DYE2's generated ids, which DYE2 does not promise.
- A recipe `save-recipe` made on a tablet while its plugin could not reach the server, and another applied there before it reconnected, is never loaded, and the Shots pulled with it are linked to no Recipe: the server loads a recipe named before its record arrives only while the Machine's Workflow still names it.
- A steam temperature set in DYE2's editor on a recipe holding "Off", with its steam time left at the 0 "Off" saved beside it, is still "Off": DYE2 applies a steam time of 0 as steam off whole whatever the temperature (`recipeMachineSettings`), so the Recipe keeps "Off" and the record is written back so. A barista sets the steam time with the temperature, or turns steam on at the Machine, which the Recipe then takes (Steam on and off, above).
- A Recipe holding a steam time and no steam temperature, loaded from DYE2's dashboard on a Machine whose steam is off, leaves the heater off with that steam time, as DYE2 applies only what a recipe holds; Streamline's strip turns steam on with it, at the temperature it remembers. Giving a Recipe a steam temperature, or "Off", avoids it.
- A Machine whose steam is off because its Loaded Recipe held "Off" stays off once the Recipe is edited to a steam temperature, as one switched off by hand does, since Decent Sync can't tell the two apart: until its steam is turned on there or the Recipe is loaded again.
- A Recipe holding no steam time takes the one steam comes back with on a Machine, as DYE2 saves it once it moves off the one the Workflow held as the recipe was applied (`movedSinceArming`), 0 where steam was off then: as from Streamline's heater switch, at the time it remembers, else its profile's, else 30 s, or from its Settings page. From v0.2.24 Streamline remembers the time steam was at as it turned it off (decentespresso/streamline-js#191, ADR-0021). So where the recipe was applied while steam was on, and steam is then turned off and back on from Streamline's heater switch, it comes back at the time the Workflow held as the recipe was applied, and the Recipe takes none, as long as Streamline still remembers that time: DYE2 saves a setting the record holds none of only once it moves off the one the Workflow held at the apply (`movedSinceArming`; `server/test/fixtures/decaid/streamline-v0.2.24/heater.json`, `heaterOnRecipe2`, for the time steam comes back at, and `server/test/steam-back-on.test.ts` for nothing saved). Where it comes back at another, the Recipe takes it, which reaches every Machine with it loaded: where the recipe was applied while steam was off, the time Streamline remembers (`record.json`, `recordOnRecipe2`), and where Streamline remembers another time by then, or none, that one, or its profile's or 30 s (`heater.json`, `heaterOnRecipe2NothingRemembered`). Giving a Recipe a steam time avoids it. Up to v0.2.23 Streamline remembered the machine's echo of 0 once it had turned steam off itself, and its heater switch brought steam back at 1 s, which such a Recipe took; that gap went with v0.2.24. A Recipe holding no steam temperature takes the temperature so, as before (Steam on and off, above).
- Steam turned back on is not kept across the plugin's loads, as a held load is (During a Shot, above): a plugin stopped before it has written the Recipe's steam temperature and time, as one updated during the Shot in which steam was turned back on, takes the Workflow as it stands once it loads again, so its next save has DYE2 save the temperature and time steam came back with into the Recipe. Keeping it would hold every save as the plugin loads until it has read Decaid's storage, which can take Decaid's 10 s.
- Steam turned back on during a Shot, with a Recipe loaded that holds a steam temperature or time other than the one it came back with, holds the save of that change's other values, and of every change on the Machine after it, until the Shot ends, while the Workflow still holds the temperature or time steam came back with (During a Shot, above). Where another recipe is applied before the Shot ends, they are saved into no Recipe: DYE2's `record` saves only into the recipe the Workflow names.
- A Recipe whose record holds no Basket takes one picked on a Machine only as DYE2 saves it, which it does only once the Basket moves off the one the Workflow held as the recipe was applied, a starting point DYE2 keeps in memory only (`armedMachine` in `workflowChanged`, `dye2:dye2-plugin/src/plugin.ts`; `movedSinceArming` in `itemPatch`, `dye2:dye2-plugin/src/utils/workflow-record.ts`), as Decent Sync records no Basket itself (Every change is saved into the Loaded Recipe, above). A record holding a Basket takes every change of it, whatever that starting point. From DYE2 v0.1.37 and Streamline v0.2.25 the apply of a recipe naming no Basket clears the Workflow's, so that starting point is none, and any Basket picked moves off it.
  - **Saved late.** One picked in the seconds after an apply, before DYE2 has noted its starting point, as it first reads the machine's settings afresh, which its `record` does not wait for (`handleRecord`), and one whose save failed, reach the Recipe at that Machine's next change saved into it, and never where another recipe is applied, or the profile changed, first.
  - **Not saved.** One picked and not yet saved as DYE2 resets its starting point to the Workflow as it stands is never saved. DYE2 resets it as it reloads, on every update of it, and as the recipe is named again on its own profile after a change of profile (decentespresso/dye2#38), as when the server writes an edited Profile into the Workflow. Nor is the Basket a Machine had as the recipe was applied, picked there again after the Recipe's Basket was cleared, in the management interface or DYE2's editor, while it was loaded, or after the load write cleared it where a Skin that clears nothing applied a recipe naming none over it. The Recipe then takes a Basket from that Machine only once a different one is picked.

## Rejected

We first worked the Loaded Recipe out by matching the Workflow against the Location's Recipes, on profile, dose, yield, grinder and grind setting, and read every Workflow change while one was loaded as an edit of it. Once DYE2 selected recipes and recorded every change into them, from #177, we rejected keeping that, and rejected recording the Workflow ourselves: the two would be separate models of the same thing, which disagree, and two recorders of one change count it twice or disagree about it. DYE2 then stopped recording on its own, from v0.1.23, and dropped its stored selection in v0.1.25 (decentespresso/dye2#36). So Decent Sync now follows the recipe DYE2's own field names, has DYE2 save each change through the call its own skin makes, and records itself only what DYE2 saves none of. We still reject two recorders of one field: Decent Sync records a dose, yield, grind setting, RPM or feed rate only while the Recipe holds none, which DYE2 does not save, and never the Basket, the brew temperature, steam, hot water or flush settings, which DYE2 does; and it keeps no selection of its own beside DYE2's field. The grind setting and RPM a Grinder's pick left are the one place both record: Decent Sync takes them with the Grinder, which DYE2 saves none of, as the pick is one change, and DYE2 saves the same two values where its record holds one and the pick left one, so the two never disagree, while only Decent Sync records the pick leaving none. So we rejected keeping the server's recording of a Basket picked after the load, which DYE2 saves from v0.1.33, as a backstop for one DYE2 saves late or never (Interim, below): it made the server a second recorder of every pick, though it changed something only then, as the plugin reports the recipes DYE2 saved before it delivers the Workflow change.

We rejected keeping the load's taking, once DYE2 and Streamline cleared as they apply (#550): the apply's write lands first, so a load would take only from a Skin that clears nothing, or a yield of 0, and a Recipe would then hold what the last Machine happened to have, or not, by the Skin that applied it. We rejected leaving the clearing to each Skin, as Decent Sync would then rest on every Skin doing it, and the previous release's plugin and a record saved before v0.1.37 show that some do not. We rejected a pass rewriting every tablet's records to v0.1.40's embedded Workflow: Streamline clears whatever the record holds, and the load write covers the rest. And we rejected reading a yield of 0 as a yield, which a Recipe holding none would take on its load, and a Shot would show as its target.

We rejected saving into the Recipe only when a barista asks, as DYE2 and Streamline now do, because Shots would record a dial the other Machines no longer have, and a barista forgetting to save would leave them grinding at the old setting. We rejected writing a Loaded Recipe's value back over any part the Workflow holds otherwise, as the server did until #216: it undid every change DYE2 had not saved, and would undo what stays the Machine's own. We rejected unloading the Recipe on another batch, as DYE2 did until v0.1.25 (decentespresso/dye2#19): a fresh bag of the same roast is the same dial, and a batch of another Bean is the Recipe's new Bean (#570). We also rejected telling a stale copy applied by matching its values against the Recipe's earlier ones, as the server did until #190 and, for the hot water the Workflow edited, until #173: it cannot tell a barista choosing a value from an old copy being applied, and wrote back a flush time a barista set deliberately.

We rejected keeping a batch of another Bean the Machine's own, as from #216 until #570: a Skin's bean dialog changing the Recipe's Bean then changed it only through the record, heard of at the plugin's poll, and the same pick changed the Recipe on one Skin and left it alone on another. We rejected reading DYE2's recipes on every Workflow change, which after a run of stepper changes adds a read per save that finds nothing new, and narrowed it to the bean and the profile. We rejected taking a Tablet's pick of what the Library retired as the management interface takes an edit, adding the batch at the Location and offering its Bean there: the Archive or finish is the later decision, and a Machine still holding the bag undoes neither. We rejected a rename rule in the server, which would rename a Recipe edited in the management interface or over the MCP endpoint, and letting a record's `beanBatchId` win over its `beanId`, which DYE2's editor saves together.

We rejected keeping steam on and off each Machine's own whatever its Recipe held, as from 2026-10-16 until #616: DYE2's dashboard, and Streamline's strip from v0.2.29, switch steam as the recipe holds it, so the load write leaving a steam temperature out of a Workflow whose steam was off changed nothing after either, and the server writing the Recipe's steam back over "Off" saved in DYE2's editor left the Machine it was saved on off and its record saying on. We rejected holding "Off" as a field of its own beside the steam temperature, which every reader of a Recipe would have to combine with it, and clearing the Recipe's steam time as it takes "Off", which would lose the time to come back to. And we rejected having an edit from "Off" to a steam temperature turn steam on at every Machine with the Recipe loaded: a Machine switched off by hand, as one being descaled, would be turned on from elsewhere.

We rejected turning steam back on at the Recipe's steam temperature and time in the server's Loaded Recipe write, which carries them already, and which the plugin leaves out of a Workflow whose steam is off, counting it as taken (Steam on and off, above). The server hears of the change only after the plugin has had DYE2 save it, as the plugin reports the recipes DYE2 saved before it delivers the change, so DYE2 would have saved the temperature and time steam came back with into the tablet's record, and the server taken it as the Recipe's edit, before any write of the server's; and keeping DYE2 from saving it needs the plugin to know the rule anyway. We did not ask DYE2 or Streamline for it: neither is at fault, as DYE2 saves into a recipe only when asked.

We rejected sharing only the stored recipes, picked up the next time a barista loads one, because Shots would record a dial the Machine no longer has. We rejected naming the Loaded Recipe anywhere but the Workflow, because Shots pulled while the tablet is offline would then reach the server without their Recipe.

## Consequences

- **A load switches steam.** Loading a Recipe that holds a steam temperature turns the Machine's steam on at it, and one holding "Off" turns it off, whatever applied it, and "Off" saved into a Recipe turns steam off on every Machine that has it loaded. An espresso-only Machine, or one being descaled, loads Recipes holding "Off" or none of steam. Steam turned off at a Machine's own switch still changes nothing else.
- **Every tweak is the Recipe's.** A change on a Machine with a Recipe loaded to its dose, yield, grind setting, brew temperature, RPM, feed rate, Basket, grinder, with the grind setting and RPM its pick left, a batch, of its Bean or another, which becomes its Bean (#570), or a steam, hot water or flush setting changes it on every Machine at the Location. That is the intent: a dose is never changed for one customer. So a one-off Shot of another coffee can no longer be pulled under a Loaded Recipe without changing it. Turning steam off at the Machine, clearing a value or picking a batch the Library retired changes no Recipe, and keeps it loaded, and turning steam back on takes its steam temperature and time, or, where it holds "Off", makes it hold what steam came back with. A Recipe under the name DYE2 generated keeps it as its Bean changes on a Skin with no rule renaming it, as Streamline has none.
- **A Recipe is the whole Shot.** Loading a Recipe leaves the Machine with none of what it names none of: no Bean Batch, Grinder, grind setting, RPM, feed rate, Basket or dose, and stop-at-weight off where it names no yield, so its Shots record none of them. A Recipe made in the management interface without a grinder or Basket no longer gains the Machine's as it loads: a value a barista sets or picks once it is loaded is a change like any other, which it takes, a batch with its Bean. Only the steam, hot water and flush settings it holds none of stay each Machine's own. A part cleared from a Recipe is cleared on every Machine that has it loaded.
- **Only an applied recipe is loaded.** Dialling in a Recipe's values by hand loads nothing. A profile change unloads it, and so does a favourite applied.
- **DYE2 is required.** A Machine without DYE2 has no Loaded Recipe, and one with a DYE2 older than v0.1.40 is not supported (ADR-0017). Nothing falls back to matching. The plugin still writes the recipe lists to every sharing tablet (ADR-0005).
- **The plugin writes more of the tablet.** Beyond the clearing on joining (ADR-0008), it writes a Loaded Recipe's values into the Workflow, clears `recipeId` there, has DYE2 save into its recipes, and writes each recipe record's embedded Workflow, with its batch, its profile at the Recipe's brew temperature and the settings the Recipe holds. A skin that remembers the steam, hot water and flush settings takes them as its own (ADR-0021).
- **Shots name their Recipe, and record its Basket.** Each Shot carries `recipeId` as it was pulled, and the Recipe's batch, grinder, Basket and RPM. A Shot is linked to the Recipe its tablet's map holds under that id, kept while it names the same id, only where its Machine had that Recipe loaded when it was pulled: a Capture-only Machine's Shots name a recipe that was never its Loaded Recipe. A Shot naming a record the map does not hold yet is linked once it does; one naming none has none. So Analytics (milestone 7) needs no inferred recipes.
