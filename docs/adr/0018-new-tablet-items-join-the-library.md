# New items from a tablet join the Library, and Beans are matched by roaster and name

An item a barista creates on a tablet of a Machine that takes part at a Location, which reaches the server without a global id (ADR-0006), joins the Library as a new item. Two kinds are matched instead of added. A Profile keeps Decaid's id, a hash of what the machine executes, which is the same on every tablet, so an identical Profile is already the same Profile. A Bean whose roaster and name match a Bean in the Library that is not Archived, ignoring case and white space at either end, is linked to that Bean, because the glossary identifies a Bean by roaster and name: when Uptown and Belmont both enter a new coffee on its launch day, it is one Bean. Bean Batches and Grinders are never matched. Two batches of one Bean can be roasted on the same day, and two grinders of one model at a Location are two Grinders.

A Machine that joins a Location brings nothing it holds of its own. A Location already defines what it offers, and moving a Machine there, or turning its sharing back on after an experiment, does not bring new equipment or coffee with it. Its tablet's records of items the Library has are those items, a Bean matched by roaster and name and a Profile by its id, and are written the Location's state. Every other record it holds stays out of the Library and is archived or hidden on the tablet, never deleted, so its Shots still find it. The exception is a kind of item the Location offers none of yet, such as at a cafe's first Machine: the joining Machine brings its own items of that kind that its tablet offers, not those archived or hidden there, as it brings its steam, hot water and rinse settings to a Location that has none (ADR-0014). A record left out joins the Library only if a barista un-archives or shows it on the tablet afterwards, as if it were entered then.

We rejected keeping a joining Machine's own items on its tablet unarchived, which would offer items the Library lacks there. We also rejected adding them all to the Library and listing them on the Machine's page so an Admin could Archive duplicates, which the first version of this decision did: it made a Location's Library grow with whatever a joining tablet held, an experiment made while capture-only included. Holding its sharing until an Admin reviewed its items would make adopting a used tablet wait on someone.

## Consequences

- **Links are made once.** A Bean is matched by roaster and name only when the server first sees it. An edit that later gives two Beans the same roaster and name, such as a rename, flags them as likely duplicates and doesn't merge them: merging two Beans that each have batches and Shots can't be undone cleanly.
- **A linked record takes the Library's content.** A tablet's Bean linked to an existing Bean is overwritten with that Bean's content. When a barista entered it while the tablet took part, each field where the two differed becomes a Conflict (ADR-0020), so nothing is dropped silently. When the tablet held it as it joined a Location, the Location's state wins and no Conflict is kept; the tablet's records are still captured as sent.
- **A joining tablet's Shots may name items the Library lacks.** A Shot pulled before its Machine joined names the tablet's own batch or grinder, which is left out. The Shot is captured as sent, so it still shows what Decaid recorded, such as the coffee's name and the grinder's model.
