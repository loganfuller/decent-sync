# New items from a tablet join the Library, and Beans are matched by roaster and name

An item a barista creates on a tablet of a Machine that takes part at a Location, which reaches the server without a global id (ADR-0006), joins the Library as a new item. Two kinds are matched instead of added. A Profile keeps Decaid's id, a hash of what the machine executes, which is the same on every tablet, so an identical Profile is already the same Profile. A Bean whose roaster and name match a Bean in the Library that is not Archived, ignoring case and white space at either end, is linked to that Bean, because the glossary identifies a Bean by roaster and name: when Uptown and Belmont both enter a new coffee on its launch day, it is one Bean. Baskets and Tools are matched by name in the same way, because a Basket is a model rather than one basket, and DYE2 itself refuses a second tool of the same name: when two cafes enter the 20 g high-flow basket, it is one Basket. Bean Batches, Grinders and Recipes are never matched. Two batches of one Bean can be roasted on the same day, two grinders of one model at a Location are two Grinders, and two recipes for one coffee are two dials.

A Machine that joins a Location brings nothing it holds of its own. A Location already defines what it offers, and moving a Machine there, or turning its sharing back on after an experiment, does not bring new equipment or coffee with it. Its tablet's records of items the Library has are those items, a Bean matched by roaster and name and a Profile by its id, and are written the Location's state. Every other record it holds stays out of the Library and is archived or hidden on the tablet, never deleted, so its Shots still find it. DYE2's records can't be archived or hidden, so a joining Machine's own recipes, baskets and tools are removed from its lists instead (ADR-0005) and not kept: a Machine that took part in no Location, or was capture-only, was used for experiments not meant to be kept. The exception is a kind of item the Location offers none of yet, such as at a cafe's first Machine: the joining Machine brings its own items of that kind that its tablet offers, not those archived or hidden there, and every recipe its tablet holds, each keeping its id there and its Recipe Slot (ADR-0005). A Location has no Recipes for this while it has none but Archived ones. A record left out joins the Library only if a barista un-archives or shows it on the tablet afterwards, as if it were entered then.

We rejected keeping a joining Machine's own items on its tablet unarchived, which would offer items the Library lacks there. We also rejected adding them all to the Library and listing them on the Machine's page so an Admin could Archive duplicates, which the first version of this decision did: it made a Location's Library grow with whatever a joining tablet held, an experiment made while capture-only included. Holding its sharing until an Admin reviewed its items would make adopting a used tablet wait on someone.

## Consequences

- **Links are made once.** A Bean is matched by roaster and name only when the server first sees it. An edit that later gives two Beans the same roaster and name, such as a rename, flags them as likely duplicates and doesn't merge them: merging two Beans that each have batches and Shots can't be undone cleanly.
- **A linked record takes the Library's content.** A tablet's Bean linked to an existing Bean is overwritten with that Bean's content. When a barista entered it while the tablet took part, each field where the two differed becomes a Conflict (ADR-0020), so nothing is dropped silently. When the tablet held it as it joined a Location, the Location's state wins and no Conflict is kept; the tablet's records are still captured as sent.
- **A joining tablet's Shots may name items the Library lacks.** A Shot pulled before its Machine joined names the tablet's own batch or grinder, which is left out. The Shot is captured as sent, so it still shows what Decaid recorded, such as the coffee's name and the grinder's model.
