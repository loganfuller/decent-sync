# Interim: sync recipes, baskets and tools by writing DYE2's storage

Decaid has no Recipes or Equipment resource: there is none in v0.9.0, and decaid#727, which proposed an equipment resource, was closed unmerged. Recipes, baskets and tools exist only in DYE2's plugin storage, under `dye2.reaplugin` as `recipes`, `baskets` and `equipment` (DYE2's name for its tools). DYE2's KV contract says DYE2 is the only writer. DYE2's plugin also saves a barista's later changes into the recipe the Workflow names when asked (`record`), as Streamline's DYE strip asks on Save changes and the plugin after each change (ADR-0022), and makes a recipe of the live Workflow (`save-recipe`), which Streamline's strip asks from its long-press menu. Until Decaid has native resources (proposed upstream), the Decent Sync plugin reads and writes these keys itself, without needing DYE2 to change. That knowingly goes beyond the convention. It's safe enough because every writer re-reads the list before saving and replaces only its own item, so items written by someone else survive.

DYE2's recipe ids are opaque: its editor gives a new recipe a UUID, and `save-recipe` an id `recipe-…`. A recipe's Recipe Slot is a field of its own, `stripSlot`, 1 to 5, the button of Streamline's DYE strip it is on (`recipeStripCells` in `streamline-js:src/modules/dye-selection.js`), or null for none, so a slot is shared by every Machine at a Location ("Uptown slot 3"), and a Location has five. DYE2 keeps a library of any number of recipes, five of them on the strip, and its Select Recipe page lists and applies them all. So each Recipe has one record id, the same on every tablet at its Location, which never changes (`recipes.record_id`): for a Recipe created on a tablet, the id DYE2 gave it there; for one created in the management interface, or copied there, a new UUID; and for one that existed before DYE2 v0.1.25, the id its records had then, its slot number, as DYE2 gave the records with ids `1` to `5` their `stripSlot` once, as it loaded (`migrateRecipeSlots`); and a Recipe restored from Archived keeps its own, unless another Recipe there has taken it since, when it is given a new one. Recipes in a slot above 5 then left their slot, and stayed at their Location. A slot-number id can so pass to another Recipe as a Machine moves to another Location, or a joining tablet's own recipes are replaced, which the plugin unloads first (ADR-0022). The plugin writes every Recipe of the Location that is not Archived into each tablet's list, under its record id, with its slot as `stripSlot`, null for one in none, keeping the order the tablet holds them in and adding a new one at the end. A write putting a record in a slot clears `stripSlot` on the slot's previous holder in the same post, as DYE2's editor does (`takeSlot` in `dye2:dye2-plugin/src/utils/dev-api.ts`), since DYE2 de-duplicates slots only once, and Streamline places the first record it finds for a slot. It translates the bean, profile, grinder, basket and tool ids inside each recipe into the tablet's own, and regenerates the fields DYE2 derives from the rest (`title`, `subtitle` and the embedded `workflow`, with the Bean's name and roaster and the batch, the full Profile at the Recipe's brew temperature, and the steam, hot water and flush settings the Recipe holds, ADR-0022), as DYE2's own record builder does, so a recipe applies the same on every tablet, including one where its Profile is hidden. Each record also carries its Library id in a top-level field of its own, which DYE2 and Streamline keep when they save, as `extras` does for Decaid's records (ADR-0006). Grinders sync through Decaid's own grinders API instead.

These records have no edit time. Baskets and tools carry only `createdAt`, and a recipe's `capturedAt` is rewritten by DYE2's editor but not when DYE2 saves dial-in changes into it. So an edit is timed when the plugin first reads it, not last-writer-wins on `capturedAt`. DYE2 has no archived or hidden flag either, and no way to delete a basket, so an item a tablet's Location stops offering is removed from that tablet's list rather than archived or hidden on it (ADR-0008). Shots keep the basket and tool names DYE2 stored on them, so they still read correctly. A key never written reads as `null`, which DYE2 treats as an empty list, and so does the plugin: it writes these lists to every sharing tablet, whether or not DYE2 is installed there, so installing DYE2 later finds them ready. If the plugin reads a list in a shape it doesn't recognise, it stops writing that list on that tablet and shows it in the Machine's sharing status, rather than risk corrupting DYE2's data; the tablet's other lists keep syncing.

We rejected waiting for DYE2's maintainer to accept a sync-aware contract, and running a DYE2 fork, because either would tie this project's progress to someone else's release schedule.

Milestones 1 and 2 capture these keys read-only. Milestone 3 writes them. The plugin is built in this repo under ADR-0012; the old `decent-sync-plugin` repo is archived.

## Consequences

- **A Recipe holds what a DYE2 recipe does, but who pulls it.** Its Bean Batch is DYE2's own `beanBatchId`, beside the Bean and its roaster (decentespresso/dye2#27), which DYE2 applies with them, a recipe naming a Bean and no batch clearing the Workflow's. A batch picked with the Bean in DYE2's editor is the Recipe's. A barista picking a Bean there with no batch, or with one of another Bean, keeps the Recipe's batch if it is of that Bean, and otherwise gives it that Bean's batch most recently added at the Location. It holds every steam, hot water and flush setting DYE2's recipe does (decentespresso/dye2#23), each in DYE2's own field of it, and in partial `steamSettings`, `hotWaterData` and `rinseData` of the embedded Workflow, as DYE2's record builder writes them; one the Recipe holds none of is written blank, so applying the recipe leaves the Machine's own (ADR-0022). Its steam and hot water modes are DYE2's display choice, taken in and written but applied to nothing. It holds no barista or drinker: the plugin writes them blank, so loading a recipe never changes who the Workflow says is pulling.
- **Tablet copies can be stale.** DYE2's pages read the lists once, when they open, and Streamline's DYE strip as the dashboard loads, regains focus or becomes visible, or returns from DYE2. Streamline's builds with live plugin notifications (decentespresso/streamline-js#120 and #127, from v0.2.14) also re-read them when the plugin tells them it has written the recipes, so a dashboard left visible shows a Recipe added, edited, moved or taken out of its slot: the plugin answers Streamline's `skin` endpoint with only a WebSocket endpoint to listen on, and pushes there after each post of `recipes` Decaid takes (`plugin/src/skins.ts`). Decaid keeps no push for a socket opened later, so a dashboard hidden at the time, or a skin without live notifications, catches up as it would anyway, on focus, visibility or load. A field of a Basket or Tool that a tablet's save sets back to the value that tablet held just before the server's latest write to it is taken as unchanged, and the server's value is written back (`before_write`), as DYE2's editor saves the basket and tool lists whole (`updateBasket`, `updateEquipment`). The cost: a barista who deliberately sets such a field back to exactly that value has it written back, and has to set another value first. Recipe records have no such rule: DYE2's editor saves only the fields changed over a fresh read of the recipe (decentespresso/dye2#28, `updateRecipe`), and its dashboard sends only its own edits over a fresh read of the Workflow (decentespresso/dye2#31), so neither sends back a value read before an edit made elsewhere. A saved 0 is a value, as a milk stop of 0 is off: DYE2 saves a blank field as `null` (decentespresso/dye2#29), which the server takes as holding none. Loading a stale copy is covered by ADR-0022.
- **A narrow window remains.** Decaid's store has no conditional write. If DYE2 rewrites a list, from one of its pages or as it saves dial-in changes, between the plugin's read and its write, or the plugin between DYE2's, one side's change is lost. The plugin's own calls of DYE2's `record` wait their turn among its reads and writes of the lists, so they never race its posts (ADR-0022), but a save asked from Streamline, or a page of DYE2's, can. Where the plugin's write is lost, it finds that on its next read, and the server writes its version again. Where DYE2's is, the plugin cannot see it: DYE2 saves it again at the plugin's call after the Workflow's next change, as it compares every field the record holds, but for the brew temperature, which it saves again only once it moves again.
- **A Machine joining a Location** takes on its Location's Recipes (ADR-0008), and its own recipes, baskets and tools are dropped unless the Location has none of that kind yet (ADR-0018), its recipes then keeping their ids and slots.
- **Upstream asks.** Answered on the supported floor (ADR-0017): a blank field saved as none rather than 0 (decentespresso/dye2#29), every steam, hot water and flush setting (decentespresso/dye2#23) and the batch its picker chose (decentespresso/dye2#27) held in a recipe, the recipe a Workflow is dialled in to named in the Workflow (decentespresso/dye2#20, #36), a recipe read again before it is applied or saved, only the fields changed saved (decentespresso/dye2#28), and DYE2's dashboard reading the Workflow again before each send (decentespresso/dye2#31). DYE2's own saving of dial-in changes, which keeps a recipe's embedded Workflow context current, answered the asks made of Streamline's auto-save. Streamline's refresh of the strip when the plugin pushes a change (decentespresso/streamline-js#120 and #127) answered the ask to refresh its recipes. The asks the Loaded Recipe waits on are ADR-0022's.
