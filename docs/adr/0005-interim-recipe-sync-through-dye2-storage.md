# Interim: sync recipes, baskets and tools by writing DYE2's storage

Decaid has no Recipes or Equipment resource: there is none in v0.9.0, and decaid#727, which proposed an equipment resource, was closed unmerged. Recipes, baskets and tools exist only in DYE2's plugin storage, under `dye2.reaplugin` as `recipes`, `baskets` and `equipment` (DYE2's name for its tools). DYE2's KV contract says DYE2 is the only writer. Since v0.1.20, DYE2's plugin also records a barista's later changes into the recipe they applied, from DYE2's dashboard or Streamline's DYE strip (ADR-0022); Streamline writes `recipes` itself only with an older DYE2 that does not record, which Decent Sync does not support (ADR-0017). Where its post of the applied recipe to DYE2 fails, Streamline at `c006dac` tries it again rather than writing the recipe itself (decentespresso/streamline-js#148). Until Decaid has native resources (proposed upstream), the Decent Sync plugin reads and writes these keys itself, without needing DYE2 to change. That knowingly goes beyond the convention. It's safe enough because every writer re-reads the list before saving and replaces only its own item, so items written by someone else survive.

DYE2's recipe ids are slot numbers, so a slot number is shared by every machine at a location ("Uptown slot 3"). The plugin writes each Location's slotted Recipes into the list in slot order, under their slot numbers, with no limit at five: DYE2's dashboard and Streamline's strip list every recipe, and only DYE2's recipe editor stops at five. It translates the bean, profile, grinder, basket and tool ids inside each recipe into the tablet's own, and regenerates the fields DYE2 derives from the rest (`title`, `subtitle` and the embedded `workflow`, with the full Profile at the Recipe's brew temperature, ADR-0022), so a recipe applies the same on every tablet, including one where its Profile is hidden. Each record also carries its Library id in a top-level field of its own, which DYE2 and Streamline keep when they save, as `extras` does for Decaid's records (ADR-0006). Grinders sync through Decaid's own grinders API instead.

These records have no edit time. Baskets and tools carry only `createdAt`, and a recipe's `capturedAt` is rewritten by DYE2's editor but not when DYE2 records dial-in changes. So an edit is timed when the plugin first reads it, as a steam setting edit is (ADR-0014), not last-writer-wins on `capturedAt`. DYE2 has no archived or hidden flag either, and no way to delete a basket, so an item a tablet's Location stops offering is removed from that tablet's list rather than archived or hidden on it (ADR-0008). Shots keep the basket and tool names DYE2 stored on them, so they still read correctly. A key never written reads as `null`, which DYE2 treats as an empty list, and so does the plugin: it writes these lists to every sharing tablet, whether or not DYE2 is installed there, so installing DYE2 later finds them ready. If the plugin reads a list in a shape it doesn't recognise, it stops writing that list on that tablet and shows it in the Machine's sharing status, rather than risk corrupting DYE2's data; the tablet's other lists keep syncing.

We rejected waiting for DYE2's maintainer to accept a sync-aware contract, and running a DYE2 fork, because either would tie this project's progress to someone else's release schedule.

Milestones 1 and 2 capture these keys read-only. Milestone 3 writes them. The plugin is built in this repo under ADR-0012; the old `decent-sync-plugin` repo is archived.

## Consequences

- **A Recipe holds more than a DYE2 recipe, and less.** It names a Bean Batch, which a DYE2 recipe can't: the plugin keeps the batch in the record's field of its own, beside DYE2's `beanId` for its Bean. A barista picking a Bean in DYE2's editor keeps the Recipe's batch if it is of that Bean, and otherwise gives it that Bean's batch most recently added at the Location. A Recipe holds all four hot water settings where DYE2 keeps one, and the plugin applies the rest when the Recipe is loaded (ADR-0022). It holds no barista or drinker: the plugin writes them blank, so loading a recipe never changes who the Workflow says is pulling. The steam and flush values DYE2 keeps in a recipe are written as the Location's (ADR-0014).
- **Tablet copies can be stale.** DYE2's pages read the lists once, when they open, and Streamline's DYE strip as the dashboard loads, regains focus or becomes visible, or returns from DYE2. Streamline's builds with live plugin notifications (decentespresso/streamline-js#120 and #127, from v0.2.14) also re-read them when the plugin tells them it has written the recipes, so a dashboard left visible shows a Recipe added, edited, moved or taken out of its slot: the plugin answers Streamline's `skin` endpoint with only a WebSocket endpoint to listen on, and pushes there after each post of `recipes` Decaid takes (`plugin/src/skins.ts`). Decaid keeps no push for a socket opened later, so a dashboard hidden at the time, or a skin without live notifications, catches up as it would anyway, on focus, visibility or load. DYE2's editor saves every field as its page loaded it. So a field that a tablet's save sets back to the value that tablet held just before the server's latest write to it is taken as unchanged. A barista who deliberately sets a field back to exactly that value has to set it again. Loading a stale copy is covered by ADR-0022.
- **A narrow window remains.** Decaid's store has no conditional write. If DYE2 rewrites a list, from one of its pages or as it records dial-in changes, between the plugin's read and its write, or the plugin between DYE2's, one side's change is lost. Where the plugin's write is lost, it finds that on its next read, and the server writes its version again. Where DYE2's is, the plugin cannot see it: DYE2 records it again only at the Workflow's next change, as it compares every field the record holds, but for the brew temperature, which it never records again.
- **A Machine joining a Location** takes on the Recipes in its slots (ADR-0008), and its own recipes, baskets and tools are dropped unless the Location has none of that kind yet (ADR-0018).
- **Upstream asks.** DYE2: save a blank field as absent rather than 0 (decentespresso/dye2#29); hold every steam, hot water and flush setting (decentespresso/dye2#23), and the batch its picker chose (decentespresso/dye2#27), in a recipe; record the selected recipe in the Workflow (decentespresso/dye2#20); and re-read a recipe before applying or saving it, saving only the fields changed (decentespresso/dye2#28). DYE2's own recording of dial-in changes, which keeps a recipe's embedded Workflow context current, answered the asks made of Streamline's auto-save. Streamline's refresh of the strip when the plugin pushes a change (decentespresso/streamline-js#120 and #127) answered the ask to refresh its recipes.
