# The Live View streams over Server-Sent Events, relayed between instances through PostgreSQL

The Live View shows what a Machine is doing and measuring as it happens, which the management interface's polling (ADR-0009: REST for everything but the plugin) can't do smoothly. The browser reads it as a Server-Sent Events stream from an ordinary GET route, so the session cookie and the guards of the rest of the REST API apply unchanged. While any viewer's stream for a Machine is open, the server asks the plugin holding that Machine to stream, and tells it to stop once the last viewer has gone. The plugin forwards Decaid's frames as sent, tagged with their source and the time the plugin received them: the `stateUpdate` event it already receives, and Decaid's local water levels, scale, shot settings, devices and sensor sockets, which it opens only while streaming, as `stateUpdate` carries no scale weight or water level (`MachineSnapshot.toJson` in `decaid:lib/src/models/device/machine.dart`). Nothing is stored: samples skip the outbox, are never acknowledged, are dropped under backpressure or while disconnected, and are never replayed after a reconnect. The finished Shot and Steam Record still arrive as before.

Live frames have a budget of their own, so they never take the room in Decaid's 1 MiB transport queue that the outbox, `hello` and heartbeats rely on. Decaid accepts a frame as soon as it is queued, so the plugin can't see what is still unsent: it counts the live bytes it has sent that the server hasn't yet said it received, and while over budget it holds only the latest frame of each source. The server says so with `liveReceived`, at most once a second as live frames arrive, carrying the bytes of them it has received on the connection. A count of the bytes sent since the last `liveReceived` would hold only on a stalled link: on one slower than the frames, each `liveReceived` would free the whole budget, and the frames would pile up in Decaid's queue (#269). The server handles a live frame as it arrives, not behind the connection's deliveries, and a failure to relay one never closes the connection.

Across instances, each open stream holds a lease on its Machine in PostgreSQL, renewed every 10 s while the stream stays open, and set to expire 30 s after the stream closes, by PostgreSQL's clock, so a reload within that linger continues the stream and a lost instance's leases lapse on their own. A new lease, and one a renewal finds gone and puts back, is announced with `NOTIFY`. The instance holding the Machine starts the plugin streaming while any lease is unexpired and stops it once none is, deciding one change at a time for each connection, and checks the leases when one is announced, after it welcomes a plugin, at the earliest expiry, and for each of its connections when it starts listening again, so a plugin that reconnects to another instance resumes at once. That instance relays each frame on one `NOTIFY` channel, outside any transaction, one at a time for each connection, with the latest frame of each source waiting, and every instance forwards it to its own viewers of that Machine. A frame whose notification would pass the 8000-byte payload limit is dropped, by the plugin before it is sent. Each renewal checks the viewer's session again and closes the stream once it has ended, so a signed-out or deactivated account stops receiving within a renewal.

## Considered Options

- **A browser WebSocket.** Rejected: the stream is one-way, and a raw upgrade bypasses the Nest guards, so it would need its own session check.
- **Polling once a second.** No new transport, but the curves of a Shot in progress would be choppy, and every viewer would add a request a second.
- **Routing each viewer to the instance holding the Machine,** such as with fly.io's `fly-replay`. Rejected: it works only on fly.io, and Decent Sync is self-hosted elsewhere too.
- **Interest announced only by repeated notifications, held in each instance's memory.** No table, but the interest is shared across connections, which ADR-0016 keeps in PostgreSQL, and a plugin that reconnects to another instance would wait for the next announcement.
- **Redis pub/sub for the samples and expiring keys for the leases.** ADR-0016 rejected Redis because an announcement could be lost between a commit and a publish. That doesn't apply to samples, which belong to no transaction, and Redis suits fast, throwaway fan-out. Rejected all the same: every self-hoster would have to run a second service for the Live View, or Decent Sync would keep two paths. Revisit if live samples reach hundreds a second, such as with a Location's Machines shown live together, or measurements show `NOTIFY` contention or listeners falling behind; a change would amend ADR-0016.

## Consequences

- **ADR-0009 is amended.** The server also pushes to the management interface, one way, over Server-Sent Events. The plugin still speaks to the server only over its WebSocket.
- **ADR-0016 is amended.** `NOTIFY` also carries data that belongs to no transaction, sent outside one: a live frame lost to a crash costs nothing, as the next one replaces it.
- **Samples share PostgreSQL's notification lock and queue.** A transaction that sends a `NOTIFY` takes a lock shared by every database in the cluster as it commits, so live samples briefly queue with every other notification there, those of other databases on a shared cluster included. At Roux's scale, a handful of Machines at a DE1's few samples a second, this is far from a limit. Notifications are not written to the write-ahead log.
- **Every instance receives every sample,** whether or not it has a viewer of that Machine.
- **The stream keeps itself alive.** It sends a comment when it has had nothing to send for 15 s, as an offline or sleeping Machine sends nothing, so proxies such as fly.io's don't close it as idle. The browser's `EventSource` reconnects by itself. Shutting down an instance ends its open streams.
- **A browser's connections to one server are limited.** Over HTTP/1.1 a browser holds at most six, and each open Live View holds one. A page showing several Machines live, such as the deferred Location page, should take them in one stream rather than one per Machine.
- **The plugin's transports.** Decaid allows a plugin eight transports (`maxTransportsPerGeneration`; `decaid:doc/Plugins.md`, Resource bounds; `docs/AI_RUNTIME_NOTES.md`). The local sockets count with the plugin's other transports and always leave one free for the server connection, as DYE2's socket does, so a steady connection holds at most seven: its connection to the server, DYE2's `changed` socket and five of Decaid's local sockets.
- **Samples may wait behind a delivery on the tablet.** They share the plugin's WebSocket, so a sample can wait a moment behind a large Shot frame in Decaid's queue.
- **Tests.** The relay and the leases are tested with two instances on one database (`startTestServer({ sharing })`).
