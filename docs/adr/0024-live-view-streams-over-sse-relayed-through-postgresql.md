# The Live View streams over Server-Sent Events, relayed between instances through PostgreSQL

The Live View shows what a Machine is doing and measuring as it happens, which the management interface's polling (ADR-0009: REST for everything but the plugin) can't do smoothly. The browser reads it as a Server-Sent Events stream from an ordinary GET route, so the session cookie and the guards of the rest of the REST API apply unchanged. While any viewer's stream for a Machine is open, the server asks the plugin holding that Machine to stream, and tells it to stop once the last viewer has gone. The plugin forwards Decaid's frames as sent, tagged with their source: the `stateUpdate` event it already receives, and Decaid's local water levels, scale, shot settings, devices and sensor sockets, which it opens only while streaming, as `stateUpdate` carries no scale weight or water level (`MachineSnapshot.toJson` in `decaid:lib/src/models/device/machine.dart`). Nothing is stored: samples skip the outbox, are never acknowledged, are dropped under backpressure or while disconnected, and are never replayed after a reconnect. The finished Shot and Steam Record still arrive as before.

Across instances, each open stream holds a lease on its Machine in PostgreSQL, renewed every few seconds while it stays open and expiring by PostgreSQL's clock some 30 s after its last renewal, so a reload or a lost instance stops the stream only after that linger. A new lease is announced with `NOTIFY`. The instance holding the Machine starts the plugin streaming while any lease is unexpired, and checks the leases again when one is announced, when a plugin sends `hello`, and when the earliest one expires, so a plugin that reconnects to another instance resumes at once. That instance relays each frame on one `NOTIFY` channel, and every instance forwards it to its own viewers of that Machine. A frame too large for a notification's 8000-byte payload is dropped. Each renewal checks the viewer's session again and closes the stream once it has ended, so a signed-out or removed account stops receiving within a renewal.

## Considered Options

- **A browser WebSocket.** Rejected: the stream is one-way, and a raw upgrade bypasses the Nest guards, so it would need its own session check.
- **Polling once a second.** No new transport, but the curves of a Shot in progress would be choppy, and every viewer would add a request a second.
- **Routing each viewer to the instance holding the Machine,** such as with fly.io's `fly-replay`. Rejected: it works only on fly.io, and Decent Sync is self-hosted elsewhere too.
- **Interest announced only by repeated notifications, held in each instance's memory.** No table, but the interest is shared across connections, which ADR-0016 keeps in PostgreSQL, and a plugin that reconnects to another instance would wait for the next announcement.
- **Redis pub/sub for the samples and expiring keys for the leases.** ADR-0016 rejected Redis because an announcement could be lost between a commit and a publish. That doesn't apply to samples, which belong to no transaction, and Redis suits fast, throwaway fan-out. Rejected all the same: every self-hoster would have to run a second service for the Live View, or Decent Sync would keep two paths. Revisit if live samples reach hundreds a second, such as with a Location's Machines shown live together, or measurements show `NOTIFY` contention or listeners falling behind; a change would amend ADR-0016.

## Consequences

- **ADR-0009 is amended.** The server also pushes to the management interface, one way, over Server-Sent Events. The plugin still speaks to the server only over its WebSocket.
- **Samples share PostgreSQL's notification lock.** A transaction that sends a `NOTIFY` takes a database-wide lock as it commits, so live samples briefly queue with the other notifications (ADR-0016). At Roux's scale, a handful of Machines at Decaid's sample rate, this is far from a limit. Notifications are not written to the write-ahead log.
- **Every instance receives every sample,** whether or not it has a viewer of that Machine.
- **The stream keeps itself alive.** It sends a comment when it has had nothing to send for 15 s, as an offline or sleeping Machine sends nothing, so proxies such as fly.io's don't close it as idle. The browser's `EventSource` reconnects by itself.
- **The plugin's transports.** Decaid allows a plugin 8 transports (ADR-0009). While streaming, the plugin holds up to seven: its connection to the server, DYE2's `changed` socket and five of Decaid's local sockets.
- **Samples may wait behind a delivery.** They share the plugin's connection with the outbox, so a sample can wait a moment behind a large Shot upload.
- **Tests.** The relay and the leases are tested with two instances on one database (`startTestServer({ sharing })`).
