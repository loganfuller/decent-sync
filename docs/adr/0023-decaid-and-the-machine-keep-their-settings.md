# Decaid and the Machine keep their own settings, and the management interface edits them live

The management interface edits a Machine's Machine Settings and its Tablet's Tablet Settings, which Decaid lets a plugin write through its API. Decaid and the Machine stay the source of truth for them, unlike the Library (ADR-0003). A Settings Edit is a one-off write the plugin makes through Decaid's documented routes, those Streamline's settings page uses where it has them, and the setting is then whatever the tablet reports. Nothing holds what a setting should be, and nothing of Decent Sync's puts back a change made on the tablet afterwards: the latest change stands, whichever side made it. An edit is made only while the Machine is online (a Tablet's connection holds it and was heard from recently), to that Tablet, and is never queued. It reaches any Machine with an entry, whatever its Location or sharing, as it is no Library write: a Capture-only Machine takes no part in the Library, but its settings are still edited.

## Considered Options

- **Managed settings, as the Library is.** The server would hold each setting and write it back whenever a tablet drifts from it. Rejected: it fights a barista's change made on the tablet. Writing back what Decaid v0.9.0 reset on each reconnect would also have been a workaround for decentespresso/decaid#1027, needing an interim ADR of its own (AGENTS.md), and since Decaid v0.9.1 keeps those settings (below) nothing is left to write back. The deferred shared machine settings, one Machine's settings copied to others, may revisit this.
- **A queue.** An edit made while the Machine is offline would wait for its next connection. Rejected: a change landing hours later, over a change a barista made meanwhile, surprises both, and settings are not Library items with ADR-0020's per-field rules to decide between them.

## Consequences

- **Not everything reported is editable.** `GET /machine/settings` also reports the steam flow, the hot water flow and the flush flow, temperature and time, which are the Workflow's: Decaid writes the Workflow's back to the Machine on every reconnect (`_setDe1DefaultsFor` in `decaid:lib/src/controllers/de1_controller.defaults.dart`), and a Loaded Recipe holds them (ADR-0022). The tank temperature is set by every profile Decaid sends the Machine, and the USB charger by the Tablet's charging mode (`BatteryController` in `decaid:lib/src/controllers/battery_controller.dart`), which is editable instead. All of these are shown, read-only, with what sets them.
- **The Tablet keeps the fan threshold and refill kit.** Decaid writes both each time it connects to the Machine: the fan threshold in `_setDe1DefaultsFor`, and the refill kit to automatic as it first connects to a Machine it has discovered, which in practice is each reconnect (`UnifiedDe1.onConnect` in `decaid:lib/src/models/device/impl/de1/unified_de1/unified_de1.dart`). v0.9.0 wrote its own defaults, over any edit (decentespresso/decaid#1027). From v0.9.1, the minimum (ADR-0017), Decaid keeps a fan threshold or refill kit setting written through `POST /api/v1/machine/settings` or `/machine/settings/advanced`, the routes Settings Edits use, for that Machine, and writes it again on each connection, the refill kit's after its automatic setting (`_saveMachineSettings` in `decaid:lib/src/controllers/de1_controller.dart`; decentespresso/decaid#1043). It keeps them in the Tablet's own preferences (`MachineSettingsStore` in `decaid:lib/src/settings/machine_settings_store.dart`), by the serial the Machine reports as it connects (its device id where that is empty or `0`), for at most 32 Machines, and leaves them out of its backups. So an edit of either lasts past a reconnect, and Decent Sync writes nothing back. A replacement Tablet, or a reset of Decaid's data, puts Decaid's defaults back: a fan threshold of 55, which the Machine holds as 50, and the refill kit on automatic. So does Decaid's own reset of the Machine's settings (`DELETE /api/v1/machine/settings/reset`). Decaid writes what it keeps shortly after it connects, not at once: the Machine is served as connected, its refill kit on automatic and its fan threshold as it held it, until Decaid has read its shot settings and then written what it keeps (`_initializeData` in `decaid:lib/src/controllers/de1_controller.dart`), later if those settings come late (`_deferStartupDefaults`), and not at all on a connection that can't read them. So a read in between, such as the plugin's full report as it reconnects, can show the refill kit on automatic until its next read of the Machine's settings, within a minute, and an edit of the refill kit made from that report is refused as changed since. The management interface says beside both fields that the Tablet keeps them, and `server/test/fixtures/decaid/simulated-devices-v0.9.1/` shows it.
- **The water refill threshold is left out.** Decaid reports it only on its water levels socket and not through its REST API, so it is left out until it does (decentespresso/decaid#1028).
- **Streamline puts back what a barista set in its settings page.** Each time its settings page opens, Streamline writes back any Machine Setting or advanced setting a barista saved there, but the heater voltage, that the Machine now holds differently (`checkMachineSettingsDrift` in `streamline-js:src/settings/settings.js`, with `streamline-js:src/settings/settings-restore.js`), as it remembers them in the page's own storage, which the plugin can't reach. So an edit of such a setting lasts until that page next opens on that Tablet. Decent Sync accepts the gap and the management interface says so, until Streamline takes a change made elsewhere as the new value, as the rule for skins asks (ADR-0021; decentespresso/streamline-js#172).
- **The plugin guards each edit.** Each edit carries the values held in the report the page showed, and the plugin refuses the edit if any field it sets changed since. It refuses any Settings Edit while the Machine is running anything, such as a Shot, steam, hot water, a flush or a cleaning cycle, as Decaid does not check, and some Tablet Settings change how a running Shot or hot water stops.
- **An edit is confirmed by reading it back.** Decaid announces no change of these settings, so after each write, refused or not, the plugin reads the collection again and reports it with its answer. The edit is applied; applied with another value than it asked for, as read back; refused, as too late, or with Decaid's error and the fields Decaid applied before refusing, as its settings writes are not atomic; or not confirmed within 60 s. The server sends an edit once, and the plugin starts no write of one with less than 15 s of its 60 s left, or once the connection that sent it closes, so one not confirmed is not started later, but for a write started as the server replaces the connection, before the plugin hears of it, whose answer is then recorded late. An answer arriving after an edit was marked not confirmed is still recorded as what came of it, but a refusal as too late leaves it not confirmed.
- **Sensor calibration is set to a value.** Decaid's write corrects the calibration the Machine holds. The management interface sets a value through Decaid's documented read-then-write instead, as Streamline's restore does. Calibrating against a reference instrument, which needs someone at the Machine, stays on the tablet.
- **Across instances.** A Settings Edit is a row in PostgreSQL, announced with `NOTIFY`. The instance whose connection holds the Machine sends it and records the answer, and any instance records an answer that reaches it after a reconnect (ADR-0016).
