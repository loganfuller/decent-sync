# The latest edit wins per field, not per record

ADR-0003 resolves conflicting edits to the same record by last writer wins. Taken per record, an edit to one field undoes a concurrent edit to another: if Uptown corrects a Bean's country while Belmont, offline, adds tasting notes to it, the later edit replaces the whole Bean and the other change is lost. So the server compares each edit with the version its tablet last had (ADR-0006 keeps that per tablet) and applies only the fields the edit changed. Two edits conflict only when both changed the same field without seeing each other. The later one wins, and the other is kept as a Conflict, which the management interface shows with where and when it was made until someone uses its value or dismisses it. Each piece of per-Location state (whether a Profile is shown, whether a Bean Batch is at a Location and its remaining weight there, each steam, hot water and rinse setting) is a field of its own. Decaid's update endpoints already change only the fields they are sent.

This amends ADR-0003 and ADR-0014.

## Consequences

- **Each item keeps its versions.** The server stores every accepted edit with the Machine or account that made it and when, which also gives each item a change history in the management interface.
- **Edit times are unchanged.** A tablet edit is timed by the record's `updatedAt` (ADR-0003), a management-interface edit by PostgreSQL's clock (ADR-0016). A delete on a tablet, which Decaid does not time, is timed by PostgreSQL's clock when the server learns of it, but never before the record that tablet last had.
- **What a tablet saw is judged by its record.** Each change to whether a Bean Batch is at a Location or a Profile is shown there is stamped with PostgreSQL's clock. A tablet's record of the item has seen a change when it answered a write the server made to it after the change, while the server awaited the answer, or when the change was the record's own edit, and it keeps the latest change it has seen; a report shows nothing of what the tablet saw of other tablets' changes, as it may have been read before them. A record that held a field of the item's content at the item's value when it was saved, after the field's last change, had seen that value too, however it came to hold it, as when its answer to a write came after the server had stopped awaiting it; a value set again since it was saved, as when one tablet changed it and another changed it back, it had not seen. A tablet reports in order, so what it reports of an item after its own edit decided the field last, as when it re-creates a Profile it deleted, was made after that edit, whatever its clock. Archiving or deleting a Bean takes its batches away (ADR-0019), so it is judged by what the tablet's record of the Bean has seen of its batches' changes, which only a write to the Bean shows: a write to one of the batches says nothing of when the Bean was archived, and the Bean's own archiving may leave batches added since in place. What a record has seen is of one Location: once its Machine moves, it has seen none of the new Location's changes until it is written or edits there. An edit from a tablet whose record had seen the field's last change applies whatever its time. Otherwise edit times decide: an edit timed before the one that set the field loses to it. An edit that applies is the field's latest change even when it leaves the value as it was, as when two tablets hide the same Profile, so an earlier edit that arrives later cannot undo it. That covers a tablet that was offline, and any record the server has not written to since the field's last change, which its own edit did not make, such as a Profile a barista re-creates after another tablet hid it; so a tablet whose clock runs behind another's can lose such an edit, a tablet clock error ADR-0003 accepts.
