# AI Build Notes

## Milestone 1 verification

Use the root package scripts listed in the README's Development section: `npm run typecheck`, `npm run build`, `npm test` (Vitest, after a build), `npm run test:e2e` (Playwright) and `npm run check:plugin-build`. CI (`.github/workflows/ci.yml`) runs all of them on every push to `main` and on every pull request that changes more than docs (anything under `docs/`, and Markdown other than `UPGRADING.md`), as parallel jobs: the checks, Vitest in four shards and Playwright in two, each test job starting a PostgreSQL container of its own in the background, one that does not wait for the disk. A newer push to a pull request cancels its older run, which then shows as cancelled, so read the newest run. Each test job logs its runner's CPU model, and per-core speed varies about 1.5x between runners, so compare CI timings as medians over at least 3 runs, or between jobs on one CPU model or Build-step band, never from one run. `vitest.config.ts` deals the test files out to the shards by size, largest first, which balances them far better than Vitest's own split by count. Its `package` job writes the plugin ZIP (`npm run package:plugin`) and runs `docker compose up --build`, checking that the image migrates and serves the management interface, without publishing anything. [The spec's Testing Decisions](https://github.com/loganfuller/decent-sync/issues/1) are the testing contract:

- Seam 1 runs the built `decent-sync.reaplugin/plugin.js` in a simulated Decaid host against a real server and a fresh PostgreSQL database per test file. Assertions use the REST API. Raw frames exercise protocol failures and delivery cases.
- Seam 2 uses Playwright against the management interface, with data seeded through Seam 1.
- Vitest module tests cover the spec's listed pure modules through their public interfaces without mocks. Other behavior is tested through the two seams unless it proves untestable there.

Seam 1's simulated tablet is `server/test/support/simulated-tablet.ts` (ticket #5, promoted from the archived [plugin dev harness](https://github.com/loganfuller/decent-sync-plugin/blob/main/scripts/dev-harness.mjs)). It runs the built `plugin.js` as Decaid v0.9.0 loads it, answers Decaid's API from `server/test/fixtures/decaid/`, and enforces Decaid's transport limits. Its header comment says how, and each option, method and fixture builder says what it simulates; read them before adding to it. Four things catch tests out. The plugin reads local times in the test process's time zone, so a test sets `process.env.TZ` to put the tablet in another. `timeScale` speeds up the plugin's timers but not the server, so the tablet's clock runs at real time from the moment a connection starts to open until the server first answers; a test of a server that never answers an upgrade sets `upgradeAtTabletPace` so its attempts time out quickly. The tablet's Decaid times its records by the test process's clock, and the server times what it stores by PostgreSQL's, which in Docker on macOS has run tens of milliseconds ahead of the host's on one day and behind it on another; so a test that orders two events timed by different clocks, in either order, such as a tablet's offline edit before a management-interface edit, or a tablet's change just after its Machine's sharing is turned back on, waits a second between them, and one that compares a stored time with the test's clock allows a second either way. And of Decaid's writes, the API carries out only those to beans, bean batches, grinders and profiles, to the Workflow (`server/test/support/decaid-workflow.ts`), to Decaid's store, and to the settings, as Decaid v0.9.0 does (`server/test/support/decaid-beans.ts`, `decaid-batches.ts`, `decaid-grinders.ts` and `decaid-profiles.ts`, which derives each profile's id from its content as Decaid does, replayed against requests recorded on Decaid's Linux release by `server/test/simulated-bean-writes.test.ts`, `simulated-batch-writes.test.ts`, `simulated-grinder-writes.test.ts` and `simulated-profile-writes.test.ts`), and refuses any other request but a `GET`. The settings writes (`decaid-settings.ts`, replayed by `simulated-settings-writes.test.ts` against `fixtures/decaid/settings-writes-v0.9.0/`, ticket #223) are the machine's (`POST /machine/settings`, `/machine/settings/advanced` and `/machine/calibration`), written as a DE1's registers hold them, truncated to their scale and held to their bounds, the flow multiplier then as the test DE1Pro's firmware held it (replayed against its reads in `fixtures/decaid/de1pro-v0.9.0/calibration-writes.json`, ticket #271), with heater voltage mapped as Decaid maps it, a sensor's (`PUT /machine/calibration/{target}`), a correction of the value it holds, Decaid's own (`POST /settings`), and its presence settings and wake schedules (`POST /presence/settings`, `POST /presence/schedules`, `PUT` and `DELETE /presence/schedules/{id}`, a schedule Decaid does not hold answering 404), each changing what the matching `GET` answers. Each applies its fields one at a time in Decaid's order, so `/settings` refusing a value leaves the fields before it applied, and `failSettingWrites` fails one field's write part-way with the answer it returns, the fields before it written. The machine routes, and `GET /machine/state`, answer 500 while `machineConnected` is false; `/settings` and the presence routes answer without a machine, `keepAwakeUntil` null then. `connectMachine()` sets the fan threshold to 50 and the refill kit to auto, as Decaid does on every connect, and `GET /machine/state` answers the state `reportState()` set. A tablet's presence settings start as a new install's (`newPresenceSettings()`), and `callApiWithText()` sends a body that is not JSON, answering a body that is not JSON as text; `writes` lists every one the plugin sent that is not a `GET`, and `requests` every route it requested, `requestedAt` holding when, by the tablet's clock (`readClock()`). `beans()`, `batches()`, `grinders()` and `profiles()` read what the tablet's Decaid holds, `addBean()`, `addBatch()` and `editBatch()` add and change beans and batches as a barista does in Decaid, `addGrinder()`, `editGrinder()` and `deleteGrinder()` grinders, `addProfile()` saves a profile as Streamline does, `setProfileVisibility()` shows, hides or deletes one, `editProfile()` changes one through `PUT`, which replaces it under a new id when its steps change, and `derivedProfile()` makes a profile to save, each pressure a Profile of its own, `deleteBean()` deletes a bean as DYE2 does, its batches first, since Decaid refuses to delete a bean that has any, `pullShot()` saves a Shot as one pulled there does, and `callApi()` calls Decaid's API as something else on the tablet would, such as another plugin, none of which the plugin is told of. Decaid's store keeps what other plugins and skins keep there, DYE2's recipes, baskets and tools included: a `POST` replaces a key's value and a `DELETE` removes it, a key never written answers `null`, a key's value starts as `api` serves it, and `serve()` replaces the store's values with the rest. `storeValue()` reads it and `storeWrites` lists the plugin's writes to it. `server/test/support/simulated-dye2.ts` acts as DYE2 v0.1.26 and streamline-js `main` at `cec5664` do on the tablet (ticket #216), checked against steps recorded from them on Decaid's Linux release (`fixtures/decaid/dye2-v0.1.26/`, `server/test/simulated-dye2-writes.test.ts` and the tests of the simulated DYE2's routes): `saveInDye2()` saves a recipe, a basket or a tool, created, edited or deleted, as DYE2's pages do, a recipe under an opaque id with its `stripSlot`, and `replayWrites()` replays a recorded step's writes, as a basket picked for the next Shot; `dye2Library()` is the library the recorded records name, `recordedDye2Tablet()` the recording's tablet with it, and `dye2NeverUsed()` a tablet where DYE2 was never used. DYE2 itself runs on a tablet loaded with a `SimulatedDye2` (`dye2` option): its clear of the Workflow's `recipeId` on a change of profile, from the profile it held when the id appeared (`idProfileChanged`), which after a restart is the Workflow's as Decaid sends it to DYE2 as it loads; its derived `selection` endpoint, its `record` and `save-recipe` routes, its one-time migration giving the records with ids `1` to `5` their `stripSlot`, its pushes on `changed`, which the plugin opens as a socket of Decaid's own, `unload()`, `disable()` and `load()`, and Decaid's `GET /plugins` listing it. Without one, Decaid answers DYE2's endpoints 404. `openDye2Dashboard()` opens DYE2's dashboard page, which reads a recipe again as it applies it and sets `recipeId` with it, and sends only its own edits over a fresh read of the Workflow (decentespresso/dye2#31); `recordedDye2MainTablet()` is the recording's tablet, holding three recipes. Streamline's DYE strip, placing recipes by `stripSlot` and applying one with its `recipeId`, its Save changes and long-press "Save to recipe" (`record` and `save-recipe`), its Drink and Dose tiles (sending the Workflow's own profile), its profile picker and wake (which clear `recipeId` as they send a profile) and its DYE2 switch are on `startStreamline()`'s skin; it clears nothing of the Workflow after a Shot but the note. Tests of the Loaded Recipe use these. The simulated Decaid writes a Workflow's profile steps back in the order Decaid's `ProfileStep.toJson` does, so a fingerprint taken of it reads the same whatever order it was sent in. `startStreamline()` (`server/test/support/simulated-streamline.ts`) runs Streamline as the tablet's skin, remembering the values given in the store, and, as streamline-js does from decentespresso/streamline-js#109 (ADR-0021), compares the Workflow with them: after each change of the Workflow while a machine is connected, as the machine's echo of it makes it, for steam time and hot water volume and temperature, and on `reload()` for every value but the steam temperature. It adopts a value changed elsewhere, and pushes only its own push the Workflow has not taken and a value for a setting the Workflow lacks. It sends the steam temperature it keeps with every steam time but 0 (`steamHeaterFor`), and never adopts it. Its `set()` is a barista's change made in it, `pushes` lists what it pushed, `adopted` what it adopted, `clock` can be held still to stay inside its 10 s echo window, and `settled()` waits until it has done what it does in reply. `apiDelayMs` slows every answer, or, as a function of the method and path, some; with `answerOnArrival` a request is answered from what Decaid holds when it arrives rather than once its delay is over, so a slow read can miss a write made meanwhile. A test that holds a read back by delaying it sets it too, or a read sent with no delay just before the hold, answered a moment later, brings what changed after the hold began (`recipeReadsHold` in `server/test/shot-recipe-links.test.ts`, #235). `serve()` replaces every response, the beans written included. Decaid's plugin storage, where the plugin keeps the tablet's id and the Workflow and machine state deliveries not yet acknowledged, belongs to a `PluginStorage` that outlives a load: pass a load the `storage` an earlier load of the same tablet used, or it starts empty, as a new tablet does; the tablet's `reload()` unloads the plugin and loads it again, as an update or a change of its settings does, on what its Decaid holds then, with the same storage and DYE2. Its `clear()` stands for resetting the tablet's Decaid data, `save()` and `restore()` for a Decaid backup, which, as Decaid's does, holds the plugin's values only once Decaid's store API has read them since the load began, and `failNextReads()` for a read Decaid never answers, of any key or of one; the plugin reads its kept deliveries as it loads, so a test of the tablet's id fails that key's reads. The tablet's `holdStorageAnswers()` holds Decaid's answers, as a slow Decaid does, so a test can unload the plugin with its storage commands unanswered. `RawConnection` sends raw frames, for protocol cases the plugin never produces: `welcomed()` connects with a `hello` (`helloWith()`, from a new tablet unless it is given a `tabletId`) and keeps the connection alive with heartbeats, `open()` and `welcomed()` can send upgrade headers a reverse proxy would add (`server/test/client-address.test.ts`), and `deliver()` resolves once a delivery is acknowledged. The other way round, `StandInServer` (`server/test/support/stand-in-server.ts`) stands in for the server on the sync endpoint, for the plugin's side of cases the real server reaches only in a race: it welcomes any `hello`, answers heartbeats, acknowledges every delivery, and `ask()` sends the plugin a `write`, `remove`, `delete` or `leaveOut` and resolves with its answer, as `send()` sends any other message, such as `requestCollections`. The simulated tablet's `host.emit` records what the plugin emits (`emits`, and `pushes()` for what a skin on one of its declared WebSocket endpoints heard; `onEmit` is called with each as it is sent, so a test reads what the tablet held then; `failEmits` makes it throw), and `callEndpoint()` calls one of its declared HTTP endpoints as Decaid dispatches it. Seam 1 tests use the REST API as an Admin through `server/test/support/admin-api.ts` (`get()` and `send()` expect a status and read the JSON answered, `waitForOnline()` waits for Machines' tablets to connect, and `staffAt()` invites and signs in a Staff member), load tablets with `syncingTablet()` (`server/test/support/loaded-tablets.ts`: one set up for a Machine at 50 times speed, polling every 5 s; `emptyLibrary()` is a tablet whose Decaid holds no library, and a `LoadedTablets` keeps those a beforeAll or a step loads, for the file's afterAll to unload), start a server with `startTestServer({ env })`, which also exposes its log through `output()`, and pass short `SYNC_HELLO_TIMEOUT_SECONDS` and `SYNC_HEARTBEAT_SECONDS` values to keep timeouts fast. Each test server records every token, link secret and session cookie it hands out, to any client (`server/test/support/secret-capture.mjs`, preloaded by `startTestServer`), and tests remember every token they hand a tablet; a server's or tablet's log holding one fails the test file once it has run (`server/test/support/secrets.ts`). `server/test/access.test.ts` checks who may use every route the server maps at startup, so a route marked `@Public()` or `@AllowStaff()` is named there.

`npm run check:plugin-build` rebuilds the plugin and fails if `decent-sync.reaplugin/` then differs from the git index (on a CI checkout, the commit under test). Report verification commands and results, including anything not exercised.

Vitest tests that need build output (the committed plugin, the compiled server) read it directly, so build before `npm test`; they refuse to start while a build is older than its sources (`server/test/support/builds.ts`), as Playwright does for the web build. Server tests run the built server as a process rather than importing Nest modules: Vitest's esbuild transform does not emit the decorator metadata Nest's dependency injection needs.

`server/test/support/test-server.ts` starts the built server on a fresh database (or, with `sharing`, as another instance on an existing server's database; `kill()` crashes it; `clockOffsetMs` runs its clock ahead or behind, for times that must come from PostgreSQL's clock, and `AdminApi.instanceClockOffsetMs` checks the offset reached the server's code; `notOwner` runs it as a role that does not own its database; `passwordHashGate` names a file: while it exists, every password hash the server starts waits, and `output()` reports each hash started and finished, so a test can hold password checks and count them; `databaseHost` connects it through another host, such as `startPoolerProxy()`'s in `server/test/support/pooler-proxy.ts`, which stands in for PgBouncer 1.26 in session mode, refusing the startup parameters it refuses by default and reporting each session's idle-in-transaction timeout; its `resetConnections()` resets every connection through it, as a lost network does) (created and dropped on the PostgreSQL server in `DATABASE_URL`) and a free port, starting it again on another if the port is taken before the server binds it, and counting it ready only once it logs that it listens there, never when another test file's server answers on that port; call it once per test file. Playwright spec files call `useFreshServer(options)` from `e2e/support/fresh-server.ts`, which does the same, points `baseURL` at it and runs the file's tests serially. They seed data with the same simulated tablets and raw connections (`e2e/machines.spec.ts`), and use `page.request` rather than `admin-api.ts`, which needs Vitest: `e2e/support/seed.ts` signs the Admin in (`signInAsAdmin`) and creates Locations and machine entries, and `e2e/support/locators.ts` finds a description list's field, a table's rows and a Machine's row. The tablets run in the Playwright worker, in its time zone, so `e2e/steam-records.spec.ts` writes each Steam Record's local `timestamp` from a UTC time in that zone (`steamAt`), and its records land at the same instants on any machine. Machine status in the management interface is polled every few seconds (`web/src/lib/use-polled.ts`), so specs waiting on it allow longer than Playwright's default 5 s. A Machine's page loads the rest (its Workflow, paired devices, settings, library, deliveries set aside and a mismatch's Pending Machine) every 30 s: a spec waiting on those installs the page's clock before it opens (`page.clock.install()`) and moves it on with `afterDetailsPolls` from `e2e/support/polling.ts`. To check that a page showed no alert, even briefly, such as an error before it went to sign-in, record them with `recordAlerts(page)` from `e2e/support/alerts.ts`. To check that a polling page notices its session ended within one poll interval, await `nextRefusedPoll(page, path)` from `e2e/support/polling.ts`, started just before the session ends. REST API tests send no `Origin`, as non-browser clients do; a test of browser behaviour must set it.

### Tests that stay reliable

- Never sleep to put events in order. Wait for something observable: an acknowledgment, a log line, a row's state, or a query waiting for a lock the test holds (`waitForLockWaits` in `server/test/support/lock-waits.ts`). Waiting for the lock also makes a test whose lock no longer matches the server's fail, rather than pass without testing anything.
- Bound times from below, not above: a limit on how long something may take fails on a busy machine. Leave the upper bound to a helper's timeout (`waitForLog`, `waitForMachine`, `expect.poll`). `vitest.config.ts` gives every `expect.poll` 15 s and every test and hook 60 s; pass a timeout only for work that takes longer than that.
- Decide a race by holding a lock that puts its sides in the order under test, rather than running it several times hoping to hit that order. Work an instance limits in its memory takes no lock; hold it at a gate instead, as `passwordHashGate` holds password hashes.
- Each test sets up the Machines and accounts it needs. A `describe` that is deliberately one scenario in steps calls `runAsSteps()` (`server/test/support/steps.ts`), so a failure is reported once and the later steps are skipped. Vitest's setup (`server/test/support/setup.ts`, `test-scope.ts`) unloads the simulated tablets and ends the raw connections a test opened, in its body or its `beforeEach`, once the test and its `afterEach` hooks have run, whether or not they passed: left running, a file's earlier tablets kept polling and heartbeating, and the server kept writing to them, which made its later tests several times slower. Those a step of `runAsSteps()` opens, or a `beforeAll`, stay open until the file's own `afterAll`, so a test that leaves a tablet for the next must be a step.
- `vitest.config.ts` caps Vitest at five workers, since more exhaust a local PostgreSQL's 100 connections; test runs in other worktrees on the same database count against them too. Playwright retries nothing, in CI either: a test that passes only on a retry fails.

## Releases

`.github/workflows/release.yml` publishes on a pushed `vX.Y.Z` tag: it checks the tag against the committed manifest (`scripts/check-release-tag.mjs`) and reads the version's upgrade notes from `UPGRADING.md` (`scripts/release-notes.mjs`, which fails while notes are left under Unreleased), waits for CI to have passed on the tagged commit as a push to `main` (it does not run CI again, and pull request runs do not count because they test a merge with `main`), pushes the server image to GHCR, then creates the GitHub release with the one plugin ZIP, its notes starting with those upgrade notes. A change owners must act on when upgrading, such as a plugin permission each tablet must approve, adds notes under Unreleased in `UPGRADING.md`. The README's Releasing section has the procedure. Pushing a release tag publishes to every Machine that installed by repo name, so tag, push or create releases only when explicitly asked. To check packaging, run `npm run package:plugin` and `docker compose up --build` locally; use a separate Compose project name and ports (`-p`, `DECENT_SYNC_PORT`, `POSTGRES_PORT`) when the development database is already running.

## Fixtures

Fixtures are records Decaid produced: real records from the test tablet where they exist, otherwise records from a Decaid build running simulated devices (it has a mock Bengle with a milk probe). Decaid's Linux release runs headless in a container with its simulated devices, and can load the built plugin; `server/test/fixtures/decaid/bengle-simulated-v0.8.7/README.md` records how, `simulated-devices-v0.8.7/README.md` a shorter start with Decaid's `--bypass-onboarding` and `--no-account` flags, and `simulated-devices-v0.9.0/README.md` one with the `tzdata` package installed, without which the container's `TZ` does not apply. DYE2's and Streamline's writes are recorded by driving their pages in Playwright's headless Chromium against such a Decaid, with the script and steps in `dye2-v0.1.26/`, and Decaid's answers to the settings writes by `settings-writes-v0.9.0/record.mjs`, whose README says what Decaid's simulated machine, which stores values unscaled, does not show. A derived fixture, such as a real Shot with its measurements repeated past 1 MiB (`longShot()` in `server/test/support/shot-fixtures.ts`), is allowed if its file or test names it as derived. Never hand-write a record shape. Trim fixtures, and scrub Barista names and notes before committing them: the repo is public. Replace hardware identifiers too (machine serials, Bluetooth and USB ids, LAN addresses) with made-up values, such as serial `10001`, addresses in `00:00:5E:00:53:xx` and IPs in `192.0.2.0/24`, and say so in the fixture's README.

## Real tablet

The last documented test endpoint is the DE1Pro tablet at `http://192.168.4.33:8080`, running Decaid 0.8.7+2847 on 2026-10-04, Decaid 0.8.8+2900 with DYE2 0.1.19 on 2026-10-12, Decaid 0.9.0+2977 on 2026-10-16, and the same with DYE2 0.1.26 and Streamline's `dist` build `55bd37d` on 2026-10-25, when #232's supervised run made the first real Settings Edits there. Confirm its identity and reachability before using it; a LAN address is not a permanent identity. Decaid's API definitions are in `decaid:assets/api/rest_v1.yml`.

The tablet API is unauthenticated on the LAN. Read-only `GET` requests, for example to gather fixtures, are allowed once its identity is confirmed. Any write needs an explicit request. Installing or updating a plugin executes code there: do so only when explicitly asked, including uploads through `PUT /api/v1/plugins/:id/source` and release installation. Install only this project's code. Use the simulated tablet for routine verification. Check the relevant Decaid source before relying on host behavior.
