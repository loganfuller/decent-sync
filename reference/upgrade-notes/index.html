Upgrade notes

What to do when upgrading to a release, beyond running its server image and letting Decaid update each tablet’s plugin. From 1.4.0, the plugin and server of adjacent releases work together, upgraded in either order, and the new server runs beside the old one as it upgrades, so nothing here stops the server or recreates the database (ADR-0025). Earlier releases’ notes may still ask that. A server that skipped a release takes each release in turn (Upgrading).

Where a note has a tablet’s plugin updated or approved through Decaid’s API from its network (POST /api/v1/plugins/update, POST /api/v1/plugins/decent-sync.reaplugin/update/approve), Decaid v0.9.2 takes the request only with a token, as v0.9.3 and later do while “Require authorization for extension management” is on in Decaid’s Security settings on the tablet: send it as Authorization: Bearer <token>, which does no harm where none is asked. Make one on the tablet in Decaid, on its Decent Account page under API access tokens, with “Manage plugins and skins” turned on. It is shown once, and needs no Decent Account sign-in (A token for managing plugins).

Each release’s notes on GitHub start with its section here. Notes for the next release wait under Unreleased until it is tagged (see docs/DEVELOPMENT.md, Releasing).

1.15.0

Check every tablet runs the 1.13.1 plugin or later before deploying

This release raises the wire revision, for a Skin’s scan of a Bean Batch’s QR code (ADR-0025, Deploying). Before deploying, check on each Machine’s page that it runs the plugin of 1.13.1 or 1.14.0. A tablet still on the 1.13.0 plugin or earlier is refused as too old until its plugin is updated, at the tablet or through Decaid’s API from its network with POST /api/v1/plugins/update. This release’s plugin adds no permission, so Decaid installs its update without approval.

A Skin can have a scanned Bean Batch brought to its Machine’s Location

The plugin has a new request for a Skin, scan (For a Skin’s author): the Skin reads the QR code on a bucket’s label and sends the text it held, and the server finds the Bean Batch by it and brings the batch to the Machine’s Location. A batch at one other Location is moved from there, all of it, with its remaining weight. One at several other Locations, or at none, is added with no weight moved. Nothing is created or brought back from the archive. There is nothing to do before or after deploying, and nothing changes until a tablet runs a Skin that scans:

  • A scan needs no account. Anything on a tablet’s network can ask its plugin, as it can change the tablet’s Workflow through Decaid, and a batch is only ever brought to that tablet’s own Location. A Capture-only Machine is refused.
  • The batch’s history says who received it. The entry names the Machine the scan was made on and the barista named on that Machine then, such as “Bar Left, by Sam”, and no account. A wrong move is corrected by moving back.
  • The text need not be a Batch Code. A URL or JSON that holds one matches too, and so does a Bean’s roaster and name, with a roast date to pick among its batches. A label that matches several batches moves nothing until the barista chooses one.

While the upgrade runs, a tablet whose plugin has updated but which is still connected to the previous release’s server refuses a scan, and its status tells the Skin so, until it reconnects to the new one. A tablet still on the previous release’s plugin has no such request until its plugin updates.

Baristas enter a batch’s weight and finish a batch in the Streamline Cafe Skin

A barista enters what is left of a Bean Batch, and finishes one, at the Machine: in the Streamline Cafe Skin’s bean and batch dialog, Enter weight on a highlighted batch (Track how much of a batch is left). The Skin has it from Streamline Cafe v0.2.34-cafe.1. Nothing in the server or the plugin changed for it, and there is nothing to do before or after deploying beyond updating the Skin on each tablet, on its Machine’s Software tab:

  • It is a weight entered at the Machine’s Location. The batch’s history names the Machine it was entered on and no account. It arrives with the tablet’s next report, every 30 seconds unless its plugin’s poll interval was changed, or once the tablet reconnects where the server could not be reached.
  • Nothing left finishes the batch there. Where the weight entered leaves nothing, the Skin’s button reads “Finish batch”, and the batch is finished at that Location, as Finish here does.
  • The container’s weight is set in the Skin, on each tablet. The Skin takes it off what the scale reads. It is the Skin’s “Batch container weight” setting, 0 until set, which Decent Sync neither holds nor sets.
  • A weight the tablet showed earlier may not be taken. A weight entered in the Skin that equals one of the last sixteen the tablet’s record held since the Location’s count last started is not taken as entered, and the tablet goes back to showing the weight worked out. Enter it in the management interface instead.

A Skin’s author enters a weight and finishes a batch the same way (For a Skin’s author).

A Bean Batch is now moved between Locations

A batch is taken from one Location to another by a Batch Move, all of it or part of its weight (ADR-0037). Nothing is migrated: a batch that is at several Locations stays at each, with the weight entered at each. There is nothing to do before or after deploying, but the batch’s page changes:

  • Move to… replaces Add it at. Each Location in a batch’s Where it is card has Move to…. Moving part lowers the weight at the Location it leaves and raises the weight at the Location it joins by the same amount. Moving all takes everything left and finishes the batch at the Location it left, as Finish here does. The page no longer adds a batch at a second Location without moving it; a batch at no Location is still offered one to add it at.
  • A batch with no weight entered moves as all of it or some of it, and no weight changes. To move a known amount, enter its weight first.
  • Staff move a batch when the Location it leaves or the one it joins is one they work at. Entering a weight, finishing a batch and adding one without moving it still need that Location.
  • Assistants move weight with move_bean_batch. set_location_offering still adds a batch at a Location, and moves no weight from any other. Over the REST API a move is POST /api/bean-batches/:id/moves, and PUT /api/bean-batches/:id/locations/:locationId adds, finishes and enters a weight as before.
  • On tablets, a batch’s remaining weight follows moves. After a move, the tablets at the Location it left and at the Location it joined each show their Location’s new weight.

While the upgrade runs, a page still open from the previous release shows a batch’s weight without the moves made since it was entered, and its Add still adds a batch at a Location, moving no weight. Reload the page. A new page that reaches a server still on the previous release can’t move a batch until the upgrade is done, and says so.

A Bean Batch’s remaining weight now falls with each Shot

A batch’s remaining weight at a Location is now worked out: the weight last entered there, less the dose of each Shot pulled there with the batch since (ADR-0037). Nothing is migrated, and there is nothing to do before or after deploying, but what you see changes:

  • A weight already entered falls at once. A weight entered before this release is read less the Shots pulled at its Location since it was entered, so an old entry may read much lower than it did, or zero. Weigh the bucket and enter the weight again to correct it. A batch with no weight entered stays as it was, and reads “Not tracked”.
  • Entering a weight of zero finishes the batch at that Location, in the management interface, over the REST API, through an assistant and on a tablet. A weight that reaches zero through Shots finishes nothing.
  • A new batch is created at exactly one Location. The create_bean_batch assistant tool and the New Batch dialog take one: create it at one, then move it to the others. So that a page still open from the previous release goes on working, the REST API still takes no Location or several in this release, each Location then starting at the weight given for it or untracked; the next release refuses them there too. A batch created at one Location with a roasted weight and no remaining weight starts at that weight; send remainingWeight: null to leave it untracked.
  • A create or an add with a remaining weight of zero is refused.
  • On tablets, a batch’s remaining weight now falls too. Each tablet at a Location is set to the batch’s remaining weight there after each Shot, so DYE2 and a Skin show what is left. A weight the server sets is not a weight entered, and adds nothing to the batch’s history. While the upgrade runs, a tablet connected to the previous release’s server is set to the weight last entered instead, until it reconnects to the new one.

While the upgrade runs, a page still open from the previous release may show a batch’s weight as entered where a new page shows it worked out, and its Set finishes a batch whose weight field reads 0, as a zero entered now does, without saying so first. Reload the page. A zero entered through a server still on the previous release is kept as a weight and finishes nothing: finish the batch there afterwards if it stays at 0 g.

1.13.1

Check every tablet runs the 1.13.0 plugin before deploying

This release raises the wire revision, for changing how a plugin or Skin updates (ADR-0025, Deploying). Before deploying, check on each Machine’s page that it runs the plugin of 1.13.0. A tablet still on the 1.12.2 plugin or earlier is refused as too old until its plugin is updated, at the tablet or through Decaid’s API from its network with POST /api/v1/plugins/update. This release’s plugin adds no permission, so Decaid installs its update without approval.

Changing how a plugin or Skin updates

An Admin can now change how an installed plugin or Skin updates, from its row’s menu on a Machine’s Software tab (ADR-0035). No step is needed, in either order of upgrading:

  • A tablet takes the change only once its plugin is this release’s. Until then the form says its plugin must update, and every other Software Action works as before.
  • To offer pinning an item where it is now, the server asks GitHub (api.github.com and github.com, over HTTPS, without credentials) as the form opens. A server that can’t reach GitHub offers the other choices.

1.13.0

The Conflict routes are gone

The routes 1.12.2 kept for a page of the release before it, GET /api/conflicts, each item’s GET .../:id/conflicts, and POST /api/conflicts/:id/use and /dismiss, are removed, and answer 404. Lost Edits are read in each item’s GET .../history, as in 1.12.2.

No step is needed. The upgrade deletes the Conflicts that were dismissed before 1.12.2, which no release has shown since; every other Lost Edit stays in its item’s History.

Tablets need Decaid v0.9.3

This release follows Decaid v0.9.3 (ADR-0017), as its plugin manages a tablet’s plugins through it (ADR-0034). Before deploying, update each tablet’s Decaid to v0.9.3 or later, at the tablet: Android asks someone there to confirm the install. Then, once every tablet runs the 1.12.0 plugin or later (below), deploy the server. It refuses a tablet on Decaid v0.9.2 or older, and its Machine’s page says why, though 1.12.2 still accepts one while it serves beside this release. On a tablet that updates to it:

  • Decaid turns its protection of plugin and Skin management off as it updates, so anything on the tablet’s network can install a plugin there until Require authorization for extension management is turned on in Decaid’s Security settings on the tablet. Turned on, the tablet asks a token as v0.9.2 did (docs/PLUGIN.md, A token for managing plugins). Either way, v0.9.3 refuses a browser page whose address is not the tablet’s own numeric one or localhost, which v0.9.2 did not.
  • v0.9.3 bundles 21 more Profiles: Decaid’s calibration and leak tests, a forward flush, and espresso Profiles such as the E61 ones. The first tablet at a Location to update reports them, and they join the Library shown at that Location, those for cleaning and calibration included. Hide the unwanted ones at the Location, and its tablets are written the same. A tablet still on v0.9.2 lacks them: bundled Profiles are never written.
  • v0.9.3 bundles DYE2 v0.1.42 and Streamline v0.2.31, the minimums ADR-0017 names, so it puts neither over a supported one.

Check every tablet runs the 1.12.0 plugin or later before deploying

This release raises the wire revision, for Software Actions (ADR-0025, Deploying). Before deploying, check on each Machine’s page that it runs the plugin of 1.12.0 or later, 1.12.2’s among them. A tablet still on the 1.11.1 plugin or earlier is refused as too old until its plugin is updated, at the tablet or through Decaid’s API from its network with POST /api/v1/plugins/update.

A tablet on the 1.12.2 plugin keeps syncing with this server, but is sent no Software Action until it runs this release’s plugin: its Machine’s Software tab says the plugin must update, and an action made for it is refused. The Draft page’s list of Machines no longer has one needing its plugin updated: every plugin this server accepts can follow a Draft, and the REST API’s needsPluginUpdate is always false.

The plugin’s update waits for approval on each tablet once

This release’s plugin adds two permissions: manage.extensions, with which it manages the tablet’s plugins and Skins when an Admin asks (docs/PLUGIN.md, Permissions), and notifications, with which it says on the tablet why it stopped syncing (docs/PLUGIN.md, When the plugin stops syncing). Decaid installs an update that adds a permission only once someone approves it, so each tablet keeps the plugin it runs until then, which works with this server and the previous one. Approve it once on each tablet, before or after deploying:

  • at the tablet, in Decaid’s Settings, Plugins: Review, then Approve and update; or

  • from the tablet’s network, with a token where the tablet asks one (above):

Decaid finds the update at its next update check, within 12 hours while its automatic update checks are on, or at once with POST /api/v1/plugins/update or Check for updates under Plugins. This approval can’t be made from the management interface, as the plugin it replaces takes no Software Actions. From the next release that adds a permission, an Admin approves the plugin’s own waiting update on the Machine’s Software tab.

With manage.extensions, an Admin’s account, or the server itself, can put code on every connected tablet: install any plugin, change any plugin’s settings and approve any update’s permissions. Decaid shows no warning on the tablet for a plugin installed through its API. Give the Admin role only to people trusted with every tablet.

A Machine’s Software tab manages its tablet’s software

Each Machine’s page gains a Software tab, between Settings and Setup, which shows its tablet’s Decaid, with the update it offers, every plugin and Skin, each with its version and how it updates, and what the tablet shows (docs/COLLECTIONS.md, Software Actions). An Admin installs, enables, disables, configures, checks for updates, approves and removes plugins there; installs, updates and removes Skins and chooses the default one; and asks Decaid to check for its own update and starts it, which Android then asks someone at the tablet to confirm. Each is a Software Action made once while the tablet is connected, and logged on the tab; all but the check for Decaid’s update need the Machine idle. The Skin on screen is reloaded from the tab, where the Skin reports the page it shows (docs/PLUGIN.md, Reloading the Skin), and the Skin view restarted from it, which brings back the default Skin: an Admin may ask for either, and so may Staff at the Machine’s Location. Staff and Viewers read the tab; the values of plugins’ settings show to Admins only, and a secret only as set or not set. Assistants read a Machine’s software with get_machine_software and list_software_actions, and make no Software Action but reloading the Skin or restarting the Skin view, with reload_skin. Each plugin’s settings now join the Machine’s Settings History. Nothing is needed.

Automatic update checks are changed on the Software tab, by Admins

An Admin turns a tablet’s automatic update checks on or off on its Machine’s Software tab again, as a Settings Edit, once the tablet runs this release’s plugin, which writes them through Decaid’s plugin host. Decaid follows the change when it next starts. Staff can’t change them, nor can an assistant: edit_machine_settings refuses them. On a tablet still running the previous release’s plugin, the edit is refused, and the page says its plugin must update.

While the checks are off nothing on the tablet updates by itself, this plugin included, so Decaid finds this release’s plugin there only when someone checks for updates, at the tablet or with POST /api/v1/plugins/update. Check each Machine’s Software tab for checks left off, and turn them on where the tablet should keep up to date.

1.12.2

Tablets need Streamline v0.2.31

This release follows Streamline v0.2.31 (ADR-0017). Decaid installs the latest Streamline on each tablet within 12 hours by itself. A tablet whose Streamline is pinned to an earlier build is moved to v0.2.31 or later by hand first, and one running a Skin built on Streamline, such as Streamline Cafe, to a build of it on v0.2.31. Then deploy the server. Nothing refuses an older Streamline, but nothing is written for what it does: the strip of v0.2.28 or earlier applies no steam temperature, so on a tablet still running the previous release’s plugin a Recipe loaded from it leaves steam off where it was off.

From v0.2.29, a hold on Streamline’s Sleep button closes Decaid, which wakes the Machine as it is opened again. It is a setting of Streamline’s, on until turned off (“Hold Sleep to sleep and close the app”, under Sleep button on its settings page). While Decaid is closed its Machine shows offline in the management interface and nothing reaches its tablet, so turn it off on tablets that are to stay reachable.

Tablets need DYE2 v0.1.42

This release follows DYE2 v0.1.42 (ADR-0017). Decaid installs the latest DYE2 on each tablet by itself; a tablet whose DYE2 is pinned to an earlier build is moved to v0.1.42 or later by hand first. Then deploy the server. Nothing refuses an older DYE2, but nothing is written for what it does: DYE2 v0.1.41 or earlier applies a Recipe’s grind setting of 0 as none, clearing the Machine’s, and DYE2 v0.1.40 or earlier, which knows no archived basket, offers in its pickers every Basket hidden at its Location, as such a Basket is now archived on its list rather than removed.

A grind setting of 0 is a Recipe’s

A grind setting of 0 is now a dial position, as DYE2 v0.1.42 applies one (ADR-0022, What 0 means). Saved on a tablet, or set in the management interface or through an assistant, it is the Recipe’s: shown, written to the Location’s other tablets, and left in a Machine’s Workflow as the Recipe loads. A dose or RPM of 0 is still none.

Nothing puts back the grind settings of 0 that 1.10.1 removed from Recipes: no record was kept of which Recipes held one. Where a tablet’s recipe still holds a 0 that its Recipe holds none of, the server writes it none, as the Recipe holds it; set the 0 again where it was meant.

As DYE2 v0.1.42 loads, it repairs each of its recipes saved at a grind setting of 0 before it, which then cleared the Machine’s grind setting as it applied. That is no edit of the Recipe and writes nothing to other tablets.

While the previous release still serves beside this one during the deploy, it takes a grind setting of 0 saved on a tablet it holds as none, as it did, and shows a Recipe’s 0 as none. A Recipe set to 0 through this release then, from another setting, is written none to the tablets the previous release holds, and cleared from the Workflow of each of their Machines that has it loaded, so a Shot pulled there names no grind setting. Each is written the 0 again as its tablet reconnects to this release.

A Basket archived in DYE2 is hidden at its Location

From DYE2 v0.1.41 a barista can archive a Basket in DYE2’s Basket picker. Earlier releases took that as part of the Basket itself: it left the picker on every tablet at every Location, while the management interface still showed it shown and not Archived. Now archiving a Basket on a tablet hides it at that tablet’s Location only, as deleting it there does, and UNARCHIVE shows it there again. Hiding a Basket at a Location in the management interface or through an assistant archives it on that Location’s tablets, where it used to be removed from their lists, so a barista can bring it back there; showing it again unarchives it. A Basket Archived in the management interface is still removed from every tablet, and Tools are unchanged.

The release’s migration takes the archive earlier releases spread out of every Basket, and changes no Location’s state. A Basket archived that way before this release therefore reappears on every tablet wherever it is shown. Where it was meant to go, archive it again in DYE2 on a tablet at that Location, or hide it there in the management interface. A Basket removed from a tablet’s list under the old rule is not put back.

A Machine joining a Location still has its Workflow’s Basket cleared if the Location does not show it, though DYE2’s own archive leaves it named.

While the previous release still serves beside this one during the deploy, it takes a Basket archived on a tablet it holds as part of the Basket again, and writes that to the tablets it holds; it removes a Basket hidden at a Location from those tablets rather than archiving it. This release reads such a Basket as not archived, so the tablets it holds are written it unarchived wherever it is shown. Archive it again once the deploy is done.

Loading a Recipe turns steam on or off

Steam on and off now follows the Recipe, as DYE2 and Streamline v0.2.31 apply one (ADR-0022, Steam on and off). Nothing is needed, but baristas will see:

  • A Recipe holding a steam temperature turns steam on as it loads, at its steam temperature and time, on a Machine whose steam was off. So an espresso-only Machine, or one being descaled, has its steam turned on by loading such a Recipe. Give the Recipes it loads a steam temperature of Off, or none.
  • A Recipe can hold Off. Off saved in DYE2’s recipe editor, or a steam temperature of 0 set in the management interface or through an assistant, is the Recipe’s: loading it turns a Machine’s steam off, and saving it turns steam off on every Machine that has the Recipe loaded. Before, the server wrote the Recipe’s earlier steam temperature back over it.
  • Steam turned off at a Machine still changes nothing else. Its heater switch, or a steam time of 0 set there, changes no Recipe and no other Machine, and steam turned back on there takes the Recipe’s steam temperature and time.
  • Nothing turns a Machine’s steam on from elsewhere. A Recipe edited from Off to a steam temperature reaches a Machine that has it loaded once its steam is turned on there, or the Recipe is loaded again. Steam turned on at a Machine whose Recipe holds Off makes the Recipe hold the steam temperature and time it came on with, and the other Machines stay off.
  • A Recipe holding no steam temperature or time leaves a Machine’s steam as it is, as before.

While the previous release still serves beside this one during the deploy, it writes a Recipe’s earlier steam temperature back over Off saved on a tablet, as it did, and a tablet running its plugin, until Decaid updates it, leaves a Recipe’s steam temperature out of a Workflow whose steam is off, so only DYE2’s or Streamline’s own apply turns its steam on.

Four settings renamed

The Machine’s page names four settings as Streamline v0.2.31’s settings page does: “Weight look-ahead”, “Volume look-ahead” and “Hot water look-ahead”, which were the three flow multipliers, and “Flow calibration”, which was “Flow multiplier”. Their values and what they do are unchanged, and so are their names in the REST API and for an assistant (weightFlowMultiplier, volumeFlowMultiplier, hotWaterFlowMultiplier, flowMultiplier).

Lost Edits replace Conflicts

An edit to a Library item that loses to another made without seeing it is no longer a Conflict waiting for someone to use its value or dismiss it. It is a Lost Edit: an entry in the item’s History, on its page and for an assistant, marked “Lost Edit”, with its value, who or which Machine made it and when, and the change it lost to (ADR-0033). To bring a value back, edit the item. Which edit wins is unchanged. No Lost Edit is kept for a value that the tablet making the change itself held.

The Conflicts page, its link in the Library’s navigation and the Open Conflicts card on item pages are gone, and so are the assistant’s tools list_conflicts and resolve_conflict. get_library_item no longer takes conflicts: its history lists Lost Edits among the item’s edits, each with lost and lostTo. In the REST API, each item’s GET .../history returns lostEdits beside versions. The routes that listed, used and dismissed Conflicts stay for this release only, for a page of the previous one: those that listed them answer an empty list, and using or dismissing one answers 410 Gone. They are removed in a later release.

No step is needed. Each open Conflict becomes a Lost Edit in its item’s History, as does each whose value was used. One that was dismissed is not shown. A page of the previous release still open during the upgrade lists no Conflicts, and asks for a reload if one is used or dismissed from it.

Check each tablet’s wake profile. Streamline’s “Load Profile on Wake” (Settings, Wake Lock) works again from v0.2.19: a wake onto a profile other than the Loaded Recipe’s own sends that profile, which unloads the Recipe each time the Machine wakes. Turn it off on a Machine that follows Recipes.

1.6.1

A Recipe is shown on the strip by its slot alone

A Recipe no longer keeps a “Shown on the dashboard” setting of its own: it is on Streamline’s strip exactly while it is in a Recipe Slot (below). As it migrates the database, this release takes each Recipe 1.6.0 left in a slot but hidden out of that slot, so each strip still shows that button empty; put the Recipe in a slot again to show it. The setting is dropped from every Recipe, and each open Conflict over it is dismissed. Past versions in a Recipe’s history still show it.

Deploy it as any release, beside 1.6.0. For the minute or so that 1.6.0 still serves beside it:

  • A recipe hidden by Streamline’s “Clear button” on a tablet connected to 1.6.0, or with the switch on a 1.6.0 page, is shown again, as this release writes a record shown exactly while its Recipe is in a slot. Hide it again once the deploy is done.
  • A “Shown on the dashboard” value 1.6.0 saves then stays in the Recipe, where nothing reads it.
  • A tablet still connected to 1.6.0 is written its recipe records without whether they are shown, which DYE2 and Streamline read as shown, until it connects to this release.
  • A page of the management interface left open from 1.6.0 reloads at its next navigation. Until then, its Recipe page can’t create a Recipe or use the switch, which this release refuses.

Let each tablet update its plugin promptly, as Decaid does within 12 hours: the server writes the records of each Recipe naming no Bean once more, with DYE2’s explicit nulls for one (below), and only this release’s plugin makes that write.

Tablets need Decaid v0.9.1 and DYE2 v0.1.32

This release follows Decaid v0.9.1 and DYE2 v0.1.32 (ADR-0017). Update Decaid on each tablet to v0.9.1 or later before deploying: this release’s server refuses a tablet on an older Decaid, and its Machine’s page says why, though 1.6.0 still accepts one while it serves beside this release. Decaid installs DYE2 on every tablet within 12 hours of its release. Check that a tablet whose DYE2 is pinned runs v0.1.32 or later.

With Decaid v0.9.1, an edit of a Machine’s fan threshold or refill kit lasts past the Machine reconnecting: the Tablet keeps the value and writes it again each time it connects. So the Settings card no longer says they reset then, and says instead that a replacement Tablet, or a reset of Decaid’s data, puts Decaid’s default back. A page left open from 1.6.0 shows the old note until it reloads.

Three things change with DYE2 v0.1.32:

  • A Recipe naming no Bean means no bean as it is loaded: loading it, from DYE2 or Streamline’s strip, leaves the Machine with no bean batch, and the load no longer gives it the Machine’s. A batch picked once it is loaded is saved into it, with its Bean, as before. The server writes such a Recipe’s records once more, with DYE2’s explicit nulls for a Bean.
  • A Recipe is on Streamline’s strip exactly while it is in a Recipe Slot. The Recipe page’s “Shown on the dashboard” switch is gone, and hiding a recipe on a tablet, by Streamline’s “Clear button” or DYE2’s switch, takes it out of its slot at its Location.
  • A grind setting is kept as typed, as a three-dial grinder’s 1.1.0, and shown and edited so; one that reads as a number stays a number, and .5 and 0.5 are one setting.

1.6.0

Make Viewers once every instance runs this release

This release adds the Viewer, an account that sees everything Staff see and changes nothing. 1.5.0 can’t read an account or invite with that role: while one exists, its Accounts page fails for Admins, and a Viewer’s requests fail on it. So invite a Viewer, or change an account to one, only once no 1.5.0 instance runs. Before rolling back to 1.5.0, change each Viewer to another role, deactivated ones included, and revoke any Viewer invite still waiting. 1.5.0 then still fails to open the link of any other Viewer invite, used, revoked or expired, rather than saying it can no longer be used. A Viewer invite for an email that has since got an account through another invite isn’t listed to revoke, and keeps 1.5.0’s Accounts page failing until it expires, 7 days after it was made.

1.5.0

Check every tablet runs the 1.4.0 plugin before deploying

This release is the first to raise the wire revision, for the Live View’s messages (ADR-0025, Deploying). Before deploying, check on each Machine’s page that it runs the 1.4.0 plugin, the previous release’s. Where one doesn’t, update it at the tablet, or through Decaid’s API from its network with POST /api/v1/plugins/update, or approve an update that adds a permission with POST /api/v1/plugins/decent-sync.reaplugin/update/approve.

A Machine’s Live View shows nothing live while its tablet runs the 1.4.0 plugin, or while an instance of 1.4.0 holds its connection during the deploy.

Run the server from source on Node.js 26

The server now needs Node.js 26 or newer with Temporal, as nodejs.org’s builds have. It refuses to start without Temporal, which Node 24 lacks, as do some packaged builds of Node 26, such as Homebrew’s. The server image has it, so Docker Compose and fly.io need nothing. Running from source, start this release on Node.js 26. 1.4.0 runs on it too, so moving the old instance first is optional.

1.4.0

Upgrade without going offline from now on

This release runs beside 1.3.1, and each release from now on runs beside the one before it. Pages opened from 1.3.1 don’t reload into the new release by themselves, as later pages do at their next navigation: reload them once after upgrading.

On fly.io, set fly.toml up as docs/SELF-HOSTING.md’s fly.io section now shows: a blue-green deploy, a wait_timeout, a 10 s check interval and a kill_timeout of 150 s. Deploy this release, then run fly scale count 2. That deploy takes nothing offline, though 1.3.1 doesn’t drain as it stops, so a request under way on it then may fail.

A stopping server now still answers requests for 15 s (DRAIN_GRACE_SECONDS), which a single instance has no use for. Set it to 0 there: with Docker Compose, add DRAIN_GRACE_SECONDS: "0" to the server’s environment in docker-compose.yml, as this release’s file does. Otherwise each later restart waits 10 s, until Docker kills the server.

The health check reports the database in its body

/api/health answers 503 only while the server is stopping. While the server can’t reach its database, it answers 200 with "database": "unreachable" in its body, so a proxy routing by it sends the server traffic again as soon as the database is back, as after a failover. A monitor that took the 503 for the database being down reads the body instead.

1.1.0

Update DYE2 and Streamline on every tablet

This release follows DYE2 v0.1.26 (ADR-0017). A Machine that follows Recipes needs DYE2 v0.1.26 or later and, where Streamline is its skin, streamline-js from main at cec5664 or later, as Streamline v0.2.18, its latest release, cannot apply a recipe that holds a grinder or Basket. Decaid installs the latest DYE2 and Streamline releases on every tablet within 12 hours, so DYE2 is likely there already; Streamline needs that build installed until a release contains ea04f83.

The migration keeps the database

The server’s migration (server/prisma/migrations/20261024000000_recipe_record_ids/migration.sql) runs as it starts, and keeps every Recipe, its history and its Shots’ links. Each Recipe takes a record id, the id of its record on every tablet at its Location from now on: a Recipe in a slot keeps its slot’s number, the id its records have on the tablets now, and one in no slot is given a new one. A Location has five Recipe Slots now, so a Recipe in slot 6 or higher leaves its slot and stays at its Location. Every Recipe of a Location that is not Archived is written to each of its tablets, those in no slot included, which DYE2’s Select Recipe page lists. What the rules this release drops kept is dropped with them: each Loaded Recipe’s record of what its load write replaced, each tablet’s recipe values from before the server’s writes, the recipe records removed from a slot, and whether each Shot’s Workflow named a selection.

Apply each Machine’s recipe again

DYE2 v0.1.26 keeps no selection: it clears the field it wrote its selection into, and names a recipe in the Workflow only as one is applied. The migration also forgets which recipe each tablet’s Workflow last named. So each Machine’s Loaded Recipe unloads at its next Workflow, and it has none until a barista applies a recipe again, from Streamline’s strip or DYE2’s dashboard or Select Recipe page. Shots pulled meanwhile are linked to no Recipe.

1.0.0

Start the server on an empty database

This release’s database migrations start again, from one that creates the whole schema, so it doesn’t upgrade a database an earlier release migrated: the server refuses to start on one, as its migration finds the tables there already. Drop the database, or give the server a new one, before starting this release, then create the first Admin, the Locations and the Machines again. The Library ids an earlier database wrote into each tablet’s records name nothing in the new one, so each tablet’s report is taken in as its first.

Adopting Machines again joins each to its Location, and the Location’s state wins (docs/LIBRARY.md, Joining a Location). At each Location, adopt first the Machine whose tablet holds the beans, profiles, grinders, recipes, baskets and tools the Location should keep: a kind the Location already has is not taken from a Machine adopted after it, whose own are archived or hidden on its tablet, and its DYE2 recipes, baskets and tools removed from DYE2’s lists. Turn sharing off for a Machine whose tablet’s should stay as they are.

Install the plugin afresh on every tablet

Remove the plugin on each tablet (DELETE /api/v1/plugins/decent-sync.reaplugin on the tablet’s API, or under Decaid’s Settings, Plugins), then install it from this release as Install the plugin says, and give it its Machine’s new token. A fresh install takes its permissions, emit among them, without the approval an update from 0.3.0 would wait on. The plugin needs Decaid v0.9.0 or newer, and a Machine that follows Recipes DYE2 built from main at 2cf631c or later and, where Streamline is its skin, streamline-js from main at c006dac or later (ADR-0017).
